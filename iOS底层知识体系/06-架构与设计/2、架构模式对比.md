# 架构模式对比(MVC/MVVM/VIPER/TCA)

> 一句话总结：**架构模式决定状态与依赖的边界；从 MVC 到 TCA，复杂度与可测试性通常同步上升。**

---

## 1. 架构模式演进

### 1.1 MVC（Model-View-Controller）

**Apple 经典架构**：

```
┌─────────────────────────────────┐
│  View (UIView/UIViewController)   │
├─────────────────────────────────┤
│  Controller (UIViewController)   │
├─────────────────────────────────┤
│  Model (Data Model)             │
└─────────────────────────────────┘
```

**职责划分**：

| 组件 | 职责 | 示例 |
|------|------|------|
| **Model** | 数据和业务逻辑 | User, NetworkManager, DatabaseManager |
| **View** | UI 展示 | UIView, UIViewController, SwiftUI View |
| **Controller** | 协调 Model 和 View | UIViewController, Presenter |

**数据流**：

```
User Action → Controller → Model (Update)
              ↓
         View (Update)
```

**优点**：
- Apple 官方推荐，文档齐全
- 职责清晰，简单易懂
- 适合小型项目

**缺点**：
- Controller 容易臃肿（Massive View Controller）
- Model 和 View 耦合度高
- 难以测试

### 1.2 MVP（Model-View-Presenter）

**改进**：

```
┌─────────────────────────────────┐
│  View (Passive View)              │
├─────────────────────────────────┤
│  Presenter (Logic)                │
├─────────────────────────────────┤
│  Model (Data)                    │
└─────────────────────────────────┘
```

**与 MVC 的区别**：

```
MVC：Controller 同时持有 View 和 Model
MVP：Presenter 只持有 Model，View 通过协议与 Presenter 通信（被动视图）
```

**优点**：
- View 和 Model 完全解耦
- Presenter 纯逻辑，易于测试
- View 可以是 Mock 对象（单元测试）

**缺点**：
- Presenter 容易臃肿（God Object）
- 协议定义繁琐
- 代码量增加

### 1.3 MVVM（Model-View-ViewModel）

**现代架构**：

```
┌─────────────────────────────────┐
│  View (UIView/UIViewController)   │
├─────────────────────────────────┤
│  ViewModel (Bindable Model)      │
├─────────────────────────────────┤
│  Model (Data)                    │
└─────────────────────────────────┘
```

**数据绑定**：

```swift
// ViewModel
class UserViewModel: ObservableObject {
    @Published var userName: String
    @Published var userEmail: String

    private let model: UserModel

    init(model: UserModel) {
        self.model = model
        self.userName = model.name
        self.userEmail = model.email
    }

    func updateEmail(_ email: String) {
        model.email = email
        userEmail = email
    }
}

// View
struct ContentView: View {
    @StateObject private var viewModel = UserViewModel(model: UserModel())

    var body: some View {
        VStack {
            TextField("Email", text: $viewModel.userEmail)
            Text(viewModel.userName)
        }
    }
}
```

**优点**：
- ViewModel 不持有 View，解耦更好
- 支持数据绑定（Combine/RxSwift）
- ViewModel 可测试
- SwiftUI 原生支持

**缺点**：
- 学习曲线陡峭
- 数据绑定调试困难
- 过度设计风险

### 1.4 VIPER（View-Interactor-Presenter-Entity-Router）

**重型架构**：

```
┌─────────────┐  ┌──────────┐  ┌─────────┐  ┌──────┐  ┌────────┐
│  View      │←→│ Presenter│←→│Interactor│←→│Entity│  │ Router │
└─────────────┘  └──────────┘  └─────────┘  └──────┘  └────────┘
```

**职责划分**：

| 组件 | 职责 |
|------|------|
| **View** | UI 展示，用户交互 |
| **Presenter** | 协调 View 和 Interactor，处理 UI 逻辑 |
| **Interactor** | 业务逻辑，数据获取 |
| **Entity** | 数据模型（纯数据） |
| **Router** | 页面路由，导航 |

**数据流**：

```
User Action → View → Presenter → Interactor → Entity
    ↑                                      ↓
    └────────── Update ←──────────────────┘
```

**代码示例**：

```swift
// Protocol
protocol HomePresentable: class {
    var interactor: HomeInteractable? { get set }
    var router: HomeRoutable? { get set }
}

protocol HomeInteractable: class {
    var presenter: HomePresentable? { get set }
    func fetchUsers()
}

protocol HomeRoutable: class {
    func navigateToDetail(for user: User)
}

// Implementation
class HomeInteractor: HomeInteractable {
    weak var presenter: HomePresentable?
    var users = [User]()

    func fetchUsers() {
        // 获取数据
        users = [User(id: 1, name: "John")]
        presenter?.didFetchUsers(users)
    }
}

class HomePresenter: HomePresentable {
    var interactor: HomeInteractable?
    var router: HomeRoutable?

    func didFetchUsers(_ users: [User]) {
        // 更新 View
        view?.updateUsers(users)
    }
}
```

**优点**：
- 职责划分最细
- 高内聚、低耦合
- 高度可测试
- 模块化好

**缺点**：
- 代码量大
- 学习曲线陡峭
- 过度设计风险
- 小项目不适用

### 1.5 MVI（Model-View-Intent）

**一句话理解**：MVI就是把"用户点击按钮"变成"发送意图"，然后用"处理函数"计算新状态，最后更新界面。

**核心思想**：
```
用户操作 → 意图(Intent) → 处理(Reducer) → 新状态(Model) → 更新界面(View)
```

**生活类比**：
> 就像在餐厅点餐：
> - **Intent（意图）**：你说"我要一份宫保鸡丁"
> - **Reducer（厨师）**：根据你的意图做菜
> - **Model（菜品）**：做好的宫保鸡丁
> - **View（餐桌）**：把菜端到你面前

**与其他架构的区别**：

| 架构 | 数据流 | 状态管理 | 学习难度 |
|------|--------|----------|----------|
| **MVC** | 双向（混乱） | Controller分散 | ⭐ 简单 |
| **MVVM** | 双向（绑定） | ViewModel集中 | ⭐⭐⭐ 中等 |
| **MVI** | **单向（清晰）** | Model不可变 | ⭐⭐⭐ 中等 |
| **TCA** | 单向（严格） | Store统一管理 | ⭐⭐⭐⭐⭐ 困难 |

**为什么叫MVI？**
- **Model**：状态（数据），不可变
- **View**：界面，只负责显示
- **Intent**：意图，描述用户想做什么

**记忆口诀**：
> MVI = 用户有意图(Intent) → 电脑处理(Reducer) → 产生新状态(Model) → 界面更新(View)

**简单代码示例**：

```swift
// 1. 意图：用户想做什么
enum CounterIntent {
    case 加1
    case 减1
}

// 2. 状态：当前的数据
struct CounterModel {
    let 数值: Int
}

// 3. 处理：根据意图计算新状态（纯函数，输入相同输出一定相同）
func 计数器处理(state: CounterModel, intent: CounterIntent) -> CounterModel {
    switch intent {
    case .加1:
        return CounterModel(数值: state.数值 + 1)
    case .减1:
        return CounterModel(数值: state.数值 - 1)
    }
}

// 4. ViewModel：连接View和Model
class CounterViewModel: ObservableObject {
    @Published var 状态 = CounterModel(数值: 0)

    func 处理意图(_ intent: CounterIntent) {
        状态 = 计数器处理(state: 状态, intent: intent)
    }
}
```

**优点**：
- ✅ **单向数据流**：数据流向清晰，容易理解
- ✅ **意图驱动**：用户操作一目了然
- ✅ **易于测试**：处理函数是纯函数，输入输出确定
- ✅ **状态不可变**：Model是结构体，每次都创建新的，避免副作用
- ✅ **学习曲线平缓**：比TCA简单很多

**缺点**：
- ❌ **需要响应式编程**：要理解Combine或RxSwift
- ❌ **意图定义多**：每个用户操作都要定义Intent
- ❌ **性能开销**：每次都创建新的Model对象

**适用场景**：
- ✅ 中大型项目（10+个页面）
- ✅ 需要清晰的数据流
- ✅ SwiftUI项目
- ✅ 团队协作（职责明确）

**什么时候选MVI？**
```
✅ 选MVI的情况：
- SwiftUI项目
- 需要单向数据流
- 团队有响应式编程基础
- 项目规模中等

❌ 不选MVI的情况：
- 小型项目（MVC足够）
- 团队Swift经验不足
- 快速原型（开发速度优先）
```

### 1.6 TCA (The Composable Architecture)

**一句话理解**：TCA就是Redux的Swift版本，所有状态都存在一个Store里，界面通过发送Action来改变状态。

**核心思想**：
```
唯一状态库(Store) → 接收操作(Action) → 处理函数(Reducer)计算新状态 → 界面自动更新
```

**生活类比**：
> 就像银行的账户系统：
> - **State（账户余额）**：唯一的数据源
> - **Action（存取款操作）**：你要存钱或取钱
> - **Reducer（银行系统）**：计算新的余额
> - **Store（银行数据库）**：存储所有账户信息
> - **View（ATM屏幕）**：显示余额

**与其他架构的区别**：

| 架构 | 状态管理 | 数据流 | 复杂度 |
|------|----------|--------|--------|
| **MVC** | Controller分散 | 双向 | ⭐ 简单 |
| **MVVM** | ViewModel集中 | 双向 | ⭐⭐⭐ 中等 |
| **MVI** | Model不可变 | 单向 | ⭐⭐⭐ 中等 |
| **TCA** | **Store统一管理** | **单向** | **⭐⭐⭐⭐⭐ 困难** |

**为什么叫TCA？**
- **T**he：这个（特指一种架构）
- **C**omposable：可组合的（小的Reducer可以组合成大的）
- **A**rchitecture：架构

**5个核心概念**：
```
1. State（状态）：所有数据，唯一真理来源
2. Action（操作）：描述状态变化的事件，如"加1"、"减1"
3. Reducer（处理器）：纯函数，接收旧状态+操作，返回新状态
4. Store（仓库）：管理状态和处理器
5. Effect（副作用）：处理异步操作（网络请求、数据库）
```

**记忆口诀**：
> TCA = 银行存取款系统
> - Store = 银行（存所有账户信息）
> - Action = 存取款单（你的操作）
> - Reducer = 柜员（计算新余额）
> - State = 账户余额（当前状态）
> - Effect = 联网验证（异步操作）

**简单代码示例**：

```swift
// 1. 状态：计数器的值
struct CounterState {
    var count: Int = 0
}

// 2. 操作：可以做什么
enum CounterAction {
    case 加1
    case 减1
}

// 3. 处理器：根据操作计算新状态
let counterReducer = Reducer<CounterState, CounterAction> { state, action in
    switch action {
    case .加1:
        state.count += 1
        return .none  // 无副作用
    case .减1:
        state.count -= 1
        return .none
    }
}

// 4. 创建Store
let store = Store(
    initialState: CounterState(),
    reducer: counterReducer
)

// 5. SwiftUI界面使用
struct CounterView: View {
    let store: Store<CounterState, CounterAction>

    var body: some View {
        WithViewStore(store) { viewStore in
            VStack {
                Text("计数: \(viewStore.count)")
                Button("+") { viewStore.send(.加1) }
                Button("-") { viewStore.send(.减1) }
            }
        }
    }
}
```

**TCA的核心优势**：

| 优势 | 说明 |
|------|------|
| **状态可预测** | 单向数据流，状态变化清晰 |
| **易于测试** | Reducer是纯函数，输入输出确定 |
| **时间旅行** | 可以回退到任意历史状态（调试神器） |
| **可组合性** | 小的Reducer可以组合成大的 |
| **类型安全** | 编译期检查，减少运行时错误 |

**为什么TCA学习曲线陡？**
```
1. 概念多：State、Action、Reducer、Store、Effect、Environment
2. 函数式编程：要理解纯函数、副作用等概念
3. 样板代码多：每个功能都要定义State、Action、Reducer
4. 调试困难：数据流清晰，但问题排查需要适应
```

**适用场景**：
- ✅ 大型SwiftUI项目（20+个页面）
- ✅ 需要严格的状态管理
- ✅ 团队有函数式编程经验
- ✅ 需要时间旅行调试
- ✅ 长期维护的项目

**什么时候选TCA？**
```
✅ 选TCA的情况：
- 大型SwiftUI项目
- 团队函数式编程经验丰富
- 需要严格的状态管理
- 愿意投入学习成本

❌ 不选TCA的情况：
- 小型项目（MVVM足够）
- 团队Swift经验不足
- 快速原型（开发速度优先）
- UIKit项目（不是原生支持）
```

```swift
import ComposableArchitecture
import Combine

// 1. 定义State
struct AppState {
    var count: Int = 0
    var users: [User] = []
    var isLoading: Bool = false
    var errorMessage: String?
}

// 2. 定义Action
enum AppAction {
    case increment
    case decrement
    case fetchUsers
    case usersResponse(Result<[User], Error>)
}

// 3. 定义Environment（外部依赖）
struct AppEnvironment {
    var apiService: APIService
    var mainQueue: AnySchedulerOf<DispatchQueue>
}

// 4. 定义Reducer
let appReducer = Reducer<AppState, AppAction, AppEnvironment> {
    state, action, environment in

    switch action {
    case .increment:
        state.count += 1
        return .none

    case .decrement:
        state.count -= 1
        return .none

    case .fetchUsers:
        state.isLoading = true
        state.errorMessage = nil

        return environment.apiService.fetchUsers()
            .receive(on: environment.mainQueue)
            .catchToEffect(AppAction.usersResponse)

    case .usersResponse(.success(let users)):
        state.users = users
        state.isLoading = false
        return .none

    case .usersResponse(.failure(let error)):
        state.isLoading = false
        state.errorMessage = error.localizedDescription
        return .none
    }
}

// 5. 创建API Service
struct APIService {
    func fetchUsers() -> Effect<[User], Error> {
        return Future { promise in
            // 模拟网络请求
            DispatchQueue.main.asyncAfter(deadline: .now() + 1) {
                let users = [
                    User(id: 1, name: "张三"),
                    User(id: 2, name: "李四")
                ]
                promise(.success(users))
            }
        }
        .eraseToEffect()
    }
}

// 6. 创建Store
let store = Store(
    initialState: AppState(),
    reducer: appReducer,
    environment: AppEnvironment(
        apiService: APIService(),
        mainQueue: .main.eraseToAnyScheduler()
    )
)

// 7. SwiftUI View
struct ContentView: View {
    let store: Store<AppState, AppAction>

    var body: some View {
        WithViewStore(store) { viewStore in
            List {
                Section(header: Text("计数器")) {
                    HStack {
                        Text("Count: \(viewStore.count)")
                        Spacer()
                        Button("-") { viewStore.send(.decrement) }
                        Button("+") { viewStore.send(.increment) }
                    }
                }

                Section(header: Text("用户列表")) {
                    if viewStore.isLoading {
                        Text("加载中...")
                    } else if let errorMessage = viewStore.errorMessage {
                        Text("错误: \(errorMessage)")
                            .foregroundColor(.red)
                    } else {
                        ForEach(viewStore.users) { user in
                            Text(user.name)
                        }
                    }
                }
            }
            .navigationTitle("TCA Demo")
            .onAppear {
                viewStore.send(.fetchUsers)
            }
        }
    }
}

// 8. Preview
struct ContentView_Previews: PreviewProvider {
    static var previews: some View {
        ContentView(
            store: Store(
                initialState: AppState(),
                reducer: appReducer,
                environment: AppEnvironment(
                    apiService: APIService(),
                    mainQueue: .main.eraseToAnyScheduler()
                )
            )
        )
    }
}
```

**TCA实战案例：用户登录功能**

```swift
// 1. 登录State
struct LoginState {
    var email: String = ""
    var password: String = ""
    var isLoading: Bool = false
    var loginResponse: LoginResponse?
    var errorMessage: String?
}

// 2. 登录Action
enum LoginAction {
    case emailChanged(String)
    case passwordChanged(String)
    case loginButtonTapped
    case loginResponse(Result<LoginResponse, Error>)
}

// 3. 登录Environment
struct LoginEnvironment {
    var apiService: APIService
    var mainQueue: AnySchedulerOf<DispatchQueue>
}

// 4. 登录Reducer
let loginReducer = Reducer<LoginState, LoginAction, LoginEnvironment> {
    state, action, environment in

    switch action {
    case .emailChanged(let email):
        state.email = email
        return .none

    case .passwordChanged(let password):
        state.password = password
        return .none

    case .loginButtonTapped:
        state.isLoading = true
        state.errorMessage = nil

        return environment.apiService.login(email: state.email, password: state.password)
            .receive(on: environment.mainQueue)
            .catchToEffect(LoginAction.loginResponse)

    case .loginResponse(.success(let response)):
        state.isLoading = false
        state.loginResponse = response
        return .none

    case .loginResponse(.failure(let error)):
        state.isLoading = false
        state.errorMessage = error.localizedDescription
        return .none
    }
}

// 5. 登录View
struct LoginView: View {
    let store: Store<LoginState, LoginAction>

    var body: some View {
        WithViewStore(store) { viewStore in
            Form {
                TextField("邮箱", text: viewStore.binding(get: \.email, send: LoginAction.emailChanged))
                    .textInputAutocapitalization(.never)
                    .keyboardType(.emailAddress)

                SecureField("密码", text: viewStore.binding(get: \.password, send: LoginAction.passwordChanged))

                if viewStore.isLoading {
                    ProgressView()
                } else {
                    Button("登录") {
                        viewStore.send(.loginButtonTapped)
                    }
                    .disabled(!viewStore.isValidForm)
                }

                if let errorMessage = viewStore.errorMessage {
                    Text(errorMessage)
                        .foregroundColor(.red)
                }
            }
            .navigationTitle("登录")
        }
    }
}

// ViewStore扩展
extension LoginState {
    var isValidForm: Bool {
        return !email.isEmpty && !password.isEmpty && password.count >= 6
    }
}
```

**优点**：
- 单向数据流，状态可预测
- 纯函数Reducer，易于测试
- 可组合性强，Reducer可以组合
- 适合SwiftUI
- 支持时间旅行调试
- 状态管理统一

**缺点**：
- 学习曲线陡峭
- 样板代码多
- 过度设计风险
- 调试相对困难

**适用场景**：
- 大型SwiftUI项目
- 需要严格状态管理
- 团队协作（多人开发）
- 需要时间旅行调试

### 1.7 Clean Architecture（整洁架构）

**一句话理解**：Clean Architecture就是把业务逻辑放到最核心层，让它不依赖任何UI框架或数据库，这样无论技术怎么变，核心逻辑都不用改。

**核心思想**：
```
外层依赖内层 ✅
内层不依赖外层 ✅
业务逻辑独立于框架 ✅
```

**生活类比**：
> 就像盖房子的**建筑图纸**：
> - ** Entities（核心设计）**：房子的设计图（不管用什么材料建）
> - ** Use Cases（功能）**：客厅要能看电视、卧室要能睡觉
> - ** Presentation（展示）**：用砖头还是木板装修
> - ** Data（数据）**：从哪里买材料、怎么运过来
>
> **核心原则**：设计图不关心用什么材料，材料可以换，但设计图不用改。

**三层架构**：

```
┌─────────────────────────────────────────┐
│      Presentation Layer (展示层)         │
│    ViewModel、ViewController             │
├─────────────────────────────────────────┤
│         Domain Layer (业务层)            │
│     Use Cases（用例）、Entity（实体）    │
├─────────────────────────────────────────┤
│          Data Layer (数据层)             │
│   Repository（仓库）、API、数据库         │
└─────────────────────────────────────────┘
```

**为什么叫Clean Architecture？**
- **Clean（整洁）**：业务逻辑清晰，不混乱
- **依赖倒置**：外层依赖内层，内层不依赖外层
- **独立于框架**：核心逻辑不依赖UIKit、Foundation

**与传统架构的区别**：

| 架构 | 业务逻辑位置 | 依赖关系 | 框架依赖 |
|------|------------|----------|----------|
| **MVC** | Controller里 | 双向依赖 | 强依赖UIKit |
| **MVVM** | ViewModel里 | ViewModel依赖Model | 依赖Combine |
| **Clean** | **独立的Domain层** | **外层→内层** | **不依赖任何框架** |

**3个核心层职责**：

```
1. Presentation Layer（展示层）
   - 职责：界面展示、用户交互
   - 包含：UIViewController、ViewModel
   - 可以依赖：Domain Layer

2. Domain Layer（业务层）← 最核心！
   - 职责：业务逻辑、实体、用例
   - 包含：Entity、Use Case
   - 不依赖任何层

3. Data Layer（数据层）
   - 职责：数据获取、存储
   - 包含：Repository、API Service
   - 可以依赖：Domain Layer
```

**记忆口诀**：
> Clean Architecture = 洋葱分层
> - 外层：展示层（看得见的界面）
> - 中层：业务层（核心逻辑）
> - 内层：数据层（数据来源）
>
> **依赖规则**：外层依赖内层，内层不依赖外层

**简单代码示例**：

```swift
// 1. Domain Layer（最核心，不依赖任何框架）

// 实体：纯数据
struct User {
    let id: String
    let name: String
    let email: String
}

// 用例：业务逻辑
protocol FetchUsersUseCase {
    func execute() -> AnyPublisher<[User], Error>
}

class FetchUsersUseCaseImpl: FetchUsersUseCase {
    private let userRepository: UserRepository  // 依赖接口，不依赖具体实现

    func execute() -> AnyPublisher<[User], Error> {
        return userRepository.fetchUsers()
    }
}

// 2. Data Layer（数据层）

// 仓库接口（在Domain层定义）
protocol UserRepository {
    func fetchUsers() -> AnyPublisher<[User], Error>
}

// 仓库实现（在Data层实现）
class UserRepositoryImpl: UserRepository {
    private let apiService: APIService

    func fetchUsers() -> AnyPublisher<[User], Error> {
        return apiService.fetchUsers()
    }
}

// 3. Presentation Layer（展示层）

class UserListViewModel: ObservableObject {
    @Published var users: [User] = []

    private let fetchUsersUseCase: FetchUsersUseCase

    init(fetchUsersUseCase: FetchUsersUseCase) {
        self.fetchUsersUseCase = fetchUsersUseCase
    }

    func fetchUsers() {
        fetchUsersUseCase.execute()
            .sink { users in
                self.users = users
            }
            .store(in: &cancellables)
    }
}
```

**Clean Architecture的核心优势**：

| 优势 | 说明 |
|------|------|
| **业务逻辑独立** | 核心逻辑不依赖UI框架，技术栈换了也不怕 |
| **易于测试** | 每层都可以独立测试 |
| **长期维护** | 业务逻辑清晰，易于理解和维护 |
| **团队协作** | 不同层可以由不同人开发 |
| **可扩展性**：新增功能不影响现有逻辑 |

**为什么Clean Architecture学习曲线陡？**
```
1. 分层复杂：要理解三层架构的职责边界
2. 依赖倒置：要理解接口和实现分离
3. 代码量多：每层都要定义接口和实现
4. 过度设计风险：小项目用这个太复杂
```

**适用场景**：
- ✅ 大型项目（20+个页面）
- ✅ 业务逻辑复杂（多模块、多交互）
- ✅ 需要长期维护（3年以上）
- ✅ 团队协作（5+人）
- ✅ 跨平台项目（iOS+Android共享业务层）

**什么时候选Clean Architecture？**
```
✅ 选Clean Architecture的情况：
- 业务逻辑复杂的项目
- 需要长期维护
- 多人协作
- 需要高可测试性
- 跨平台开发

❌ 不选Clean Architecture的情况：
- 小型项目（MVVM足够）
- 快速原型（开发速度优先）
- 业务逻辑简单（CRUD）
- 团队经验不足
```

```swift
// 1. Domain Layer（业务层，最核心）

// Entity（实体）
struct User {
    let id: String
    let name: String
    let email: String
}

// Use Case（用例协议）
protocol FetchUsersUseCase {
    func execute() -> AnyPublisher<[User], Error>
}

// Use Case实现
class FetchUsersUseCaseImpl: FetchUsersUseCase {
    private let userRepository: UserRepository

    init(userRepository: UserRepository) {
        self.userRepository = userRepository
    }

    func execute() -> AnyPublisher<[User], Error> {
        return userRepository.fetchUsers()
    }
}

// Repository协议（仓库）
protocol UserRepository {
    func fetchUsers() -> AnyPublisher<[User], Error>
    func fetchUser(id: String) -> AnyPublisher<User, Error>
}

// 2. Data Layer（数据层）

// Repository实现
class UserRepositoryImpl: UserRepository {
    private let apiService: APIService
    private let cacheService: CacheService

    init(apiService: APIService, cacheService: CacheService) {
        self.apiService = apiService
        self.cacheService = cacheService
    }

    func fetchUsers() -> AnyPublisher<[User], Error> {
        // 先从缓存读取
        if let cachedUsers = cacheService.loadUsers() {
            return Just(cachedUsers)
                .setFailureType(to: Error.self)
                .eraseToAnyPublisher()
        }

        // 缓存没有，从网络获取
        return apiService.fetchUsers()
            .handleEvents(receiveOutput: { users in
                self.cacheService.saveUsers(users)
            })
            .eraseToAnyPublisher()
    }

    func fetchUser(id: String) -> AnyPublisher<User, Error> {
        return apiService.fetchUser(id: id)
    }
}

// 3. Presentation Layer（展示层）

// ViewModel
class UserListViewModel: ObservableObject {
    @Published var users: [User] = []
    @Published var isLoading: Bool = false
    @Published var errorMessage: String?

    private let fetchUsersUseCase: FetchUsersUseCase
    private var cancellables = Set<AnyCancellable>()

    init(fetchUsersUseCase: FetchUsersUseCase) {
        self.fetchUsersUseCase = fetchUsersUseCase
    }

    func fetchUsers() {
        isLoading = true
        errorMessage = nil

        fetchUsersUseCase.execute()
            .receive(on: DispatchQueue.main)
            .sink { completion in
                self.isLoading = false
            } receiveValue: { users in
                self.users = users
            }
            .store(in: &cancellables)
    }
}

// SwiftUI View
struct UserListView: View {
    @StateObject private var viewModel: UserListViewModel

    init(viewModel: UserListViewModel) {
        self._viewModel = StateObject(wrappedValue: viewModel)
    }

    var body: some View {
        List {
            if viewModel.isLoading {
                ProgressView()
            } else if let errorMessage = viewModel.errorMessage {
                Text("错误: \(errorMessage)")
                    .foregroundColor(.red)
            } else {
                ForEach(viewModel.users) { user in
                    Text(user.name)
                }
            }
        }
        .navigationTitle("用户列表")
        .onAppear {
            viewModel.fetchUsers()
        }
    }
}

class DIContainer {

    private init() {}

    lazy var apiService: APIService = {

    }()

            cacheService: cacheService
```

**Clean Architecture实战：登录功能**

```swift
// 1. Domain Layer

// Entity
struct LoginCredentials {
    let email: String
    let password: String
}

struct AuthToken {
    let token: String
    let expiresAt: Date
}

// Use Case
protocol LoginUseCase {
    func execute(credentials: LoginCredentials) -> AnyPublisher<AuthToken, Error>
}

class LoginUseCaseImpl: LoginUseCase {
    private let authRepository: AuthRepository

    init(authRepository: AuthRepository) {
        self.authRepository = authRepository
    }

    func execute(credentials: LoginCredentials) -> AnyPublisher<AuthToken, Error> {
        // 验证邮箱格式
        guard credentials.email.contains("@") else {
            return Fail(error: AuthError.invalidEmail)
                .eraseToAnyPublisher()
        }

        // 验证密码长度
        guard credentials.password.count >= 6 else {
            return Fail(error: AuthError.passwordTooShort)
                .eraseToAnyPublisher()
        }

        // 调用Repository
        return authRepository.login(credentials)
    }
}

// Repository协议
protocol AuthRepository {
    func login(_ credentials: LoginCredentials) -> AnyPublisher<AuthToken, Error>
    func logout() -> AnyPublisher<Void, Error>
}

// 2. Data Layer

// Repository实现
class AuthRepositoryImpl: AuthRepository {
    private let apiService: APIService
    private let tokenStorage: TokenStorage

    init(apiService: APIService, tokenStorage: TokenStorage) {
        self.apiService = apiService
        self.tokenStorage = tokenStorage
    }

    func login(_ credentials: LoginCredentials) -> AnyPublisher<AuthToken, Error> {
        return apiService.login(email: credentials.email, password: credentials.password)
            .handleEvents(receiveOutput: { token in
                self.tokenStorage.save(token)
            })
            .eraseToAnyPublisher()
    }

    func logout() -> AnyPublisher<Void, Error> {
        return apiService.logout()
            .handleEvents(receiveOutput: {
                self.tokenStorage.clear()
            })
            .eraseToAnyPublisher()
    }
}

// 3. Presentation Layer

// ViewModel
class LoginViewModel: ObservableObject {
    @Published var email: String = ""
    @Published var password: String = ""
    @Published var isLoading: Bool = false
    @Published var errorMessage: String?
    @Published var isLoggedIn: Bool = false

    private let loginUseCase: LoginUseCase

    init(loginUseCase: LoginUseCase) {
        self.loginUseCase = loginUseCase
    }

    func login() {
        let credentials = LoginCredentials(email: email, password: password)
        isLoading = true
        errorMessage = nil

        loginUseCase.execute(credentials: credentials)
            .receive(on: DispatchQueue.main)
            .sink { completion in
                self.isLoading = false
            } receiveValue: { [weak self] _ in
                self?.isLoggedIn = true
            } failure: { [weak self] error in
                self?.errorMessage = error.localizedDescription
            }
            .store(in: &cancellables)
    }
}

// View
struct LoginView: View {
    @StateObject private var viewModel: LoginViewModel

    init(viewModel: LoginViewModel) {
        self._viewModel = StateObject(wrappedValue: viewModel)
    }

    var body: some View {
        Form {
            TextField("邮箱", text: $viewModel.email)
            SecureField("密码", text: $viewModel.password)

            if viewModel.isLoading {
                ProgressView()
            } else {
                Button("登录") {
                    viewModel.login()
                }
                .disabled(!viewModel.isValidForm)
            }

            if let errorMessage = viewModel.errorMessage {
                Text(errorMessage)
                    .foregroundColor(.red)
            }
        }
        .navigationTitle("登录")
    }
}
```

**优点**：
- 业务逻辑独立，易于测试
- 依赖倒置，高层不依赖低层
- 各层职责清晰
- 易于维护和扩展
- 适合大型项目

**缺点**：
- 代码量多
- 学习曲线陡
- 过度设计风险
- 小项目不适用

**适用场景**：
- 大型项目
- 需要长期维护
- 团队协作
- 业务逻辑复杂

### 2.2 如何选择？

**项目规模**：

```
小型项目（< 5 个页面）：
→ MVC

中型项目（5-20 个页面）：
→ MVVM + Combine
→ 或 MVI（如果需要单向数据流）

大型项目（> 20 个页面）：
→ UIKit：VIPER 或 MVVM + Module
→ SwiftUI：TCA 或 Clean Architecture
→ 团队协作：VIPER / Clean Architecture
→ 个人开发：MVVM / MVI
```

**团队规模**：

```
1-2 人：MVC 或 MVVM
3-5 人：MVVM + Module 或 MVI
5+ 人：VIPER / Clean Architecture / TCA
```

**技术栈**：

```
UIKit：
→ MVC（传统）
→ MVVM（推荐，结合Combine）
→ MVI（单向数据流）
→ VIPER（大型项目）
→ Clean Architecture（业务复杂）

SwiftUI：
→ MVVM（原生支持）
→ MVI（推荐，学习曲线平缓）
→ TCA（严格状态管理）
→ Clean Architecture（业务复杂）
```

**业务复杂度**：

```
业务简单（CRUD）：
→ MVC / MVVM

业务中等（有状态管理）：
→ MVVM / MVI

业务复杂（多状态、异步操作）：
→ TCA / Clean Architecture

业务非常复杂（多模块、多交互）：
→ Clean Architecture + VIPER
```

**何时选择MVI？**
✅ 需要单向数据流，但TCA太复杂
✅ SwiftUI项目，需要清晰的状态管理
✅ 中型项目，团队能力中等
❌ 超大型项目（考虑TCA或Clean Architecture）

**何时选择TCA？**
✅ 大型SwiftUI项目
✅ 需要严格的状态管理
✅ 需要时间旅行调试
✅ 团队有函数式编程经验
❌ 小项目（过度设计）
❌ 团队Swift经验不足

**何时选择Clean Architecture？**
✅ 业务逻辑复杂
✅ 需要长期维护
✅ 多人协作
✅ 需要高可测试性
❌ 小项目（过度设计）
❌ 快速原型（开发慢）
