## 2. 案例选择标准

一个 case 能成为 10 年以上高级 iOS 岗的面试案例，至少应满足其中 4 项：

- 有真实线上信号：Crash Issue、性能数据、用户反馈、告警、业务指标；
- 有完整证据链：现象 → 假设 → 验证 → 根因，而不是“猜测后改了”；
- 有技术取舍：说明为什么不用其他方案，及方案的副作用；
- 有本人 Owner 边界：自己主导了什么，协作方负责什么；
- 有前后验证：灰度、版本、重点场景、影响用户数或性能指标；
- 有可沉淀的防回退措施：压测、监控、测试、Review 或开关；
- 有业务约束：营收路径、实时性、用户体验、迭代节奏、兼容性等。

**反例**：只有“我加了一个 Hook”“本地没崩”“我用了 Instruments”的小修复，通常不足以单独讲成“最难问题”；可作为大案例的一个技术细节。

## 4. 与“最难的问题”总题的组合方式

### 推荐答案 A：语音房大型重构（优先）

用于回答“最难的问题”：核心营收业务、存量架构、消息洪峰、多人协作、渐进迁移与长期人效。稳定性/性能问题作为重构必须同时解决的业务约束，而不是额外堆砌的技术清单。

### 推荐答案 B：稳定性治理体系 + 一个关键战役

当面试官重点关注稳定性、性能或线上质量时使用：

```text
业务增长下，稳定性问题集中爆发
→ Firebase 只有部分 Crash 现场，无法直接映射业务状态
→ 先补数据、做场景优先级和根因修复，不先大规模 Hook
→ 建立 Crash / FOOM / 卡顿 / 内存的持续治理闭环
→ 立刻落到一个具体案例：C1 / C3 / C5
```

**不能只讲**“监控、告警、Hook、工具”；必须在 1～2 分钟内进入一个具体案例。

## 5. 每张案例卡的统一模板

```md
# Cx｜案例名称

## 1. 一句话定位
适合回答什么问题；证明什么能力。

## 2. 90 秒主回答
背景 → 线上信号 → 判断 → 方案与取舍 → 结果。

## 3. 事实证据
版本、场景、指标、日志、工具结果；待核实项单列。

## 4. 技术推理链
线上信号 → 假设 → 验证 → 根因。

## 5. 方案与取舍
为什么选它；替代方案；为何不选；风险、开关、灰度、回滚。

## 6. 验证与防回归
线上验证、压测、监控、测试、Review、后续机制。

## 7. 追问
只保留真正可能被高级面试官追问的 3～8 题。
```
