
这是本次训练采用的表达和审查框架，不冒充某公司的固定考题或评分标准。

## 2. ARC：修复有效不等于根因已经证明

### 2.1 最小对象图

```text
外部强引用 → VC
VC → Manager
VC → View
Manager → View
```

在没有其他持有关系的假设下，移除外部对 VC 的全部强引用不会留下回指 VC 的强引用。VC 释放自身的强持有关系；Manager 若也没有其他强持有者，会随之释放。View 何时释放由它剩余的持有关系决定，不能由 View 尚在内存中反推 VC 一定未释放。[A1]

准确说法是“外部对 VC 的强引用已经解除”，不是“对象图已经没有任何 strong 属性”。这张抽象图解释 ARC 规则，不证明真实 UIKit 页面恰好只有这些引用。

### 2.2 协议不是额外的一层对象

```swift
protocol RoomContext: AnyObject {
    var targetView: UIView { get }
}

extension RoomViewController: RoomContext {
    var targetView: UIView { view }
}

final class PluginManager {
    weak var context: (any RoomContext)?
}
```

如果赋值为 `manager.context = vc`，这里实际引用的是实现协议的 VC 实例，不是另一个“协议对象”。weak 不延长该实例的生命周期；调用 getter 获得 View 后，若插件将返回值存入 strong 属性，仍会形成插件对 View 的强持有。[A1] 协议示意假定项目中存在对应 UIKit 类型。

是否适合 weak 取决于所有权设计：谁创建、谁负责销毁、谁仅借用。不能把“全部 weak 化”当作通用修复。

### 2.3 需要补回真实案例的证据

- 明确未释放对象：VC、Manager、插件、View，还是多个对象。
- 给出实际强持有者路径，区分外部长期持有与循环引用；不要凭方法能访问某对象就画 strong 箭头。
- 保留可复现操作与退出后观察时点；证明断开哪条边后哪些对象释放。
- 将“当时实际验证”“从当前笔记推测”“现在建议新增”分开。

目前候选人提供的旧 `VC → Manager → View` 仍不足以证明原泄漏闭环。本讲义不补造那个回指对象。

## 3. Actor：数据隔离不等于异步业务事务

### 3.1 本次回答的纠正

Actor 的作用恰恰包括保护其隔离的可变属性访问，不能说它“保护 State 但不保护里面属性”。遵守隔离规则时，不同任务不会同时执行同一 actor 的隔离代码；但异步方法在实际挂起时可以让其他任务进入，因此方法整体不自动成为不可分割事务。[A2]

`await` 是潜在悬挂点，不是保证每次都悬挂；普通 actor 也不应被理解为一条固定线程。跨悬挂点依赖的状态必须重新验证。[A2]

### 3.2 题目的失败时序

```text
enter(A)：写 currentRoomID=A，发起请求，挂起
leave()：清空当前房间与成员
enter(B)：写 currentRoomID=B，发起请求，挂起
B 请求返回：members 写入 B 的结果
A 请求迟到：旧任务恢复，将 members 覆盖成 A 的结果
```

这是业务状态的时序错误，不要求两个任务同时写同一内存地址才能发生。执行顺序仅是用于说明缺陷的一种可行时序，不宣称真实线上必然以这个顺序运行。[A2]

### 3.3 取消和身份校验

`Task.cancel()` 发出协作式取消信号，并不保证业务代码再也不会继续执行；底层异步实现及调用方应响应取消。[A3] 因此可以用取消节省不再需要的工作，但仍需要状态有效性检查。

只比房间 ID 的不足，是“退出 A 再进入 A”：两次请求属于同房间，却不属于同一轮会话。这是本题的设计推论，不是已确认的项目事故。

可用每轮进房 token 区分会话。下面仅演示成功响应的防陈旧回写，不是完整网络请求框架：

```swift
import Foundation

actor RoomState {
    typealias Fetch = @Sendable (String) async throws -> [String]
    private let fetch: Fetch
    private var sessionToken: UUID?
    private var currentRoomID: String?
    private var members: [String] = []

    init(fetch: @escaping Fetch) { self.fetch = fetch }

    func enter(_ id: String) async throws {
        let token = UUID()
        sessionToken = token
        currentRoomID = id
        members = []

        let result = try await fetch(id)
        guard sessionToken == token,
              currentRoomID == id,
              !Task.isCancelled else { return }
        // 校验和写回之间不新增潜在悬挂点。
        members = result
    }

    func leave() {
        sessionToken = nil
        currentRoomID = nil
        members = []
    }
}
```

本次验证：上述示例使用本机 Apple Swift 6.2.4、`-swift-version 6` 完成类型检查；未运行异步交错测试，不以编译通过宣称覆盖所有时序。

范围限制：未展示任务 handle 的保存及取消、网络取消桥接、错误状态写回、重试、UI 发布与资源 teardown。错误响应和 UI 事件也要沿用同一会话有效性约束，不能只保护成功成员列表。

建议验证的场景：A→B、A→退出→A、取消后迟到成功、迟到失败、退出无新进房。测试要控制响应顺序，不靠偶然网络延迟。

## 5. 后续专项顺序与验收

1. 真实战役与主回答：先补案例卡，形成 90 秒和 3 分钟表达。
2. 异常类型与终止边界：区别异常表现、进程终止和客户端观测能力。
3. 采集与符号化：核对现场安全、异常链、UUID／地址坐标及 SDK 共存。
4. 根因定位：Crash、泄漏、内存峰值、异步时序和卡顿分别建立证据链。
5. 治理取舍：修根因、临时降级、监控预算、上线与回滚。
6. 结果证明：分母、分桶、观察窗口、覆盖变化、误判与因果限制。
7. 变式追问：不能靠原文背诵；改变时序、设备或采集前提后仍能推理。

一轮回答只证明该轮覆盖的能力，尚未掌握的部分继续教学，不用“完全掌握”“必过某公司”替代验收。
