## 2. 文本回忆：分开输入阶段、字符边界、索引单位和附件

用户回忆：“键盘编辑中的 emoji，换行后变成图片、长度改变，跳过某些‘可变编辑器’可解决。”以下只核验概念，不能由概念相似反推根因。

| 议题 | Apple 已确认的边界 | 对回忆能说到哪里 |
|---|---|---|
| `markedTextRange` | `UITextRange?`；无 marked text 时为 nil；marked text 是多阶段输入中尚待用户确认的临时文本。[S1] | 这是输入阶段，不是 emoji、附件或组合字符检测器的定义。 |
| UTF-16 `NSRange` | `NSString` 的长度、字符索引和范围按 UTF-16 单元表达；`length` 不能直接代表视觉上的长度。[S2][S3] | 视觉上的“一个表情”与 NSString 长度不能混用；此契约限于相应字符串 API，不能说所有 `NSRange` 都天然表示 UTF-16。 |
| composed-character sequences | 可把范围扩展至完整组合字符序列；输入范围必须先在接收字符串边界内。[S4] Apple 字符串指南建议按 grapheme cluster 边界确定用户感知字符边界。[S3] | 保护组合序列边界与处理尚未确认的输入是两个不同问题；扩展范围不是修复已有越界范围。 |
| `NSTextAttachment` | 富文本的 attachment 属性使用附件对象；`init(attachment:)` 以附件基字符构造富文本。[S5][S6] | 是否真的发生替换，要看实际字符串和 attachment 属性，不能仅由显示“像图片”判断。 |
| U+FFFC 的证据状态 | 已读 `NSTextAttachment.character` 页只说明它表示附件，未给数值；初始化页指向该常量。[S6][S7] | **本次尚未从已读 Apple 正文确认 U+FFFC 数值对应关系**；不把本地笔记的写法冒充一手核验。 |

**已确认的修正边界**：已读 Apple 文档没有提供“输入换行会自动把 emoji 转为图片附件”的保证，也没有把“跳过可变编辑器”定义为修复措施。不能将这两句话升级为已证明的系统行为或项目修复。

**条件推导，不是现场结论**：若应用代码把长度为 k 的文本范围替换为一个附件基字符，UTF-16 长度可能因此改变；只有看到实际替换操作才能讨论旧 range 是否失效。单凭换行前后看起来不同，不能证明该链路。

## 3. 列表回忆：批量更新不是绕过数据源一致性

用户回忆：“消息爆发时，用 UITableView ‘performPatch’ 删除历史数据。”

### 已确认的 API 与索引契约

- Apple 实际 API 是 `performBatchUpdates(_:completion:)`：把插入、删除、reload、move 合成一组动画，并要求数据源反映对应变化。[S8]
- **名称仍未知**：用户的 `performPatch` 可能是此 API 的口述，也可能是项目封装；没有调用代码，不能宣称已识别。
- 批次按**先删除、后插入**处理；删除使用更新前的表格索引。Apple 指南进一步明确：删除／reload 对应原表，插入对应结果表。[S8][S11]
- 调用 `insertRows` 与 `deleteRows` 的代码先后，不改变上述 UIKit 处理顺序；这与可变数组逐步变更后的索引语义不同。[S9][S10][S11]
- `insertRows` 会随即调用相关 delegate／data source 取得可见内容；批次数据源不能等到动画 completion 才反映新增结果。[S8][S10]
- completion 的 `finished` 表示动画是否完成，不是数据一致性验证结果。[S8]

### 数量不变量：由契约推导，非历史事故确诊

固定一个 section、无跨 section move、无 section 增删时：

`N_after = N_before - D + I`

纯删除时 `I = 0`。这是“批次操作与更新后数据源一致”的数量推导。[S8][S11] 满足数量只是一部分检查，**不代表消息 ID 和 index path 一定对应正确**。涉及 section 或跨 section move 时不能直接套用这个简化式。

### 建议核对的提交顺序，不是唯一生产实现

1. 冻结本批旧快照与目标新快照；删除路径从旧快照计算，插入路径从目标结果计算，不把旧路径套到已删后的数组。
2. 在同一更新提交中同步更新数据源与声明的行变更；Apple 示例先准备数据集合，再提交更新，`performBatchUpdates` 文档也要求更新数据源。[S8][S11]
3. 不把“completion 才清历史 model”与当下的 `deleteRows` 混用；它会让表格变更与数据源返回值不处于同一状态。此处是契约风险推导，不是已观察到的项目 Bug。
4. 突发新消息应怎样排队、合并或取消，是项目设计问题；Debounce／串行化可以控制提交节奏，但**不能替代数量与索引一致性**。本次未审计并发实现。

**项目层未知**：历史数据清理阈值、删除 ID／旧路径、是否同时 append、实际 rows 数、section 变化、是否混用 reloadData／其他批次、是否已有 animation 正在运行。缺少这些，不能认定当年的根因就是“先后顺序错误”。
