## 第一部分：治理项目 STAR——回答“你做过最难的项目是什么？”

### S｜背景：问题为什么越来越难处理

我做过一项比较有挑战的工作，是从 2023 年开始牵头 Gravity 的稳定性治理。当时业务和 DAU 增长很快，Feed、个人主页和语音房的使用量与状态复杂度都在增加，崩溃、卡顿和内存问题开始影响用户体验。

项目已经接入 Firebase，但有报表不等于能直接还原用户操作。有些问题有明确的业务调用，有些只看到系统栈；还有一些单次操作都没问题，多个异步结果和用户操作交错时才出错。业务又在持续迭代，不能为了治理把整个模块停下来重写。

### T｜任务：我负责什么

我负责牵头治理，也亲自处理其中的线上问题。目标是先降低高影响 Issue，再把反复出现的状态和生命周期风险收敛到公共更新逻辑，而不是每出现一个 Crash 就在某个调用点补一个判断。

### A｜行动：从排序进入一个具体战役

我先按用户影响、业务场景、线索充分度和修复成本排优先级，重点看 Feed、语音房和个人主页。能确认调用方原因的优先修根因；线索不足的继续补上下文，不会看到 UIKit 栈就直接归因成系统 Bug。

持续治理中，一个比较有代表性的案例是 2026 年的 Feed Header 偶现崩溃。同一个 Feed 页面，Header 会根据语音房或活动请求调整内容和高度；列表本身又有下拉刷新、投稿成功插入，以及切账号后的清理。它们由不同事件驱动，却都在改变同一个页面。

我没有把它当成单个 insertRows 越界，而是把问题拆成两层：旧请求的结果是否还有效，以及当前数据源与表格是否允许执行这次增量更新。

在请求层，我给两类 Header 请求分别加递增 token，每次新请求记录自己的 token，返回时只有仍是当前轮次才允许更新。切账号清理语音房 Header 时，也先让旧请求失效，避免旧数据在清理后又写回来。

在 UI 层，回调更新前检查页面是否加载、是否还在 window，以及是否正在下拉刷新；Header 高度调整不再借用列表的 beginUpdates/endUpdates，而是收敛到统一入口。投稿插入也不再直接改模型后无条件 insertRows，而是核对当前行数与模型的关系，状态符合时增量插入，否则使用当前数据源 reload。

### R｜结果：具体修复和治理价值

这次改动同时收敛了旧请求回写、页面更新准入和增量更新前提，保留了原有业务功能，没有为了不崩溃就简单丢弃新投稿或关闭 Header。

整体上，持续治理后常规崩溃大盘有明显改善；这个结果是多个修复共同带来的，不能归功于这一项。这个案例给我的核心经验是：复杂线上问题不一定是某次访问不安全，也可能是多个入口对“当前状态”和“更新完成”的理解不一致。治理要明确结果何时失效、何时允许提交，以及增量更新失败时如何收敛到可靠状态。

### 如果只能讲 60～90 秒

> 我从 2023 年开始牵头 Gravity 的稳定性治理。业务增长后，Feed 和语音房的状态越来越复杂，已有 Crash 报表，但不能只靠逐个补判断。
>
> 我亲自处理过一个 Feed Header 的偶现崩溃。Header 网络回调、下拉刷新、切账号和投稿插入都可能更新同一个页面。我把它拆成两类问题：异步结果已经过期还在回写，以及模型与表格状态不满足增量更新的前提。
>
> 修复中，我用请求 token 让旧结果失效，切账号时同步失效旧请求；更新前检查页面和刷新状态，Header 高度更新不再借用列表批更新，投稿插入则根据当前模型与行数决定增量插入还是 reload。
>
> 这个案例让我把治理重点从“这行会不会越界”，提升到“这个结果现在还能不能用、这次更新是否符合当前状态”。整体大盘改善是持续治理的结果，单项收益我不会没有报表就编一个比例。

## 第二部分：Feed STAR——回答“具体讲一个你亲自解决的问题”

### S｜背景：几个合理操作，组合后出现偶现问题

我举一个 2026 年处理的 Feed Header 偶现崩溃。Feed 顶部会根据请求结果展示关注用户的语音房或活动，同时页面本身支持下拉刷新；投稿成功后，还会把新 Feed 插到推荐列表顶部。退出或切换账号时，又需要立即清掉上一个账号的语音房 Header。

这些操作分散在网络回调、通知和刷新逻辑中。单看每一段代码都不复杂，但它们依赖的页面状态并不一定还是发起操作时的状态。

### T｜任务：同时处理数据有效性和 UI 更新前提

我负责这个修复。需要保持 Header 和投稿插入功能，同时避免旧请求回写，以及当前列表状态不匹配时仍强行执行插行。改动范围要集中，不能把整个 Feed 的刷新和数据源架构一起重写。

### A｜行动：我怎么拆解和修复

我顺着几个更新入口核对旧代码。Header 请求回来后只检查是否正在下拉刷新，然后用 beginUpdates/endUpdates 调整高度；切账号时虽然清了 Header 内容，但没有让已经在途的旧请求失效。投稿成功的通知则先往模型插入一条，再直接 insertRows，没有核对表格当前是否仍对应那个旧模型。

我先把“请求完成”和“请求结果还能用于当前页面”区分开。语音房 Header 与活动 Header 分别维护递增 token，发起时捕获当前轮次，返回时进行比对。同一类请求发起了新一轮，旧一轮即使成功返回，也不再写回。切账号清理语音房 Header 时先递增 token，再清内容，因此旧请求不能把清掉的旧账号数据重新填回来。

然后，我把 UI 的更新准入收敛起来：页面已加载、仍在 window、且不在下拉刷新时，才应用 Header 网络结果。高度调整通过一个统一方法设置并重新赋值 tableHeaderView，不再因为 Header 高度变化去开启一次列表行更新。

最后，我把投稿顶部插入也收敛到一个入口。模型新增后，核对表格的当前行数是否等于新模型数量减一，并检查不在加载状态。满足前提才 insertRows，否则 reload 当前数据源。这里不是为了省事全量刷新，而是只在无法可靠做增量更新的状态下退回整体重建。

### R｜结果：哪里已经收敛，哪里不夸大

这个补丁把请求轮次、页面准入、Header 高度调整和投稿插入的处理串起来了：旧结果不会仅仅因为对象还活着就被使用，增量插入也不再无条件假设表格与模型一致。

它不是把所有操作加锁，也不是捕获异常后继续运行。对我来说，真正解决的是多个入口的状态有效性和更新契约。提交能证明这些改动，但目前没有独立的上线后报表，所以我不会承诺这个 Issue 已经清零，也不会说全 Feed 所有更新入口都由这次补丁保证安全。

**这个案例的难点可以用一句话概括：**

> 多个入口都认为自己只是做一次小更新，但它们依赖的旧状态可能已经过期；我需要同时决定哪些结果应该失效，以及哪些更新还能按增量方式提交。

## 第三部分：主案例技术展开——体现深度的不是 token 名字，而是状态推理

### 3.1 先画更新链路，避免只盯着崩溃的一行

按对应历史代码，可以还原这些入口：

```text
语音房 Header 请求 ──┐
活动 Header 请求 ────┤──→ Header 内容与高度
退出／切账号清理 ────┘
                              ↓ 同一个 Feed 页面
下拉刷新／列表加载 ──────→ feedList 与表格状态
投稿成功通知 ───────────→ feedList 顶部插入 + insertRows
```

语音房与活动 Header 是不同业务类型，不必解释成在所有页面上同时存在。它们使用同一种处理思路，但分别维护请求轮次。

**不能直接从这张图断言当年的某次崩溃一定发生了哪种嵌套。** 已确认的是旧入口的更新方式和补丁针对的风险；原始崩溃线程、异常全文和实际事件顺序尚未取得。

### 3.2 第一个问题：对象还活着，为什么结果不能再用了？

`[weak self]` 只解决对象的持有和存在性，不解决业务结果是否过期。页面对象可以一直存在，但账号、请求轮次或显示资格已经变了。

下面是由旧代码允许的**教学时序**，不是伪造事故现场：

```text
T1：账号 A 的语音房 Header 请求发出
T2：切账号／退出，清空 A 的 Header
T3：T1 的旧请求成功返回
T4：控制器仍存在，刷新也已结束
    旧回调按原条件通过，重新展示 A 的数据
```

这条时序即使所有事件都在主线程依次处理，也可能出错。它是异步业务状态过期，不要求两个线程同时写同一块内存。

**口述：**

> weak self 只回答“对象还在不在”，token 回答“这个结果还是不是当前那一轮”。这两个检查解决不同问题，不能相互替代。

### 3.3 实际 token 方案：清理动作也必须让旧结果失效

历史补丁核心逻辑：

```swift
// 发起一轮语音房 Header 请求
feedHeaderUserRoomRefreshToken += 1
let token = feedHeaderUserRoomRefreshToken

TPAudioLiveViewModel.getFollowUserRoomList { [weak self] list in
    guard let self,
          token == self.feedHeaderUserRoomRefreshToken,
          self.canUpdateTableHeaderView() else { return }
    // 按当前结果更新 Header
}
```

切账号／退出的清理路径则先做：

```swift
feedHeaderUserRoomRefreshToken += 1
applyTableHeaderViewHeight(0.0001) { header in
    header.clearVoiceRooms()
}
```

它同时处理两类问题：

| 情况 | 没有轮次校验 | token 的作用 |
|---|---|---|
| 同类请求 A、B，B 后发先回 | A 迟到后可能覆盖 B | 新一轮发出后，旧一轮失效 |
| 已清空旧账号 Header，但旧请求仍在途 | 旧数据可能重新出现 | 清理动作也递增轮次，使在途旧结果失效 |

**关键不是把请求取消了，而是取消不了、已经完成或仍回调时，旧结果也没有应用资格。** 这次补丁没有实现完整取消链路，不能把 token 说成节省网络资源的机制。

### 3.4 为什么不能只比较账号 ID？为什么两类请求要分开？

> 只比较账号 ID，不能区分同一账号下连续发起的两轮请求。例如用户仍是 A，但新刷新已经完成，旧刷新才回来，账号一致仍然可能覆盖新结果。请求轮次保护的是当前刷新的一致性，不只是账号身份。
>
> 两类 Header 请求分别维护 token，是为了各自按自己的最新轮次处理，避免一个不相关请求把另一条链路的结果错误失效。这次实现是每类请求各自 latest-wins，不是一个全局 token 包打天下。

**注意方案语义：** latest-wins 指“最新发起的这一轮有资格应用”，不是“最后返回的那个结果获胜”。如果最新一轮失败，是否保留已有内容属于错误／空结果策略，token 本身不会决定。

### 3.5 第二个问题：结果没过期，为什么也可能不能立刻更新？

历史新增的 UI 准入是：

```swift
private func canUpdateTableHeaderView() -> Bool {
    guard isViewLoaded,
          view.window != nil,
          let mjHeader = tableView.mj_header,
          !mjHeader.isRefreshing else {
        return false
    }
    return true
}
```

三个检查分别服务于不同约束：

- `isViewLoaded`：页面 UI 已创建；不要为了应用一个回调去隐式加载页面。
- `view.window != nil`：页面仍连接到 window；这是本补丁的生命周期准入，不是完整可见性或业务会话证明。
- `!isRefreshing`：不在下拉刷新阶段应用 Header 网络结果，减少两条更新链路在不合适的时机交错。

**这里不能夸大为“状态机已经统一所有更新”。** `isLoading` 与刷新控件状态也不是同一个检查；Header 和投稿入口分别检查各自条件。

如果问“不允许更新时怎么办”，准确回答：

> 历史补丁在这里直接返回，没有保存待应用结果或自动重试。它用一部分刷新机会换取受控更新。如果要保证页面恢复后一定展示最新状态，需要另外设计重新请求或待刷新标记，不能把那部分说成已经实现。

### 3.6 第三个问题：为什么修改 Header 高度要换一种方式？

旧 Header 高度处理：

```swift
tableView.beginUpdates()
header?.tp_height = height
tableView.endUpdates()
```

历史补丁收敛为：

```swift
private func applyTableHeaderViewHeight(
    _ height: CGFloat,
    contentUpdate: ((TPFeedListHeaderView) -> Void)? = nil
) {
    guard let header = tableView.tableHeaderView as? TPFeedListHeaderView else {
        return
    }
    contentUpdate?(header)
    guard abs(header.tp_height - height) > 0.01 else { return }
    header.tp_height = height
    tableView.tableHeaderView = header
}
```

**你要讲的不是“beginUpdates 本身有 Bug”，而是职责收敛：**

> Header 内容和高度变化不是新增或删除列表行，没有必要因为这个变化再开启一轮列表更新。这个补丁把 Header 更新收敛到自己的入口，减少与列表加载和插行链路相互影响的机会。
>
> 清内容回调放在高度差判断之前，所以即使高度已经接近最小值，也会先完成账号 Header 的内容清理；不能只让高度变化成功，而旧内容仍留着。

这也是一个能被继续追问的细节：`0.01` 的高度差判断只是抑制重复高度赋值，不负责去重所有内容更新。

### 3.7 投稿插入：为什么模型先加一，再比较行数？

旧通知处理收到投稿后，插入模型并直接 `insertRows`。历史修复将这段收敛为：

```swift
feedList.insert(model, at: 0)

let currentRows = tableView.numberOfRows(inSection: 0)
let canInsertRow = !isLoading && currentRows == feedList.count - 1
if canInsertRow {
    tableView.insertRows(at: [IndexPath(row: 0, section: 0)], with: .fade)
} else {
    tableView.reloadData()
}
```

单 section、这次只插入一行时，必要关系是：

```text
旧表格行数 + 1 = 新数据源数量
```

这里 `feedList` 已经新增了一条，因此比较的是 `currentRows == feedList.count - 1`，不是与新增后的数量直接相等。

两组教学数字：

| 状态 | 表格旧行数 | 模型新增后数量 | 处理 |
|---|---:|---:|---|
| 状态匹配且未加载 | 100 | 101 | 可以按这次单行变化增量插入 |
| 状态不匹配 | 99 | 101 | 无法靠“插一行”描述目标，reload 当前模型 |

**计数匹配是必要条件，不是全局正确性证明。** 相同行数也可能对应不同 ID、不同顺序；这次补丁没有统一全部数据源版本，也没有证明所有其他入口都不能改变模型。

### 3.8 为什么 fallback 是 reload，而不是吞掉这次更新？

> 新投稿已经进入模型了。状态不符合增量前提时，只跳过 insertRows 会让界面与模型继续不一致；在这个入口，reload 用当前模型重新构建表格，是比盲目声明一条插入更保守的选择。
>
> 但这不代表 reload 可以在任何 UIKit 状态下随便调用，也不代表刷新请求之后一定不会覆盖本地新投稿。完整的数据合并、去重和更新调度属于其他约束，要继续审查。

**这一层体现的是失败策略：**增量更新是优化路径，状态不可信时不能为了保留动画而继续假设；但退回路径也要有自己的使用边界。

### 3.9 方案对比：为什么不是加锁、延时或取消就够了？

| 方案 | 能解决什么 | 单独采用的不足 |
|---|---|---|
| 所有更新放主线程／MainActor | UIKit 线程使用和隔离 | 旧请求仍可以在新状态后恢复，不能自动判断结果是否过期 |
| 给数据源加锁 | 保护共享内存访问 | 不回答结果属于哪轮请求，也不保证 UI 声明与模型版本一致 |
| 只取消旧请求 | 可能节省无效工作 | 已完成或不响应取消的回调仍可能到来；需要结果有效性检查 |
| 固定延时再更新 | 可能避开一部分碰撞窗口 | 状态是否有效不能靠时间猜测，没有明确安全条件 |
| 所有变化都 reload | 降低局部插删维护成本 | 仍须处理旧结果、页面状态和数据身份，也有重建与体验成本 |
| 本次分层处理 | 请求失效＋页面准入＋Header 独立更新＋受控增量 | 局部修复，不是统一覆盖所有入口的完整状态机 |

**口述答案：**

> 我先明确是哪个层次的问题。内存访问隔离、异步结果有效性和 UI 更新契约是不同的事，不能用“全部放主线程”或者“加一把锁”同时解决。这个补丁采用分层处理，尽量保持现有架构并收敛改动范围。

### 3.10 如果面试官追问“是不是彻底解决了？还有哪些漏洞？”

这恰恰是能体现深度的追问。不要把局部补丁说成万能框架。

> 这次修复针对明确入口，不是全部 Feed 更新统一事务化。仍有几个需要继续治理的边界：
>
> 第一，token 的递增、比对和 UI 应用需要在同一个受约束的执行环境中完成；普通整数不是锁，若其他入口在后台直接修改，仍可能出错。这次不能只凭一个 guard 宣称所有调用线程都已经审计。
>
> 第二，页面暂时不能更新时，历史实现会丢弃这次结果，没有自动补刷新。重新可见或刷新结束后是否重新获取，需要其他生命周期逻辑保证。
>
> 第三，展示资格变化、其他账号事件和所有数据源入口是否都会失效旧结果，需要系统检查，不能因为两个 token 就认为完整会话管理已经做好。
>
> 第四，插行只核对数量，还没有统一检查模型 ID 和版本。下一步可以让列表变化基于明确的旧快照与目标快照，再集中提交。

这些是**当前对补丁边界的分析和后续建议**，不把“我后来想到的完善”倒写成当年已完成。

### 3.11 怎么验证：围绕状态转换，不只跑随机操作

目前未取得该补丁的历史回放记录，下面是现在会采用的验证设计：

| 场景 | 应验证的结果 |
|---|---|
| 请求 A→请求 B，B 先返回 | A 后返回不能覆盖 B |
| 请求发出→退出／切账号清理→旧请求返回 | 旧账号内容不能被重新填回 |
| 同一账号重复刷新 | 只让当前轮次应用，不只检查账号是否相同 |
| 语音房请求与活动请求各自更新 | token 独立，不错误失效另一类请求 |
| 当前轮次返回时正在刷新／页面不在 window | 不直接应用；另查恢复后重新请求策略 |
| 高度不变但内容需要清理 | 内容清理不能被高度差判断跳过 |
| 模型新增后数量匹配、未加载 | 单行插入对应新模型，ID 和位置正确 |
| 行数不匹配或正在加载 | 进入 fallback；确认表格与当前模型重新一致 |
| 相同行数但模型 ID 已变化 | 暴露计数检查的局限，不能当成正确通过 |
| 刷新返回与本地投稿交错 | 检查投稿是否被覆盖、重复，以及滚动位置是否正确 |

网络请求用可控制返回顺序的替身，列表更新在真实控件中检查。不用偶然的网络延时作为唯一复现手段，也不把一个纯 token 模型跑通当成 UIKit 回归完成。

## 第四部分：消息列表 STAR——回答“有没有复杂 UI 状态一致性的案例？”

### 4.1 可直接讲的 STAR

#### S｜背景

语音房公屏是我持续治理的一个场景。新消息定时追加，展示窗口又要裁剪旧消息，同时还涉及滚底和用户手动上滑。这里模型数组正确，并不代表 UITableView 的批更新就正确。

我在 2023 年调整过同一批消息的行号快照和刷新策略。下面这个边界修复是后续在 2026 年做的，不是 2023 年一次性完成的全部工作。

#### T｜任务

我需要让历史裁剪、实际追加的数据，以及表格声明的删除和插入行数完全一致，特别是新消息数量恰好达到展示上限这种容易遗漏的边界。

#### A｜行动

旧逻辑中，当新消息数量“大于”上限时才清空旧数据；后面的另一个删除分支又要求删除数量“小于”当前旧数据数量。新消息数量刚好等于上限时，这两个严格不等式都可能挡住删除。

更关键的是，UI 的插入行数按上限裁剪了，但模型仍把新消息全部追加。以旧数据 10 条、上限 100、来 100 条新消息为例，旧逻辑没有删除这 10 条，UI 只声明插入 90 行，模型却追加了 100 条，最后表格按操作应该是 100 行，数据源却是 110 条。

我引入 V2，把“大于上限”补成“大于等于上限”，统一清旧数据、保留新窗口的处理。其余分支允许删除全部旧数据；插入时直接根据实际追加的消息数量生成行号，不再让模型和 UI 各自计算一套数量。V2 与旧路径通过开关选择，保留了控制修改范围的能力。

#### R｜结果

这次补丁修正了这个边界下模型和 UI 操作不一致的问题，也让我把列表治理的重点从“某个 index 是否越界”转到“这一批更新是否描述同一个状态变化”。

代码里有新旧路径和默认关闭的开关，所以能确认的是我提交了修复及控制路径，不能仅凭 Git 就说当时已经全量上线、该 Issue 已彻底清零。

### 4.2 把例子算清楚：不是只会说“行数不一致”

教学数字：旧数据 `O=10`，展示上限 `L=100`，新消息 `M=100`。

| 步骤 | 旧逻辑 | 修改后的逻辑 |
|---|---|---|
| 是否走清旧窗口分支 | `100 > 100` 为 false | `100 >= 100` 为 true |
| 是否走另一删除分支 | 需删除 10，但 `10 < 10` 为 false | 删除旧 10 条 |
| 模型实际追加 | 100 条 | 100 条 |
| UI 声明插入 | `min(10+100,100)-10=90` 行 | 100 行 |
| 最终数据源 | 110 条 | 100 条 |
| 按 UI 操作计算的最终行数 | `10-0+90=100` 行 | `10-10+100=100` 行 |

单 section、只讨论插删的情况下，必要数量约束是：

```text
更新后行数 = 更新前行数 - 删除行数 + 插入行数
```

这个约束**必要但不充分**。数量相等时仍可能删除了错误的消息，或把新消息放到了错误位置，因此还要检查 ID、顺序和 index path 所属的状态。

### 4.3 如果追问“你怎么从设计上避免同类问题”

> 我会先用旧状态和这一批新消息确定目标展示窗口，再让模型变化与 UI 插删都依据同一个计划。删除索引对应旧状态，插入索引对应更新后的状态。数据源需要在这次批更新过程中反映对应变化，不能等动画 completion 才改模型。
>
> 主线程执行解决的是 UIKit 的线程要求；一份更新计划解决的是状态一致性。这是两个条件，不能相互替代。

为了理解计划，可以把当前补丁抽象成下面的模型。**这是本次整理得到的分析模型，不声称项目已实现独立的 UpdatePlan 类型。**

假设上限 `L>0`，旧窗口已有 `O<=L` 条，新批次有 `M` 条：

```text
实际保留的新消息 K = min(M, L)
删除旧消息 D       = max(0, O + K - L)
实际插入 I         = K
目标行数 F         = O - D + K

目标内容 = 旧窗口去掉头部 D 条 + 新消息保留最后 K 条
删除路径 = 旧状态中的 0..<D
插入路径 = 结果状态中的 (O-D)..<F
```

这套推导把“超过上限”和“等于上限”放在同一组约束里，避免模型裁剪与 UI 裁剪分别写条件。实际代码还要处理消息身份、多 section、异步来源和生命周期等约束。

### 4.4 常见追问

**Q：为什么不用 reloadData，一步解决？**

> reload 可以避免维护复杂的增量插删，在低频或无法可靠生成增量计划时是合理备选。但高频公屏刷新还涉及重建、布局和滚动体验，不能不看成本就全部改成 reload。我在历史上也调整过 reload 与追加策略，不会把某一次策略说成所有场景的最优解。

**Q：performBatchUpdates 不是已经保证一致性了吗？**

> 它管理这批 UI 更新，不会替我修正数据源和 index path。如果模型最终是 110 条，UI 操作只描述到 100 行，把这些代码放进同一个闭包也不会变正确。

**Q：展示上限是不是意味着丢消息？**

> 这里控制的是公屏的展示窗口。这个补丁不能证明服务端接收、业务分发或历史存储的完整性，也不能反过来说裁剪 UI 就丢了上游消息。要分别看消息链路和展示链路。

**Q：怎么验证？**

> 我会重点验证空批次、当前窗口已满、新批次小于／等于／大于上限、一次删除全部旧数据，以及连续多个批次。除了最终行数，还要断言保留的消息 ID 和顺序正确，再做 UIKit 场景回放看上滑、滚底和退出后的行为。

上述是当前建议的回归设计，不是已有历史 UIKit 压测结果。

## 第五部分：输入框 STAR——回答“有没有富文本或输入边界的案例？”

### 5.1 可直接讲的 STAR

#### S｜背景

另一个是我在 2026 年处理的 IM 输入框表情插入问题。这个路径涉及富文本替换、当前选区和插入后的光标，容易把用户看到的字符数与 API 使用的范围单位混在一起。

#### T｜任务

我要先把调用方的范围和光标计算修正，让替换区间属于当前文本，并让插入后的光标落到实际插入内容之后，而不是先把问题归因成系统键盘 Bug。

#### A｜行动

我回到对应代码检查了两条路径。一个路径直接拿 `selectedRange` 去替换可变富文本，没有先根据当前文本收敛范围；另一个路径用自定义 `length() + 1` 把光标放到文末。

这里我没有只凭方法名判断单位，而是看了 `length()` 的实际实现，它返回的是 Swift 的 `String.count`。相关 Foundation 字符串和富文本范围使用 UTF-16 单元，两种计数不能混用，额外加一也没有可靠依据。

修复中，我依据当前 `attributedText.length` 处理 `NSNotFound`、起点越界和选区超长，再执行替换。插入后的光标用合法替换起点加上实际插入富文本的长度；置于文末的路径直接使用富文本长度。对还处于 marked text 的输入，历史补丁先调用 `unmarkText()` 再继续编辑。

#### R｜结果

这次改动修正了调用方的范围计算和光标计算，使它们与当前富文本采用同一套坐标。但提交本身是尝试性修复，不能据此承诺所有偶现输入问题都消失。

这个案例对我的启发是，输入问题要同时看当前文本、范围单位和编辑阶段，不能用“一个表情算一个字符”这种视觉直觉代替 API 契约。

### 5.2 两个具体例子：为什么 length()+1 不可靠

| 文本 | Swift `String.count` | Foundation 字符串 UTF-16 长度 | 旧 `count+1` 的问题 |
|---|---:|---:|---|
| `A` | 1 | 1 | 得到 2，已经超过文末 |
| `😀😀` | 2 | 4 | 得到 3，不是文末，还落在第二个 Emoji 的 UTF-16 序列内部 |

某些文本中两种算法可能碰巧得到一样的数，不代表计算契约正确。

**准确说法**：这里的字符串／富文本 API 使用 UTF-16 范围；不是所有 `NSRange` 在任何用途下都代表 UTF-16。

### 5.3 实际修复关心哪些约束

设当前富文本长度为 `L`，替换起点为 `P`，替换长度为 `N`：

```text
0 <= P <= L
0 <= N <= L - P
```

历史补丁将 `NSNotFound` 收敛为文末空选区，裁剪起点后再按 `L-P` 限制选区长度。这样检查针对当前文本，也避免直接依赖可能越界的区间终点。

实际光标变化：

```swift
// 替换后的光标：按实际插入富文本的长度计算
NSRange(location: replaceRange.location + mutiEmojiAttr.length, length: 0)

// 另一条置于文末的路径
NSRange(location: textAttribute.length, length: 0)
```

这里的代码主动构造了图片富文本／附件，不能把它说成“系统在换行后自动把 Emoji 变成图片”。系统 Emoji、应用创建的附件、输入法 marked text 是不同层次。

### 5.4 如果追问“范围合法就够了吗”

> 不够。范围在 0 到 length 内，解决的是基本数值边界，不自动保证没有截断组合字符，也不保证这个范围对应用户原本想编辑的内容。如果选区来自旧文本，即使裁剪后合法，也可能替换错位置。
>
> 我会进一步区分组合字符边界、选区是否属于当前文本，以及是否还在输入法的组合输入阶段。必要时按业务决定等待确认，或者明确结束组合输入。历史补丁使用了 unmarkText，但不能把强制确认输入当成所有编辑场景的通用最佳方案。

当前建议回归：空文本、普通文本、复合 Emoji、选中替换、应用附件、粘贴、组合输入、`NSNotFound` 和陈旧选区。它们需要实际控件测试，不能用几组字符串计算替代。

### Q3：你怎么排优先级，为什么先看 Top Issue？

> 我综合看用户影响、核心场景、线索充分度和处理成本。高频且调用方明确的问题通常可以较快降低风险；重要业务链路即使次数没排第一，也可能更优先。
>
> Top 10 是初期排序入口，不是固定只修十个。难以定位的 Issue 先缩小范围或补线索，不为了短期数字把所有异常吞掉。

不要补造 Top 10 的贡献比例；按次数和按去重用户统计的占比不同，各 Issue 用户也可能重叠。

### Q4：只有系统栈、EXC_BAD_ACCESS，没有业务异常原因，怎么定位？

> 我先确认报告和符号化，再结合异常类型、subtype、fault address、指令、最后业务帧和版本场景聚集情况提出假设。
>
> EXC_BAD_ACCESS 不直接证明野指针，低地址也不直接证明 use-after-free。怀疑 ObjC 已释放对象被发消息时用 Zombie，怀疑越界或释放后访问时用 ASan，怀疑数据竞争时在支持的模拟器用 TSan，工具要跟假设匹配。
>
> 像本稿的 Feed 问题，要进一步区分 UI 更新契约和异步业务状态，不能因为都带“时序”二字就当成同一种内存竞争。

这是方法，不新增一件记不清根因的内存事故来充当本人战役。

### Q5：你做过 Runtime 防护吗，为什么不直接全局兜底？

> 做过特定数组访问路径的防护，但它是规避和止血，不是通用根因修复。越界后返回 nil，可能让本次调用不立即崩溃，却没有恢复数据和业务语义。
>
> 本稿这种问题更不适合全局吞异常：旧账号结果已经写回，或者模型与表格不一致，即使进程没终止，状态仍是错的。应该修结果资格和更新契约，而不是隐藏失败。
>
> 如果今天设计防护，我会限定适用范围、明确降级语义、触发观测和退出条件，同时检查兼容和内存成本。

历史启动开关不等于可以进程内即时撤销 Hook；涉及系统内部实现的旧规避也不包装成推荐的新方案。

### Q6：治理有什么结果？能证明是你的改动带来的吗？

> 持续治理后，常规崩溃大盘明显改善。我能把个人贡献落到代码和保证变化，但大盘受多个修复、版本覆盖和业务变化影响，不归功于这一个 Feed 补丁。
>
> 单项收益需要看对应 Issue、发布版本和同口径窗口。目前可以明确说明我改了什么，没有原始报表时不承诺 Issue 清零，也不编单补丁贡献比例。

如果使用本人回忆的量级，可以说：

> 按我目前记得的线上指标，常规崩溃从早期千分之几，降到了万分之一量级，这是持续治理的整体结果。

它仍是回忆值，不是本次核验的后台统计；准确口径见第七部分。

### Q7：你怎么防回归？

> 我把历史问题转成状态转换约束。请求看旧轮次失效、账号清理和迟到回调；页面看能否更新与恢复后的刷新策略；列表看旧快照、新模型、ID 和插删是否描述同一变化。
>
> 线上再看对应 Issue、版本和重点场景趋势，检查修复是否带来过多 reload、内容不更新或滚动体验回退。不只验证“没崩”，也验证业务结果仍然正确。

当前测试设计与历史已执行测试分开，不为了让 R 更完整就补出自动化回归记录。

### Q8：Crash 好了，但用户仍反馈闪退或卡顿，怎么办？

> 先分开常规 fatal Crash、疑似内存退出、Watchdog 和卡顿，它们不是同一个指标，也不一定有同样现场。
>
> 内存要区分持续抬升的基线、瞬时峰值和长期缓存；分配函数栈只提供调查方向。卡顿要定位主线程耗时和高频场景，不是加一个 RunLoop Observer 就完成治理。
>
