## 2. 四个概念不要混为一谈

| 维度 | 例子 | 意义 |
|---|---|---|
| 系统异常类型 | EXC_BAD_ACCESS、EXC_CRASH | 描述终止／异常呈现 |
| BSD 信号 | SIGSEGV、SIGBUS、SIGABRT | 报告中的相关信号 |
| 内存异常 subtype | KERN_INVALID_ADDRESS、KERN_PROTECTION_FAILURE | 解释访问为何无效／被保护 |
| 语言异常 | NSRangeException 等 | API／语言层抛出的异常信息 |

`NSRangeException` 不是 `EXC_BAD_ACCESS` 的 subtype。Objective-C 数组越界抛出的语言异常应读 reason 和 Last Exception Backtrace；未捕获语言异常常见报告形式为 EXC_CRASH (SIGABRT)。SIGABRT 本身也不能反推出必定数组越界。[S1][S2]

Mach Exception 与 Mach-O 不同。Mach-O 是二进制格式；不能说“Mach-O Exception 捕获”。观察到 EXC_BAD_ACCESS 也不能据此证明项目 SDK 自行实现了 Mach 异常端口采集。[S1][S7]

推荐面试表达：

> 我先按报告呈现决定首查路径，不直接按异常名认定根因。语言异常结合 reason 和最后业务帧；内存访问异常结合 subtype、地址、指令、寄存器及线程时序，提出并验证假设。

“有／无业务帧”是线索完整度维度，不是完整根因分类。实际排查还应先核对符号化；系统帧位于栈顶不自动表示系统有 Bug。

## 3. 低地址不是 use-after-free 的充分证据

本次最重要的纠错：候选人把 0x10 这样的低地址高概率解释为野指针，这是证据跳跃。

以**教学合成例**说明，不冒充真实 Crash：

```text
fault address = 0x10
x0 = 0
faulting instruction = ldr x8, [x0, #0x10]
```

可根据指令与寄存器推导本次访问地址为 0 + 0x10，即空基址加字段偏移。它没有提供分配、释放历史，不能证明某个对象已经释放后仍被访问。空基址的上游原因仍待追查；并不排除上游存在更早的破坏。

区分两种问题：

- 空指针解引用／空基址偏移访问：指针值为零却被用于读写或跳转。
- use-after-free：所用地址指向曾经分配、如今已经结束生命周期的对象／内存。

地址只是线索。还需区分数据读写与取指异常、核对崩溃指令与寄存器、回溯值的来源，再用工具或控制时序验证生命周期假设。[S2][S4]

## 4. 工具须与假设匹配

| 假设／任务 | 工具 | 不能据此宣称 |
|---|---|---|
| ObjC 消息发送给已释放对象 | Zombie | 能覆盖所有 C 缓冲区或所有坏内存访问 |
| 越界、释放后访问等内存破坏 | ASan | 覆盖未执行的路径或证明没有所有内存错误 |
| 多线程无同步访问共享内存 | TSan | 覆盖所有业务时序错误；iOS 真机可运行 TSan |
| UI API 调用线程违规 | Main Thread Checker | 所有主线程业务逻辑都正确 |

Apple 说明 ASan 对分配边界与释放隔离区做检查；TSan 对读写访存插桩，并明确 iOS 等平台应在支持的 Simulator 而非真机运行。实际执行路径与插桩覆盖决定可检出的范围。[S3] Zombie 的证据应落在已释放对象收到消息和具体调用点，不是见到 objc_msgSend 就直接定性。[S4]

AI CR 规则可以作为检查清单，但不能代替动态证据。置空某个指针变量不会自动清除其他别名：

```c
T *p = allocate();
T *q = p;
free(p);
p = NULL;
use(q); // q 仍是原地址
```

这只是所有权示意，不是可编译运行的完整程序。“deinit 里访问 self”规则应额外核对其具体禁止条件。本轮没有审计 CR Skill 文件，也未取得 Deinitialization 全文，不判定实际规则错误；后续应区分正常清理、对象逃逸及异步持有等情形。[S8：待核验]

## 5. superview == nil 本身不是非法状态

UIKit 的 superview 是可选属性，无父视图时可以是 nil。因此须区分新视图尚未添加、从层级移除、传入 nil 子视图、以及约束依赖不存在的共同祖先等情形。不能仅凭“superview nil”宣称 addSubview 本身有 Bug。[S5]

该笔记记录的是约束安装失败和 NSGenericException，而不是已证明的 addSubview 崩溃。无法确认它就是候选人此次回忆的同一事故，不能合并事故身份。

### 同时发现的笔记因果缺口

原文称 SnapKit makeConstraints 闭包返回后存在“微小时间窗口”，即使同步主线程执行，用户点击也会自动插入并移除视图。检查上游 ConstraintMaker.swift 后可见：prepareConstraints 返回后在同一调用中遍历并激活约束，没有在这里主动 enqueue 或 await。[S6]

因此仅有“闭包结束”不足以证明让出了主线程。若确有插入，必须证明额外重入、嵌套事件循环、跨线程违规操作或自定义封装等机制；也可能是其他错误，不能补造。

原笔记 T6 已移除视图，却又写 T8 对同一视图 superview != nil 检查通过，缺少重新添加／换对象的证据。这条时序目前不闭合。

本次只核验上游 develop 分支的标准实现，未确认项目依赖版本及自定义 chain 封装，不据此宣称已定位或修复该真实事故。

## 6. 分配函数栈是方向，不是 OOM 证明

可以将 malloc、对象分配、图形上下文等栈聚为“内存风险待调查”，但不能统一当成已确认 OOM。需要看具体异常、分配输入与资源尺寸、内存走势、堆破坏线索和系统终止证据。[S2][S3]

保留表达：

> 我们将这一类 Issue 作为内存风险重点排查，逐个核实是资源峰值、输入尺寸、泄漏、分配失败还是更早的内存破坏，而不是看到分配 API 就认定 OOM。

这是建议的表达框架，不证明项目当时已逐项完成上述验证。

## 7. 把百分比变成可解释的治理目标

Firebase 区分 crash-free users 与 crash-free sessions；其 crash-free 指标以 fatal 事件为基础，不能把非致命 Hook 上报数直接混入同一百分比。[S9]

```text
崩溃影响用户比例 = 期间遇到崩溃的去重用户 / 期间活跃用户（按平台身份定义）
崩溃会话比例 = 以崩溃结束的会话 / 总会话
```

它们不是“Crash 次数 / DAU”的同义词。[S9] 自建指标也可以存在，但须说明名称、定义、分子分母、去重和窗口。没有确定指标前，不把回忆中的 0.26%、0.30%、0.01% 填进某一公式。

Top 10 贡献应确认按次数、影响用户并集还是其他单位计算；重叠用户不能把各 Issue 影响人数简单求和。

若同口径、分母可比，0.26%→0.10% 对应约 61.5% 相对下降；0.30%→0.10% 对应约 66.7%。这是算术条件，不是上线效果预测。短期目标须结合可修复 Issue 覆盖、风险和排期；长期目标还要考虑新 Issue 与不可确定退出。
