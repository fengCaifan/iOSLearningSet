>
> 语音房公屏是另一个持续演进的场景。新消息追加、旧消息裁剪和滚到底部都涉及模型与 UITableView 的状态。2023 年我处理了同一批插入行号使用同一计数快照，以及滚底和追加策略。后续仍继续补边界，2026 年又提交了批更新行数一致性的修复。这个过程让我更加明确：主线程执行和 performBatchUpdates 都不是万能保证，模型变化和 UI 声明必须来自同一份更新计划。
>
> 对难以定位的系统或基础层问题，我也做过 Runtime 防护和输入路径 workaround，但保持工程边界：有开关、有适用范围，防护不能替代根因。历史上防护本身也出现过新的内存风险，因此不能只看 Crash 是否暂时消失，还要看业务语义、内存和兼容成本。

> 在持续治理过程中，常规崩溃大盘逐步改善。我个人的贡献既包括牵头治理，也包括基础容器、消息面板和输入路径的具体提交。这个项目最难的不是某个 API 的使用，而是在信息不完整、业务不能停的情况下，区分证据与假设，选择副作用可控的修复，再把经验带回后续开发和 Review。”

> “如果落到一个具体问题，我会举 2023 年对 SafeArray 的修复。
>
> 当时这个基础容器采用并发队列管理访问，读通过 sync，写通常通过 barrier。但一个‘取出并删除前 N 条数据’的方法，先检查 count，再单独读取，最后又调用异步删除。几步分别受管理，却不是一个原子操作。另一个 removeFirst 还在锁外判断非空，并用普通 sync 执行修改。
>
> 所以风险不是没有写 guard，而是 guard 看到的状态和真正操作的状态可能不同；取回一批数据，也不代表这批数据已经删除。在多调用方交错时，可能出现越界或重复消费等风险。核心是这几步允许其他调用穿插，必须保证完整的取走动作，而不只是某一次访问。
>
> 我把这些复合动作统一放到同步 barrier 内，在里面读当前长度、裁剪范围并删除。同一个方法结束时，返回值与状态修改形成一致的语义。
>
> 这件事对我的启发是：线程安全不只是一组独立 getter、setter 安全，还要看业务依赖的组合动作是否原子。治理不能停在调用方不断加判断，必要时要修改基础模块的接口契约。”

## 4. 主案例 A：SafeArray——单次安全不等于组合原子

### 4.1 时间、本人贡献与源码

- **2023-06-05**；`45767743c7`；作者／提交者：`fengcaifan`。[E1]
- `Chat/Chat/TPFundation/Extension/SafeArray.swift`。
- 原类采用 `DispatchQueue(..., attributes: .concurrent)`。本次核对了提交及其父版本，不是从当前 HEAD 反推旧实现。

### 4.2 旧实现的两层问题

```swift
func removeAndReturnPreElements(_ count: Int) -> [Element] {
    if self.count > count {                  // 第一段：读取长度
        var result = [Element]()
        queue.sync {
            result = Array(self.array[0..<count]) // 第二段：读取内容
        }
        self.removeFirst(count)             // 第三段：另行提交异步 barrier 删除
        return result
    } else {
        return removeAllAndReturn()
    }
}
```

1. **组合动作不原子**：检查、读取、删除之间允许其他操作进入。
2. **“返回并移除”语义不足**：内部删除异步提交，方法返回不等于该删除已完成。
3. **旧 removeFirst 的额外风险**：`guard !isEmpty` 位于修改前；实际修改用普通 `queue.sync`，在并发队列上它并不自动拥有 barrier 的独占语义。

教学构造的交错，不能冒充当年的真实调度：

```text
A：读到 count=5，打算取前 2 项
B：在 A 下一次读取前删除／清空数据
A：继续对当前数组取 0..<2，先前 count 已失效
```

即使切片没有越界，“先取回，后异步删除”的设计也不提供一个完整的 take 操作。这里必须分析具体排队顺序，不声称每次调用都会重复消费。

### 4.3 历史实际修复

```swift
func removeAndReturnPreElements(_ count: Int) -> [Element] {
    var removedElements: [Element] = []
    queue.sync(flags: .barrier) {
        let endIndex = min(count, self.array.count)
        removedElements = Array(self.array[0..<endIndex])
        self.array.removeSubrange(0..<endIndex)
    }
    return removedElements
}
```

**这段是历史补丁，不是完整生产模板。**它解决该复合操作的同步粒度，但没有新增负 count 检查，不能宣称整个容器全部输入和 API 已安全。

### 4.4 你必须说清的原理

- 这里是**自定义并发队列**。barrier 等待之前提交的任务完成，自己执行期间阻止随后任务进入；不是对任意 global queue 加 barrier 就获得同样的私有读写保护。[A1]
- `sync` 的语义是返回前提交的工作完成；不是“必然切换到一条后台线程”。[A1]
- 只有相关读写都遵守同一隔离机制，才有保护。暴露原始存储、另一个队列直接访问、可变引用元素在外部被修改，都超出这个保证。
- 同一队列内重新同步提交、以及任务之间互相等待会有死锁风险。临界区内不能再调用会重新进入该同步机制的公共接口。
- 把原子性落实在小接口里，比要求每个调用方先 count、再读取、再删除更可维护。

### 4.5 如今天再完善，怎样回答（不是当年已做）

> “今天我会再补输入约束、队列重入检查和接口语义说明；队列应在初始化阶段确定，不依赖无同步的首次 lazy 初始化。临界区只做必要的数组操作，不做网络、磁盘或调用未知业务回调。大量头部删除还要关注 O(n) 移动成本，必要时评估环形缓冲／双端队列，不把安全修复等同于性能最优。”

回归设计：空数组、0／负数、N 大于当前长度、多个消费者、并发 append／drain，以及返回集合无重复／无遗漏。**这是当前完善建议，不声称 2023 年已有完整测试。**

本次课堂模型已验证负数／0／超长请求与 64 个并发消费者；它不是原项目运行测试，详见第 11 节。

### 5.3 一个能算清楚的边界例子

教学数字，**不是线上业务量统计**：旧数据 10 条，展示上限 100，来新消息 100 条。

旧逻辑：

```text
100 > 100 不成立，没有进入“清旧数据、保留新窗口”分支
removeCount = 10，但 10 < oldCount(10) 不成立，没有删除
UI 新行数量：min(10+100, 100) - 10 = 90
模型却 append 100：模型最终 110，表格按操作最终 100
```

新逻辑：

```text
新消息数量 >= 上限 → 删除旧 10 条
保留并追加新 100 条 → 插入 100 行
模型与表格目标都是 100
```

固定单 section、没有跨 section move 等额外操作时，必要的数量关系是：

`N_after = N_before - D + I`

**数量匹配还不够**：删除路径应针对旧状态，插入对应结果状态，模型 ID 与 index path 也要一致。`performBatchUpdates` 要求数据源同步反映对应变更，不是在 completion 中才改模型。[A2]

### 5.4 追问时的三个边界

- “放主线程就安全了吗？”——解决 UI 线程使用要求，不自动解决旧状态与新批次混用。
- “reloadData 是否更稳？”——在复杂或无法可靠生成增量计划时是备选，有刷新成本；历史 7 月尝试和 8 月策略变化不能说成已经验证的普适最优方案。
- “是否丢消息？”——这里裁剪的是公屏**展示窗口**。这段补丁不能证明服务端消息接收和持久化的完整性，不承诺所有历史都保留。

### 6.3 源码事实

**提交作者支持代码归属，不自动证明你是每项决策唯一负责人。**

### Q4：SafeArray 已用并发队列，为什么还会出问题？

> “同步机制的粒度不够。count getter 安全不代表它的值在下一次操作前仍有效；普通 sync 也不等于并发队列的独占写。要把业务要求的检查、取值和修改作为一个受保护动作，而不是让调用方拼多个接口。”[A1]

### Q5：为什么用 sync barrier，而不是 async barrier？

> “这个接口要返回被取走的数据，调用方需要返回时状态修改已完成。同步 barrier 能表达这个契约。异步方案也可以设计，但要改成 completion 或 async 接口，并在实际操作完成后交付结果，不能方法先返回、删除另行排队却仍称同步取走。”[A1]

### Q6：barrier 是不是全局锁？

> “不是。这里基于自定义并发队列，相关操作必须都提交到同一队列。它不保护另一个队列的绕过访问，也不保证返回的引用元素内部状态安全，更不能把 global queue 的 barrier 当私有容器的同等读写锁。”[A1]

### Q7：会不会死锁或影响主线程性能？

> “会有风险，尤其在同一隔离上下文里重新 sync，或者持有其他锁形成等待环。临界区应该小，不能执行未知回调或 I/O。同步调用也可能让主线程等待已有工作；头部删除和复制还会随数据量增长。所以正确性修复后还要测负载，必要时改数据结构。我没有现成历史测量值，不报虚构微秒数。”[A1]

### Q8：如果重做，为什么不直接用 Actor？

> “可以作为新模块的选择，但要考虑调用方是否能接受异步接口和改造成本。Actor 保护隔离状态，不自动保护跨实际悬挂点的业务不变量；如果取出和删除之间 await，仍可能允许其他操作改变状态。换工具不能替代正确的操作边界。”[A4]

### Q9：批更新为什么放主线程仍可能崩？

> “UI 主线程要求与模型一致性是两个问题。即使全在主线程，不同异步批次或回调也可能沿用旧索引。performBatchUpdates 接收的删除、插入与数据源变化，必须描述同一个旧状态到目标状态的迁移；数量、身份和路径都要一致。”[A2]

### Q10：为什么不全用 reloadData？为什么不全用 Diffable？

> “reload 是无法可靠增量更新时的备选，但有刷新和滚动成本；Diffable 可以减少手工路径计算，但仍需要稳定 ID、合法快照和明确的提交顺序。我们历史上确实调整过 reload 与 append 策略，不能据此说某种方案永远最好。方案取决于消息频率、展示窗口和一致性要求。”

这里是方案比较，不宣称历史消息面板已经迁移到 Diffable。

### Q11：EXC_BAD_ACCESS 是野指针吗？0x10 呢？

> “都不能直接这样判断。EXC_BAD_ACCESS 是内存访问异常的表现；subtype 解释访问为何非法，不等于业务根因。低地址可能提示空基址加字段偏移，需要看故障指令和寄存器；use-after-free 还需要生命周期证据。NSRangeException 是语言异常，不是 EXC_BAD_ACCESS 的 subtype。”[A5]

### Q12：Zombie、ASan、TSan 怎样选择？

> “已释放 ObjC 对象仍收到消息，用 Zombie 查相应线索；越界和释放后访问等内存破坏，用 ASan；无同步共享内存访问，用 TSan。它们依赖执行路径与支持环境，未报错不是无 Bug 证明。iOS 的 TSan 应在支持的 Simulator 上运行，不承诺真机可用。”[A5–A6]

### Q13：栈顶在 malloc／alloc，是不是 OOM？

> “我会先放入内存风险调查方向，而不是确认为 OOM。需要区分资源峰值、错误输入、分配失败和更早的堆破坏，再结合报告、设备和内存信息。系统因资源限制终止、普通内存访问异常和客户端推断的退出原因，也不是同一个统计口径。”[A5–A7]

### Q14：FOOM 怎么讲？你做过自研归因吗？

> “FOOM 我会作为业务/APM 侧疑似前台内存相关退出的口径来解释，不能把它说成精确系统标签。Jetsam 可能有系统事件报告，但通常不是含线程回溯的普通 Crash 报告。是否项目实际接入自研退出归因，要以实现与数据口径为准；这次崩溃提交复盘不足以证明完整 FOOM 系统。”[A7]
