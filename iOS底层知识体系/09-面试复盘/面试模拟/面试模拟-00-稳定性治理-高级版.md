# 面试模拟 00（高级版）：Gravity 稳定性治理

> **目标岗位**：10 年以上高级 / 资深 iOS 工程师、核心业务 Owner、偏 Tech Lead 的岗位。
>
> **与旧版的关系**：本文是 `面试模拟-00-稳定性治理.md` 的面试表达重构版。旧版保留较多原理资料和方案草稿；本文只保留可用于面试的项目叙事、工程决策、关键追问和待补案例卡。
>
> **事实边界**：以下已知事实：2023 年 Gravity 业务和 DAU 快速增长、语音房进入营收场景；早期已接 Firebase；Crash 最高约 `0.23%`、后续约 `0.01%`；FOOM 数据后期上线，峰值约 `0.7%`、后续约 `0.2%`。所有具体口径、实现细节、案例数据必须在面试前按真实线上资料补全，不能补造。

---

## 1. 高级岗位的回答原则

稳定性项目不应回答成“我会 Firebase、Hook 和 Zombie”。面试官真正想确认的是：

1. **你如何判断问题和数据是否可信**：Crash 栈、FOOM 归因和行为日志都不是真相本身；
2. **你如何排优先级**：用户影响、核心业务路径、可修复性和治理风险如何权衡；
3. **你如何做工程取舍**：监控、诊断和防护本身也会产生性能、隐私、兼容性和维护成本；
4. **你如何让系统长期运行**：发现、归因、修复、验证、发布与防回退，而不只是一次专项；
5. **你本人负责什么**：必须说明 Owner 边界，避免把团队或平台能力都说成个人实现。

**表达模板**：`业务背景与约束 → 数据和判断 → 方案与取舍 → 个人职责 → 结果与验证 → 复盘`。

## 2. 主回答（3～4 分钟）

> “我负责 Gravity 的稳定性治理是在 2023 年。当时业务和 DAU 增长很快，语音房也开始成为营收场景。Feed 和语音房的使用量、状态复杂度和资源消耗都明显上升，而早期在监控、性能基线和技术债治理上的投入不足，开始集中表现为用户反馈卡顿、崩溃和内存问题；当时 Crash 最高约 0.23%。
>
> 我当时没有把它看成逐个修 Bug，而是把目标定为建立一套持续运行的稳定性机制。短期希望把 Crash 控制到 0.1% 内，长期稳定在 0.02% 左右；同时明确不能只看 Crash，需要逐步把卡顿、内存和 FOOM 纳入同一套治理视图。我的主要职责是推动 iOS 侧的数据补齐、问题归因和治理落地，并和业务、QA、数据及相关 SDK 同学共同闭环。
>
> 第一阶段先解决可观测性问题。项目当时已有 Firebase，因此我们按 Crash Issue、版本、机型和业务场景梳理 Top 问题。但崩溃栈通常只能告诉我们‘在哪里异常’，不能完整解释‘用户经过什么操作和状态走到这里’。所以我们补了关键路径日志，并采集 CPU、内存、FPS 等性能上下文，优先覆盖 Feed、语音房的进入退出和关键状态切换。这样才能把 Crash、用户操作和性能状态关联起来，缩小复现范围。
>
> 后续 FOOM 数据上线后，峰值约 0.7%。这让我们确认只看 Firebase 的常规 Crash 会低估内存风险。FOOM 没有普通 Crash 那样的标准堆栈，因此我们把它作为基于退出状态、前后台和已捕获 Crash 等信号得到的疑似指标，再结合内存水位、机型档位和业务场景观察趋势；它用于指导优先级，不会被表述成百分之百精确的系统退出原因。
>
> 治理上我坚持分层。堆栈明确、能够复现的问题优先修根因，例如生命周期、线程访问、资源释放和容器使用问题。对少量历史遗留、高频且能安全降级的容器边界问题，才做有限范围的 Runtime 防护，并保留触发日志、开关、灰度和回滚；防护的目的是止血和补线索，不替代修根因。野指针、泄漏和内存峰值问题，线上先按版本和场景缩小范围，线下用 Zombie、Memory Graph、Instruments 等工具验证。卡顿则通过 RunLoop 监控发现线索，再结合 Time Profiler、Core Animation 和压力回放定位主线程瓶颈。
>
> 最后我们把 Crash、FOOM、卡顿、内存、磁盘和内购等核心指标接入自动告警，并按版本、设备和业务场景持续观察。经过长期治理，Crash 从约 0.23% 降到约 0.01%，FOOM 从数据上线后的峰值约 0.7% 降到约 0.2%。我认为最有价值的不是某一个 Hook，而是把发现、归因、修复、验证和防回退固化成了可持续的工程机制。”

### 30 秒压缩版

> “2023 年 Gravity 在业务增长和语音房营收阶段，Feed、语音房的 Crash、卡顿和内存问题集中暴露。我们先用 Firebase 按 Issue、版本、机型和场景建立基线，再补关键路径日志和 CPU/内存/FPS 上下文；FOOM 数据上线后发现峰值约 0.7%，因此把内存风险纳入治理。可定位问题优先修根因，少量可安全降级的边界问题才做受控 Runtime 防护，野指针和内存问题在线上缩小范围、线下验证，卡顿通过 RunLoop 监控和性能工具定位。最终 Crash 约从 0.23% 降到 0.01%，FOOM 从约 0.7% 降到约 0.2%，并形成了自动告警和防回退机制。”

## 3. 主回答的关键决策点（高级岗位拉分）

| 决策 | 为什么这样做 | 体现的能力 |
|---|---|---|
| 不先大规模 Hook，而是先按数据建立 Top 问题和场景基线 | 防护可能掩盖根因并带来兼容风险；没有上下文无法有效排优先级 | 证据驱动、风险控制 |
| Firebase 之外补关键路径和性能上下文 | 栈能定位异常点，但往往缺少触发状态和业务路径 | 可观测性设计 |
| FOOM 定位为“疑似指标”而非精确退出原因 | 系统内存终止通常没有应用可用的标准 Crash 现场 | 数据可信度与边界意识 |
| 根因修复优先于 Runtime 防护 | 防护只能止血，可能造成静默错误 | 技术债治理 |
| 按业务场景、设备和版本分桶验证 | 全局均值容易掩盖核心路径或低端机恶化 | 指标/SLO 思维 |
| 诊断与告警都限频、采样、可关闭 | 监控本身也有性能、功耗、隐私和噪声成本 | 工程成本意识 |

## 4. 必答追问

### Q1：Crash、FOOM、卡顿为什么必须先定义口径？

> “没有统一口径，优化前后比较的就不一定是同一件事。Crash 要明确分母是活跃用户、活跃设备还是会话/启动次数，统计窗口、去重规则、是否按版本和机型拆分；卡顿要明确阈值、连续次数、采样和去重方式。
>
> FOOM 更需要谨慎，它是异常退出的归因指标，不是系统给的绝对标签。所以要明确排除了哪些退出、还有什么误判边界。验证时既看比例也看影响用户数，并在同版本、同设备档位和重点业务场景下做对比。”

**继续追问：如何避免把用户量或版本覆盖率变化误认为优化成果？**

> “对比新旧版本同期，按重点机型和重点场景分桶；同时看绝对影响用户数和比例。灰度阶段观察趋势，并结合功能开关、流量结构变化和版本覆盖率解释异常点，不能只拿全局均值下结论。”

---

### Q2：Firebase / Crashlytics 的价值和边界是什么？

> “它是 Crash 治理的入口：可以按堆栈聚合 Issue，并关联版本、机型和系统信息，适合做优先级排序和修复后的回归验证。但它不能替代业务上下文；堆栈不一定说明用户为什么走到该状态。对 Jetsam 类内存终止、部分 Watchdog 或异常退出，也不一定有可靠的传统 Crash 栈。因此我们补关键路径日志、性能上下文和后续的 FOOM 归因。”

**继续追问：`alloc` / `malloc` 出现在栈里是不是 OOM？**

> “不是。它只是内存风险线索，可能是分配失败、堆损坏、非法访问或第三方库问题。是否和内存压力相关，要结合设备、场景、内存水位、系统退出信号和线下复现判断。”

---

### Q3：FOOM 是什么？怎么归因，误判来自哪里？

> “这里我会明确说 FOOM 是业务/APM 侧的疑似前台内存相关异常退出指标，而不是 iOS 提供的百分之百精确系统标签。普通 Crash 往往有异常现场，Jetsam 类终止通常没有，所以需要根据上次运行的前后台状态、版本升级、已落盘 Crash、启动完成状态等信号做排除，再结合内存水位、设备档位和业务场景观察趋势。
>
> 误判可能来自 Watchdog、用户或系统结束进程、生命周期状态记录不完整、版本升级或后台切换。因此 FOOM 适合用于趋势、版本和场景排序；对单个退出只能作为排查线索，不能轻率地下最终结论。”

**继续追问：为什么不能只依赖 `applicationWillTerminate:`？**

> “它不会覆盖很多实际退出路径，特别是系统终止或用户直接结束进程。因此它最多是辅助信号；真正的归因要使用多信号交叉排除，并明确数据不是绝对真值。”

---

### Q4：Runtime 防护怎么做，为什么不全局吞 `unrecognized selector`？

> “Runtime 防护只用于少量高频、边界明确且业务可安全降级的问题。例如对实际高频的特定容器类簇和特定 API 做白名单化边界保护；触发时记录类、selector、场景和调用信息，并保留开关、灰度和回滚。
>
> 我不会全局 Hook `NSObject` 的消息转发，更不会把所有未知 selector 转给通用代理吞掉。未知方法的参数和返回值可能不同，通用签名有 ABI 风险；更重要的是，这通常表示对象类型、生命周期或接口契约出了问题，吞掉 Crash 可能把故障变成更隐蔽的数据错误。对这类问题优先用堆栈、日志、断言和线下复现修根因。”

**继续追问：为什么常见做法放在 `+load`？**

> “如果需要确保目标 API 在首次业务调用前完成注册，轻量的 `+load` 是常见选择；但它不是唯一选择，也不能做 I/O、对象初始化或其他耗时工作，避免影响启动。实现上要处理真实类簇、继承关系和重复注册，不能只机械交换两个 IMP。”

---

### Q5：野指针、泄漏、内存峰值如何分别定位？

> “先区分曲线和症状，而不是看到内存高就叫泄漏。多次进退场后基线持续上升，优先看生命周期和持有链；某个操作瞬时上冲，优先看大图、解码、批量对象和重复副本；长期高位不回落，则看缓存上限和对象堆积。
>
> 线上通过版本、机型、场景、行为日志和最后的性能状态缩小范围；线下再用 Zombie / ASan 定位 use-after-free，用 Memory Graph、Leaks、Allocations / Generation Mark 看引用链和分配。线上不默认全量开启 Zombie 或全局延迟释放，因为其内存、性能和兼容成本不可控。”

---

### Q6：RunLoop 卡顿监控怎样避免流于“加 Observer”？

> “RunLoop Observer 是发现主线程长时间没有回到正常事件循环的信号，不是完整的卡顿结论。实现通常是在主线程监听关键状态，后台按时间窗口判断是否连续超时；达到阈值后采集主线程栈、前后台状态、页面和关键操作，并做去重、限频。
>
> 还要处理敏感度与成本：阈值过低会误报，频繁抓栈有功耗成本，栈只能说明卡在哪里。最终必须结合 Time Profiler、Core Animation、压力回放和业务日志，区分文本布局、图片解码、频繁刷新、锁竞争、主线程 I/O 或渲染问题。”

---

### Q7：怎么证明治理有效，并防止回退？

> “不能只看一次测试截图或一个全局百分比。Crash 看 Issue、影响用户数和重点场景趋势；内存看场景峰值、退出后的基线、重点机型和 FOOM 趋势；卡顿看时长分布、发生场景和主线程 CPU。发布时按版本、设备和业务场景观察，必要时通过灰度和功能开关控制风险。
>
> 长效机制包括 dSYM 自动归档、核心指标告警、高风险功能的降级预案、Code Review 中的生命周期/线程/主线程耗时/资源释放检查项，以及 P0 事故复盘后补齐测试和监控。”

## 5. 进阶追问（选择性准备，不主动堆砌）

### Q8：一个高级工程师如何排序稳定性 Issue？

> “我不会只按发生次数排序，会综合四类信号：影响用户数和频率、是否落在营收/登录/进房等关键链路、可复现和可修复程度、以及处理本身的风险和成本。比如语音房进房或支付路径上一个比例不高的 Crash，可能比普通页面的高频轻微异常优先级更高。排序结果要能解释给业务和管理者，而不是只给技术团队看。”

### Q9：监控和日志怎样控制成本和隐私？

> “日志先定义最小必要字段，业务内容脱敏；高频事件限频、采样和批量上报；离线或弱网时做本地容量上限和过期淘汰；诊断能力支持远程关闭。任何新增指标都要说明它能支持哪项决策，否则不值得长期采集。”

### Q10：如何设计 Crash 聚合？

> “按异常类型和符号化后的关键业务帧生成稳定 fingerprint，过滤通用系统帧和 SDK 自身帧，必要时折叠递归重复帧。聚合后同时看影响用户数、次数、版本、机型和业务场景。行号通常用于定位展示，是否参与 fingerprint 取决于聚合粒度，不应机械地只做字符串 hash。”

### Q11：这个项目的难点是什么？

> “单点技术并不一定最难，难的是信息不完整时的工程决策：Crash 栈、日志和 FOOM 归因都有不确定��；诊断和防护本身会带来性能、兼容性和隐私成本；业务高速迭代又不能停摆。因此需要持续判断证据强弱、按用户影响排序、用最小副作用的方案降低风险，并把经验沉淀成团队机制。”

## 7. 不建议直接使用的表述

| 不建议 | 更成熟的说法 |
|---|---|
| “Firebase 覆盖 95% 崩溃。” | “Firebase 覆盖大部分有崩溃现场的异常，但对系统终止和异常退出有边界。” |
| “`malloc` 栈就是 OOM。” | “它是内存风险线索，需结合场景、内存数据和复现判断。” |
| “FOOM 排除法可以精确判断 OOM。” | “FOOM 是疑似指标，要说明排除项和误判边界。” |
| “全局吞掉未知 selector 就能防崩。” | “全局吞消息风险很高，应优先修接口契约和生命周期根因。” |

| “我实现了某诊断框架的所有底层能力。” | “区分项目实际接入能力、自己实现部分和学习/选型方案。” |

- 能在 **3～4 分钟**讲清主回答，不堆砌工具；
