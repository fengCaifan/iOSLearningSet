### A — Action（行动）

> "具体工作分了以下几步：

#### 第一步：分析现状

我们最初的版本有对接 Firebase，所以有一些基础信息可以获取。我们发现大多数崩溃都可以被捕获，常见的 **Mach Exception、Signal 崩溃、NSException（OC 崩溃）** 等，基本覆盖了 95% 的崩溃。另外 Firebase 无法捕获的就是 **OOM / FOOM** 崩溃，需要我们自己收集。之所以要掌握 OOM 相关的崩溃，是因为我们发现 Firebase 上已经有很多定位在 `alloc`、`malloc` 的崩溃，这些崩溃通常都是在少内存的低端设备上出现的，说明内存对崩溃的影响比较大。另外就是按场景区分优先级，像语音房、Feed 这种用户使用高频的场景的崩溃要优先解决。

#### 第二步：数据先行，完善日志打点上报

1. 因为 Firebase 捕获到的堆栈不一定是崩溃现场，所以我们需要尽可能多地收集用户的行为日志。我们用 **AOP Hook** 了主要功能的打点；
2. 对 **CPU、内存、FPS** 等使用情况进行了定时采集；
3. 补充了对应的 **FOOM 和 OOM 的判断**（排除法），然后打点上报。

#### 第三步：实际治理

**① 常见崩溃类型的 Hook 防护**

对数组越界、字典插入 nil、找不到对应方法（unrecognized selector）等常见崩溃，我们加了对应的 API Hook：

- **数组越界**：对 `NSArray`、`NSMutableArray` 等类簇的 `objectAtIndex:` 等方法进行 Method Swizzling，加入边界检查，越界时 log 上报而不是直接 crash；
- **字典插入 nil**：对 `NSDictionary`、`NSMutableDictionary` 的 `setObject:forKey:` 等方法拦截 nil 值；
- **Unrecognized Selector**：利用 OC 消息转发机制的三次补救机会：
  1. `+resolveInstanceMethod:` — 动态添加方法实现；
  2. `forwardingTargetForSelector:` — 转发给一个安全的"桩对象"来消化无法识别的消息；
  3. `forwardInvocation:` — 最终兜底，记录错误信息上报，避免抛出 `NSInvalidArgumentException`。
  
  我们的做法是在 `forwardingTargetForSelector:` 这一步，将消息转发给一个全局的 **SafeProxy** 对象，该对象通过 `methodSignatureForSelector:` + `forwardInvocation:` 吞掉消息并上报日志。

**SafeProxy 完整实现：**

```objc
// ============ SafeProxy.h ============
@interface SafeProxy : NSObject
+ (instancetype)sharedInstance;
@end

// ============ SafeProxy.m ============
@implementation SafeProxy

+ (instancetype)sharedInstance {
    static SafeProxy *instance;
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        instance = [[SafeProxy alloc] init];
    });
    return instance;
}

// 关键：为任何 SEL 返回一个合法的方法签名（避免抛异常）
- (NSMethodSignature *)methodSignatureForSelector:(SEL)aSelector {
    // 返回一个通用签名：返回 void，无参数（v@:）
    return [NSMethodSignature signatureWithObjCTypes:"v@:"];
}

// 关键：吞掉调用，不执行任何操作，只记录上报
- (void)forwardInvocation:(NSInvocation *)anInvocation {
    // 到这里消息已经被安全拦截，不会崩溃
    NSString *selectorName = NSStringFromSelector(anInvocation.selector);
    NSLog(@"[SafeProxy] 拦截到未识别消息: %@", selectorName);
    
    // 上报到 APM（线上统计哪些 selector 被误调用）
    [APMLogger reportUnrecognizedSelector:selectorName
                               targetClass:NSStringFromClass([anInvocation.target class])
                                callStack:[NSThread callStackSymbols]];
}

@end

// ============ NSObject+SafeSwizzle.m ============
// 在 NSObject 的 Category 中 Hook 消息转发
+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        // Hook forwardingTargetForSelector:
        Class cls = [NSObject class];
        SEL originalSEL = @selector(forwardingTargetForSelector:);
        SEL swizzledSEL = @selector(safe_forwardingTargetForSelector:);
        
        Method original = class_getInstanceMethod(cls, originalSEL);
        Method swizzled = class_getInstanceMethod(cls, swizzledSEL);
        method_exchangeImplementations(original, swizzled);
    });
}

- (id)safe_forwardingTargetForSelector:(SEL)aSelector {
    // 先调原始实现，看是否有正常的转发目标
    id target = [self safe_forwardingTargetForSelector:aSelector];
    if (target) {
        return target; // 有正常转发目标，不干预
    }
    
    // 过滤系统私有方法（避免干扰系统行为）
    NSString *selName = NSStringFromSelector(aSelector);
    if ([selName hasPrefix:@"_"] || [selName hasPrefix:@"accessibility"]) {
        return nil; // 系统方法走原始流程
    }
    
    // 没有转发目标 → 即将崩溃 → 转发给 SafeProxy 兜底
    return [SafeProxy sharedInstance];
}
```

**SafeProxy 工作流程：**
```
调用 [obj unknownMethod]
     ↓
Runtime: objc_msgSend 查找 → 找不到 IMP
     ↓
resolveInstanceMethod: → 未动态添加 → NO
     ↓
forwardingTargetForSelector: → 被我们 Hook
     ├── 原始逻辑有转发目标？→ 走正常转发
     └── 无转发目标？→ return SafeProxy
          ↓
     Runtime 向 SafeProxy 发送 unknownMethod
          ↓
     SafeProxy.methodSignatureForSelector: → 返回通用签名
          ↓
     SafeProxy.forwardInvocation: → 吞掉消息 + 上报日志
          ↓
     不崩溃，程序继续运行
```

**② 野指针崩溃治理**

比较难处理的是野指针崩溃，因为大多数野指针崩溃很难从堆栈直接定位到具体业务场景。我们的做法是：
- **线上**：查看用户崩溃时间点的行为日志，结合崩溃堆栈回溯用户操作路径；
- **线下**：打开 **Zombie Objects** 来复现崩溃场景。根据线上用户行为日志模拟操作路径，Zombie 会在访问已释放对象时给出明确的类名和调用信息。这个思路可以复现大多数的崩溃问题。

**③ 内存相关的崩溃治理**

内存相关的崩溃没法具体定位到某一个堆栈，只能根据统计数据，按模块、业务来排查。拿语音房举例：

- 首先看进出语音房前后的**内存使用对比**，根据数据判断是否有内存泄漏；
- **内存泄漏治理**分 2 种：
  1. 可以用 **MLeaksFinder** 捕获的内存泄漏（循环引用、delegate 未 weak、Timer 未释放等）；
  2. **资源缓存没有及时释放**导致内存越来越大 — 用 Instruments Allocations 的 **Generation Mark** 在线下跑主要场景，对比每两个 Mark 之间使用内存最多的类型有哪些，然后对应去治理；
- 另外就是**移除无用的 SDK**，尤其是项目启动就初始化的单例。这里主要就是 Unity — 我们将 Unity 整体移除后，内存下降非常明显。

#### 第四步：防护和监控

1. 刚才说的**常见崩溃的 Hook 防护**（兜底不崩，但同时上报）；
2. 对日常的**崩溃率和 OOM 率**做每天的定时预告和告警：
   - 我们将崩溃数据接入了神策概览；
   - 每天早上把崩溃概览截屏发到邮箱；
   - 我们在打包机上上线了一个网站服务，功能是每天早上定时去邮箱获取对应的邮件和截图，然后通过如流的机器人发到开发群里；
   - 只要崩溃异常陡增，我们立刻就可以获悉。"

## 深挖问题

---

### 深挖 Q1：崩溃是怎么分类的？

**答**

从系统层级来看，iOS 崩溃分为三层，**由底层到上层**：

**① Mach Exception（最底层）**
- 内核级异常，通过 Mach 端口机制传递；
- 常见：`EXC_BAD_ACCESS`（野指针/越界访问）、`EXC_BAD_INSTRUCTION`（非法指令）、`EXC_ARITHMETIC`（除零）、`EXC_BREAKPOINT`（断点/断言）。

**② BSD Signal（中间层）**
- Mach Exception 未处理时**转化**为 Unix Signal；
- 常见对应关系：
  - `EXC_BAD_ACCESS` → `SIGSEGV` / `SIGBUS`
  - `EXC_BAD_INSTRUCTION` → `SIGILL`
  - `EXC_ARITHMETIC` → `SIGFPE`
  - `EXC_BREAKPOINT` → `SIGTRAP`
  - NSException 未捕获 → `SIGABRT`

**③ NSException（应用层，OC/Swift）**
- OC 的 `@throw` 或 Foundation 框架抛出的异常；
- 常见：`NSInvalidArgumentException`（unrecognized selector）、`NSRangeException`（数组越界）、`NSInternalInconsistencyException`。
- 未捕获的 NSException 最终也会转化为 `SIGABRT`。

**不可捕获的崩溃（约 5%~10%）**：
- **OOM / Jetsam**：系统发 `SIGKILL`，不可被任何进程捕获；
- **Watchdog**：启动/后台任务超时被系统杀掉；
- 这些需要通过排除法等间接方式判断。

### 深挖 Q2：Hook 怎么做？为什么在 +load 中做 Hook，不在 +initialize 中做？

**答**

**Hook 实现方式 — Method Swizzling：**

```objc
+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        Class cls = NSClassFromString(@"__NSArrayM"); // NSMutableArray 的类簇真实类
        Method originalMethod = class_getInstanceMethod(cls, @selector(objectAtIndex:));
        Method swizzledMethod = class_getInstanceMethod(cls, @selector(safe_objectAtIndex:));
        method_exchangeImplementations(originalMethod, swizzledMethod);
    });
}
```

**为什么必须在 `+load` 而不是 `+initialize` 中做：**

| 特性 | `+load` | `+initialize` |
|------|---------|---------------|
| 调用时机 | 类被加载到内存时（dyld 阶段） | 类第一次收到消息时 |
| 调用次数 | 只调一次，且父子类各自调一次 | 可能不被调用（类从未使用） |
| 线程安全 | Runtime 保证线程安全 | Runtime 加锁保证线程安全 |
| 执行顺序 | 确定（父类→子类→Category） | 不确定（取决于谁先发消息） |

**核心原因：**

1. **时机确定性**：`+load` 在 App 启动时、任何业务代码执行之前就会被调用，保证 Hook 在**第一次使用前就生效**。如果放在 `+initialize`，万一在 `+initialize` 执行之前就有代码调用了未 Hook 的方法，就会漏掉防护导致崩溃；
2. **一定会执行**：`+initialize` 只在类第一次收到消息时触发，如果某个类从未被使用过，Hook 就不会生效。而 `+load` 只要类被编译进二进制就一定会执行；
3. **无继承干扰**：`+initialize` 有继承链传递机制（子类没实现会调用父类的），可能导致重复 Hook。`+load` 不参与消息转发和继承。

**`+load` 的注意事项：**
- `+load` 中不要做耗时操作，会影响启动速度；
- Method Swizzling 用 `dispatch_once` 保证只执行一次；
- 对类簇要找到真实的私有子类（如 `__NSArrayM`、`__NSSingleObjectArrayI` 等）。

### 深挖 Q3：Zombie 的原理是什么？线上可以怎么做野指针 Hook？

**答**

**Zombie Objects 原理：**

```
正常释放流程：
  对象 dealloc → 内存回收 → 地址可被复用

开启 Zombie 后：
  对象 dealloc → 不真正释放内存
       ↓
  将对象的 isa 指针改为 _NSZombie_原类名
       ↓
  对象变为 Zombie 实例（内存保留、对象"僵尸化"）
       ↓
  任何向该对象发送的消息都会被拦截
       ↓
  输出："-[_NSZombie_MyClass doSomething]: message sent to deallocated instance 0x..."
```

**核心机制：**
1. Hook `dealloc` → 不调用 `free()`，对象内存不回收；
2. 用 `object_setClass(obj, zombieClass)` 将 isa 指向动态生成的 `_NSZombie_XXX` 类；
3. 该 Zombie 类的 `forwardingTargetForSelector:` 等方法会打印错误信息并中断。

**为什么 Zombie 不能上线：**
- 不释放内存 → 内存只增不减 → 很快 OOM；
- 适合**线下精确定位**，不适合线上使用。

---

**线上野指针 Hook 方案（SafeObj / 死亡档案思路）：**

```
线上轻量方案原理：

1. Hook objc_destructInstance / dealloc
       ↓
2. 对象释放时，不立即 free
   而是将对象信息写入「死亡档案」Ring Buffer：
   ├── 对象类名
   ├── 对象地址
   ├── 释放时间戳
   └── 释放时的调用栈（轻量回溯，只取 Top 5~8 帧）
       ↓
3. 将该内存块填充特定模式（如 0x55），延迟释放
   （Ring Buffer 满时，淘汰最早的记录，真正 free）
       ↓
4. 当发生 EXC_BAD_ACCESS 时：
   ├── 取 fault address
   ├── 在 Ring Buffer 中查找该地址
   └── 若匹配，则合并「访问栈 + 释放栈 + 类名」上报

优势：
  ✅ 内存开销可控（Ring Buffer 固定大小，如 2~5MB）
  ✅ 能提供释放时的类名和栈，辅助归因
  ✅ 采样开启（如 10% 用户），性能影响有限

局限：
  ❌ Ring Buffer 容量有限，早于缓冲区淘汰的野指针无法捕获
  ❌ 不是 100% 实锤，是启发式匹配（地址可能已被复用）
  ❌ 只是线索辅助，不能像 Zombie 那样精确到消息级
```

**面试话术收尾：**
> "Zombie 是线下神器，能精确告诉你哪个类的哪个方法被发给了已释放对象；但它无法上线。线上的做法是 Ring Buffer 记录死亡档案，崩溃时做启发式匹配，提供**释放栈 + 类名**作为排查线索。结合用户行为日志，线下用 Zombie 复现，可以解决大部分野指针问题。"

### 深挖 Q4：这些都是基础的常见的业务上的崩溃治理，难度体现在哪里？

**答**

> "确实单个技术点看都不算特别深，难度主要体现在以下几个方面：

**① 问题的不确定性和不可复现性**

- 线上崩溃大部分是**偶发的**，尤其是野指针和多线程问题，可能只在特定设备、特定内存压力、特定操作时序下才出现；
- 用户行为日志和崩溃堆栈之间有**信息断层** — 堆栈告诉你「死在哪里」，但不告诉你「怎么走到那里的」；
- 有些崩溃的堆栈指向系统库或第三方 SDK 内部，需要逆向推断是哪个业务逻辑触发的。

**② 系统性工程的复杂度**

- 不是修一两个 bug 就完事，而是需要建立一套**从发现、定位、修复到预防的完整体系**；
- 涉及多个系统的联动：打点系统、崩溃捕获、日志上报、告警机器人、数据看板 — 任何一环缺失都会影响效率；
- 需要在**性能开销和信息完整度之间做平衡** — 比如行为日志打太多影响性能和包大小，打太少出问题时信息不够。

**③ OOM 类问题的定位困难**

- 没有堆栈、没有崩溃日志、系统直接 SIGKILL — 传统的崩溃治理思路完全用不上；
- 内存问题是**全局性的** — 可能是 A 模块泄漏 + B 模块大图 + C 模块缓存没释放，叠加起来才触发 Jetsam，不是某一处的问题；
- 需要结合排除法、内存水位监控、Generation Mark、MLeaksFinder 等多种手段交叉验证。

**④ 业务迭代与稳定性的矛盾**

- 23年是增长最快的时期，业务需求排期非常紧，不可能停下来专门做稳定性；
- 很多崩溃是**新功能引入的** — 需要在不阻碍业务节奏的前提下，建立起防劣化机制；
- 需要推动团队形成规范：Code Review 加入高危检查、新功能默认加降级开关等，这涉及到协作和流程，不纯粹是技术问题。

**⑤ 效果验证的滞后性**

- 崩溃率的改善不是改完代码就能立刻看到的，需要等版本发布、用户更新、数据积累；
- OOM 的治理效果更是需要观察多个版本的趋势才能确认；
- 过程中需要耐心做持续的数据跟踪和对比分析。"

**面试话术收尾：**
> "总结来说，难度不在于单点技术的深度，而在于**在信息极度不完整的情况下，如何系统性地构建一套排查-治理-防护的闭环**，同时还要在业务高速迭代的环境下落地。"

### 补充 Q5：AOP 的原理是什么？你们怎么用 AOP 做打点？

**答**

**AOP（Aspect-Oriented Programming，面向切面编程）** 的核心思想是在**不修改原有业务代码**的前提下，在方法执行的前后插入额外逻辑（如日志、打点、性能监控等）。

**iOS 中 AOP 的底层实现原理 — Method Swizzling：**

```
OC 方法调用的本质：
  [obj doSomething]
       ↓ 编译为
  objc_msgSend(obj, @selector(doSomething))
       ↓ Runtime 查找
  在类的 method_list 中，通过 SEL 找到对应的 IMP（函数指针）
       ↓
  调用 IMP

Method Swizzling 做的事：
  交换两个 SEL 对应的 IMP 指针

  交换前：
    SEL(doSomething) → IMP(原始实现)
    SEL(hook_doSomething) → IMP(Hook实现)

  交换后：
    SEL(doSomething) → IMP(Hook实现)      ← 外部调用走这里
    SEL(hook_doSomething) → IMP(原始实现)  ← Hook内部调原始逻辑
```

**我们用 AOP 做行为打点的方式：**

```objc
// 示例：Hook UIViewController 的 viewDidAppear: 来自动记录页面曝光
+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        Class cls = [UIViewController class];
        
        SEL originalSEL = @selector(viewDidAppear:);
        SEL swizzledSEL = @selector(aop_viewDidAppear:);
        
        Method originalMethod = class_getInstanceMethod(cls, originalSEL);
        Method swizzledMethod = class_getInstanceMethod(cls, swizzledSEL);
        
        // 先尝试添加（防止父类方法被交换）
        BOOL didAdd = class_addMethod(cls, originalSEL,
                                       method_getImplementation(swizzledMethod),
                                       method_getTypeEncoding(swizzledMethod));
        if (didAdd) {
            class_replaceMethod(cls, swizzledSEL,
                               method_getImplementation(originalMethod),
                               method_getTypeEncoding(originalMethod));
        } else {
            method_exchangeImplementations(originalMethod, swizzledMethod);
        }
    });
}

- (void)aop_viewDidAppear:(BOOL)animated {
    // 1. 调用原始实现（因为 IMP 已交换，这里实际调的是原始 viewDidAppear:）
    [self aop_viewDidAppear:animated];
    
    // 2. 插入打点逻辑
    NSString *pageName = NSStringFromClass([self class]);
    [Analytics trackPageView:pageName];
    [Analytics trackMemoryFootprint]; // 顺带采集内存
}
```

**我们 Hook 的主要节点：**
- `UIViewController` 的 `viewDidAppear:` / `viewDidDisappear:` — 页面曝光/离开；
- `UIButton` 的 `sendAction:to:forEvent:` — 按钮点击；
- `UITableView` / `UICollectionView` 的 `didSelectRowAtIndexPath:` — 列表项点击；
- 网络请求的发送/回调节点 — 接口耗时和错误率。

**AOP 的优势**：业务代码零侵入，一处 Hook 全局生效，新增页面自动被覆盖。

### 补充 Q6：崩溃捕获框架（KSCrash）怎么抓到崩溃？

**答**

整体对应三层异常，各层都需要接入：

- **Mach 层**：`task_set_exception_port` 注册端口 → 监控线程收消息 → `thread_get_state` → unwind/backtrace → 写 report；
- **Signal 层**：`signal()` / `sigaction()` 注册 handler；在 handler 里通过 `ucontext_t` 取寄存器；**只能做异步安全操作**，不能 malloc、objc_msgSend；
- **NSException 层**：`NSSetUncaughtExceptionHandler`，可拿 name、reason、callStackSymbols。

### 补充 Q7：堆栈是怎么 unwind 出来的？

**答**

**ARM64 栈帧结构（核心）：**

```
高地址
┌─────────────────────────────┐
│       调用者的栈帧            │
├─────────────────────────────┤
│  Return Address (LR)        │  ← 当前函数返回后跳转的地址
├─────────────────────────────┤
│  Saved Frame Pointer (FP)   │  ← 指向上一级栈帧的 FP（形成链表）
├─────────────────────────────┤  ← 当前 FP 指向这里
│       局部变量               │
│       ...                   │
├─────────────────────────────┤  ← 当前 SP 指向这里
低地址
```

**关键寄存器：**
- **PC（Program Counter）**：当前正在执行的指令地址 → 崩溃点
- **LR（Link Register）**：存储函数返回地址 → 调用者
- **FP（Frame Pointer / x29）**：指向当前栈帧底部 → **形成链表**
- **SP（Stack Pointer）**：栈顶指针

**FP 链回溯算法（核心中的核心）：**

```c
// 简化版 FP 链遍历（KSCrash 的核心逻辑）
typedef struct FrameEntry {
    struct FrameEntry *previous;  // 上一级 FP（链表指针）
    uintptr_t return_address;     // 返回地址（即调用者的下一条指令）
} FrameEntry;

void unwind_stack(uintptr_t *buffer, int maxFrames) {
    FrameEntry *frame = __builtin_frame_address(0); // 取当前 FP
    int i = 0;
    
    while (frame != NULL && i < maxFrames) {
        buffer[i] = frame->return_address;  // 记录返回地址
        frame = frame->previous;             // 沿 FP 链向上走
        i++;
    }
}
```

**崩溃时的完整抓取流程：**

```
1. 异常触发（如 EXC_BAD_ACCESS）
       ↓
2. 进入 Mach/Signal handler
       ↓
3. 通过 thread_get_state() 获取崩溃线程的寄存器快照
   ├── PC → 崩溃点精确地址
   ├── LR → 直接调用者
   ├── FP → 栈帧链表头
   └── SP → 栈顶（辅助验证）
       ↓
4. 从 FP 开始沿链表回溯
   ├── frame[0].return_address → 第 1 层调用者
   ├── frame[0].previous.return_address → 第 2 层调用者
   ├── frame[0].previous.previous.return_address → 第 3 层
   └── ... 直到 FP == NULL（栈底）或达到最大帧数
       ↓
5. 对所有线程重复 3~4（通过 task_threads() 枚举）
       ↓
6. 将所有 instruction address 写入 JSON report
   （此时只是裸地址，如 0x100a3f4c8，还未符号化）
```

**两种回溯方式对比：**

| 方式 | 原理 | 优势 | 局限 |
|------|------|------|------|
| FP 链（Frame Pointer） | 沿 FP 寄存器链表遍历 | 快速、简单、可在 Signal handler 中安全使用 | 编译器可能优化掉 FP（`-fomit-frame-pointer`） |
| DWARF unwind info | 读取 `__eh_frame` / `__unwind_info` 段 | 即使无 FP 也能回溯 | 需要解析复杂表格，不适合崩溃现场（可能不安全） |

> ARM64 下 Apple 默认**保留 FP**（不优化掉），所以 FP 链回溯在 iOS 上是最可靠的方式。

### 补充 Q8：符号化原理？

**答**

**为什么需要符号化：**
- 崩溃时拿到的是**裸内存地址**（如 `0x100a3f4c8`）；
- 由于 **ASLR（地址空间随机化）**，每次启动 image 加载的基址不同；
- 需要把地址还原为**函数名 + 文件名 + 行号**才能定位代码。

**符号化的完整计算过程：**

```
原始崩溃地址：0x100a3f4c8
镜像加载基址（slide）：0x100a00000（从 crash report 的 Binary Images 段获取）
Mach-O 文件内偏移：0x100a3f4c8 - 0x100a00000 = 0x3f4c8

在 dSYM 的 DWARF 信息中查找 0x3f4c8：
  → Symbol Table：落在函数 -[ChatViewController sendMessage] 的范围内
  → Line Table：对应 ChatViewController.m 第 127 行

最终结果：
  -[ChatViewController sendMessage] (ChatViewController.m:127)
```

**dSYM 中的关键数据结构：**

```
dSYM 文件（DWARF 调试信息）
├── Symbol Table（符号表）
│   ├── 函数名 → 起始地址 + 大小
│   │   例：-[ChatVC sendMessage] → offset 0x3f400, size 0x120
│   └── 通过 offset 落在哪个函数的 [start, start+size) 区间来匹配
│
├── Line Number Table（行号表）
│   ├── 指令地址 → 源文件 + 行号
│   │   例：0x3f4c8 → ChatViewController.m : 127
│   └── 这就是为什么 Release 包如果 strip 了行号信息就只能定位到函数级
│
└── UUID（唯一标识）
    └── 必须与 crash report 中 Binary Image 的 UUID 匹配
        否则地址对不上（版本不一致）
```

**符号化工具链：**

```bash
# 方式 1：atos（Apple 官方，最常用）
atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp -l 0x100a00000 0x100a3f4c8
# 输出：-[ChatViewController sendMessage] (ChatViewController.m:127)

# 方式 2：llvm-dwarfdump（查看 DWARF 结构）
llvm-dwarfdump --lookup=0x3f4c8 MyApp.dSYM

# 方式 3：symbolicatecrash（Apple 脚本，批量处理整个 crash report）
symbolicatecrash crash.ips MyApp.app.dSYM > symbolicated.crash
```

**线上符号化流程（工程实践）：**

```
打包阶段：
  Xcode Archive → 生成 .app + .dSYM
       ↓
  CI 脚本自动上传 dSYM 到符号化服务器（按 Build UUID 索引）
       ↓
崩溃上报阶段：
  SDK 上报 JSON：{instruction_addrs: [...], image_uuid: "xxx", image_base: "0x..."}
       ↓
服务端符号化：
  1. 根据 image_uuid 找到对应的 dSYM
  2. 对每个 addr 计算 offset = addr - image_base
  3. 在 DWARF 中查找 offset → 函数名 + 行号
  4. 存储并展示符号化后的堆栈
```

**常见坑：**
- **dSYM 丢失**：Archive 后未保存，线上崩溃无法符号化 → 必须 CI 自动归档；
- **UUID 不匹配**：重新编译后 UUID 变了，旧版本崩溃无法用新 dSYM 解析；
- **系统库符号缺失**：需要从对应 iOS 版本的设备上提取系统符号文件；
- **Bitcode 重编译**：App Store 开启 Bitcode 后 Apple 会重新编译，dSYM 需从 App Store Connect 下载。

### 补充 Q9：OOM 和 FOOM 的区别是什么？OOM/FOOM 既然没有日志，到底怎么定位？

**答**

**OOM 与 FOOM 的区别：**

| | OOM（Out Of Memory） | FOOM（Foreground OOM） |
|---|---|---|
| **定义** | App 因内存超过系统限制被 Jetsam 杀掉 | OOM 的子集：App **在前台**时因内存被杀 |
| **触发场景** | 前台 or 后台都可能 | 仅在前台（用户正在使用时） |
| **用户感知** | 后台 OOM 用户可能无感，下次打开重新加载 | **用户正在操作时突然闪退**，体验极差 |
| **严重程度** | 后台 OOM 相对可接受 | FOOM 是最严重的稳定性问题之一 |
| **系统机制** | 内核 Jetsam 发送 `SIGKILL` | 同左 |
| **可否捕获** | ❌ SIGKILL 不可被任何进程捕获 | ❌ 同左 |

**简单记忆**：
- **OOM** = 所有因内存被杀的情况（前台 + 后台）
- **FOOM** = 前台 OOM（Foreground OOM），是 OOM 中对用户影响最大的部分
- **BOOM** = 后台 OOM（Background OOM），相对可接受

**为什么特别关注 FOOM**：用户正在使用时突然闪退，等同于崩溃体验；但不会被常规崩溃 SDK 捕获，如果只看崩溃率会遗漏大量稳定性问题。

---

**为什么所有 APM 都捕获不到 OOM：**

```
OOM 的杀进程路径：
  内核 memorystatus_monitor 线程
       ↓
  发送 SIGKILL（不可被任何进程捕获的信号）
       ↓
  进程立即终止，用户态代码零运行机会
  ————————————————————————————
  Firebase / Bugly / Sentry / Matrix
  任何 SDK 的 handler 都没有执行机会
```

---

定位分三个层次，**从「知道有没有」到「知道是哪里」** 逐步深入：

#### 第一层：计数层 — 知道「发生了多少次」

**MetricKit（iOS 14+，苹果官方数据，最准确）**

```swift
// 实现 MXMetricManagerSubscriber，每日收到系统聚合数据
func didReceive(_ payloads: [MXMetricPayload]) {
    for payload in payloads {
        // 前台 OOM 次数（最有价值）
        let fgOOM = payload.applicationExitMetrics?
            .foregroundExitData.cumulativeMemoryResourceLimitCount
        // 后台 OOM 次数
        let bgOOM = payload.applicationExitMetrics?
            .backgroundExitData.cumulativeMemoryResourceLimitCount
    }
}
```

- ✅ 苹果官方数据，不依赖任何 SDK，**最权威**；
- ✅ 适合版本对比：某次改动后 OOM 是否上涨；
- ❌ **每日聚合**，不实时；**没有堆栈**，只有数量。

#### 第二层：归因层 — 知道「是不是 OOM 导致的」

**排除法 FOOM 归因（所有 APM 的共同底层逻辑）**

```
下次启动时，判断上次退出原因：

if 上次在前台（wasForeground == true）
   && 无版本升级（bundle version 相同）
   && 无系统升级（os version 相同）
   && 无捕获到的 crash 记录（crash SDK 未写入报告）
   && 非用户主动退出（applicationWillTerminate 未被调用）
then → 大概率是 FOOM（前台 OOM）
```

**口径宽严的坑：**

```
宽口径（容易误判）：
  只排除 crash + 升级 = FOOM
  → 会把 Watchdog、后台异常唤醒等也算进去，数字虚高

严口径（较准确，Facebook / Matrix 做法）：
  额外排除 Watchdog + 用户强杀 + exit() + 后台态唤醒
  → 数量更少、更可信，适合做趋势分析
```

**关键实现：用 mmap 记录退出状态（不能用 UserDefaults）**

```swift
// UserDefaults 在 OOM 时可能未刷盘，mmap 文件在进程被杀后仍保留
mmapFile.write(.launching)  // App 启动时立即写入

func applicationWillTerminate(_ application: UIApplication) {
    mmapFile.write(.normalExit)  // 正常退出标记
}

// crash SDK 回调中
NSSetUncaughtExceptionHandler { _ in
    mmapFile.write(.crash)  // crash 标记
}

// 首屏完成后
func markLaunchSuccess() {
    mmapFile.write(.success)
}
```

**辅助佐证：**
- `didReceiveMemoryWarning` 是否有记录（进一步支撑是 OOM）；
- 内存水位监控最后一次采样是否超阈值；
- MetricKit OOM 计数同期是否上涨。

#### 第三层：定位层 — 知道「具体哪里用了多少内存」

**先判断是哪种类型**：

```
内存水位曲线形态 → 决定定位方向：

缓慢线性增长 → 内存泄漏（Leak 型）
     └── MLeaksFinder + FBRetainCycleDetector
         Instruments Leaks / Memory Graph
         找循环引用、未释放持有链

突然尖峰暴涨 → 大对象 / 大图（Peak 型）
     └── Xcode Memory Gauge（比 Instruments 更能抓瞬间峰值）
         注释二分法缩小范围
         OOMDetector 堆内存快照

持续高位不降 → 缓存未清理 / 大量对象堆积
     └── Instruments Allocations + Generation Mark
         检查各业务模块缓存上限设置
```

**OOMDetector（腾讯开源）— 定位能力最强的开源方案**

```
工作原理：

1. Hook malloc / free 系列函数
       ↓
2. 每次内存分配时，记录：
   ├── 分配大小
   ├── 当前调用栈（符号化后）
   └── 时间戳
       ↓
3. 按「调用栈聚合」，统计各路径累计分配了多少内存
       ↓
4. 存入本地 mmap 文件（进程被杀后保留）
       ↓
5. 下次启动读取快照，上报 Top N 内存分配调用栈

结果示例：
  [图片解码路径]     累计分配 320MB  ← 大图未降采样
  [列表 cell 路径]   累计分配  85MB
  [WebView 缓存路径] 累计分配  60MB
```

- ✅ 能精确看到哪条代码路径分配了最多内存；
- ✅ mmap 保证进程被杀后数据不丢失；
- ❌ hook malloc 有性能开销，一般**只在灰度包或采样用户中开启**；
- ❌ 图片 ImageBuffer 等不走 malloc 的内存追踪不到。

**内存水位监控实现（配合 mmap 循环缓冲区）**

```swift
// 定时采集 phys_footprint（最贴近 Jetsam 被杀风险的指标）
Timer.scheduledTimer(withTimeInterval: 5.0, repeats: true) { _ in
    var taskInfo = task_vm_info_data_t()
    var count = mach_msg_type_number_t(
        MemoryLayout<task_vm_info>.size / MemoryLayout<integer_t>.size
    )
    withUnsafeMutablePointer(to: &taskInfo) {
        $0.withMemoryRebound(to: integer_t.self, capacity: 1) {
            task_info(mach_task_self_, task_flavor_t(TASK_VM_INFO), $0, &count)
        }
    }
    let footprintMB = Double(taskInfo.phys_footprint) / 1024 / 1024

    // 写入 mmap 循环缓冲区（进程被杀后文件保留，下次启动可读取）
    mmapRingBuffer.write(timestamp: Date(), footprint: footprintMB)

    // 超阈值上报预警
    if footprintMB > warningThreshold {
        APM.report("memory_high_watermark", value: footprintMB)
    }
}
```

#### OOM 完整定位流程总结

```
第 1 步：确认问题存在（计数层）
  MetricKit OOM 计数 → 版本上线后是否上涨？
       ↓ 确认有问题

第 2 步：缩小范围（归因层）
  FOOM 排除法 → 前台 OOM 还是后台 OOM？
  内存水位曲线 → 缓慢增长（泄漏）？还是瞬间尖峰（大图）？
       ↓ 判断类型

第 3 步：精确定位（定位层）
  泄漏型 → MLeaksFinder / Memory Graph / Instruments Leaks
  尖峰型 → Memory Gauge + 注释二分 + OOMDetector 快照
  缓存型 → Allocations Generation Mark + 检查缓存策略

第 4 步：验证修复
  对比 MetricKit OOM 计数前后变化
  对比内存水位曲线峰值
  连续 N 个版本观察 FOOM 率趋势
```

### 补充 Q10：内存优化具体做了什么？

**答**

### 补充 Q11：多线程崩溃怎么复现？

**答**

3. **看崩溃报告所有线程状态**：多个线程同时操作同一数据结构（如都在 `_CFArrayReplaceValues` 里）→ 确认多线程竞争。

### 追问 Q13：iOS 内存和桌面系统最大区别？Dirty / Compressed / Clean 怎么理解？

**答**

**iOS 内存最大特点 — 无 Swap：**
- 使用**虚拟内存**，但 **没有 Swap 到外存**（不能像 macOS/Linux 那样把匿名页换到磁盘）；
- 内存压力上来 → **`didReceiveMemoryWarning`** → 仍不够 → **Jetsam** 按优先级杀进程；
- 看 App 占用用 **`phys_footprint`**（`task_vm_info`），比只看 `vm_size` 更贴近**被杀风险**。

**三种内存页类型：**

| 类型 | 含义 | 系统回收能力 | 举例 |
|------|------|-------------|------|
| **Clean** | 未修改的页，系统可随时回收重建 | ✅ 可回收 | 代码页、mmap 只读映射的文件 |
| **Dirty** | 已修改的页，系统回收代价高 | ❌ 不能直接回收 | 堆分配的对象、全局变量、图片解码 buffer |
| **Compressed** | 不活跃的 Dirty 页被压缩存储 | 部分可回收 | 长时间未访问的对象 |

**Compressed 的隐坑：**
- 当访问被压缩的页时，系统需要**解压**，解压瞬间 footprint 会冲高；
- 大量压缩页同时被访问 → **尖峰 OOM**（页面切回前台时容易触发）；
- 这就是为什么"看起来内存不高但还是被杀"的一种原因。

### 追问 Q14：GCD 里强引用 self 为什么危险？

**答**

```swift
// 危险写法
DispatchQueue.global().async {
    let data = self.loadData()  // block 强持有 self
    DispatchQueue.main.async {
        self.tableView.reloadData()  // 回主线程时 self 可能已释放
    }
}
```

- `DispatchQueue` 本身不 retain `self`，但 **block 强持有 self**；
- 异步执行时若 **VC/对象已释放**（比如用户已 pop 离开），回主线程仍用 self 调 UI → 典型**野指针 / EXC_BAD_ACCESS**；
- 正确做法：`[weak self]` + `guard let self = self else { return }`；
- 注意：这类问题**不会导致循环引用**（队列不持有 self），但会导致**野指针崩溃** — 这是"不泄漏但会崩"的典型场景。

### 追问 Q15：GWPASan / HWASan 是什么？和 ASan 有何区别？

**答**

**三者对比速查：**

| 工具 | 平台 | 开销 | 能否线上 | 检测原理 |
|------|------|------|----------|----------|
| **ASan** | iOS/Android | ~2x 内存/CPU | ❌ 仅 Debug | 编译插桩，全量检查每次内存访问 |
| **GWPASan** | iOS 14.5+ | < 1% | ✅ 灰度常态 | 低概率采样 guard page |
| **HWASan** | Android ARMv8.5 | ~15% | ✅ 灰度阶段 | 硬件 TBI tag 校验 |

**GWPASan 关键点（iOS 面试重点）：**
- Apple 在 iOS 14.5+ 引入，**不需要编译插桩**，系统层面支持；
- 原理：以**低概率（约 1/1000）** 对 malloc 的内存块加「guard page」保护；
- 访问已释放内存时触发 `EXC_GUARD`，崩溃报告附带**分配栈和释放栈**；
- 性能开销极低（< 1%），可以在灰度用户中**常态化开启**；
- 相当于"**线上 Zombie 的低成本替代品**"。

**ASan（线下用）：**
- 编译器插桩，每次内存访问都插入检查；
- 能检测：堆溢出、栈溢出、UAF（Use-After-Free）、double-free；
- 致命缺点：内存开销 2～3 倍，CPU 开销 ~2x，**完全不能上线**。

### 追问 Q16：崩溃聚合算法是怎么做的？（Stack Hash 去重）

**答**

线上同一个 bug 可能产生**数千条不同的原始报告**（ASLR 不同、递归深度不同），必须做聚合。

**Stack Hash 算法：**

```
Step 1：符号化（地址 → 函数名）
  └── 必须先符号化，否则 ASLR 导致同一 bug 地址完全不同

Step 2：清洗堆栈
  ├── 去掉系统库通用帧（libdispatch, CoreFoundation 底层）
  ├── 去掉崩溃捕获框架自身的帧（KSCrash 内部帧）
  └── 只保留「最能代表 bug 位置」的关键帧（通常 Top 3～5 帧）

Step 3：计算 Hash
  ├── 对清洗后的「函数名 + 文件名」拼接字符串
  └── 取 MD5 / MurmurHash → 作为该崩溃的 Issue ID

Step 4：聚合
  └── 相同 Hash → 同一个 Issue，累加 count 和影响用户数
```

**关键取舍：**
- **行号要不要参与 Hash**：参与更精确，但代码改一行就裂成两个 Issue → 大多数平台**函数名参与、行号只做展示**；
- **递归崩溃去重**：连续相同帧折叠（只保留一层），避免 hash 不稳定；
- **相似度聚合**（进阶）：Sentry 用编辑距离做相似度，超阈值归并同一 Issue。

### 追问 Q17：启动保护是怎么做的？如何防止崩溃 loop？

**答**

**崩溃 loop** = App 每次启动都在同一个地方崩溃，用户完全无法使用。

**触发场景：**
- 本地缓存/数据库数据损坏，启动时读取崩溃；
- 启动期 SDK 崩溃，阻断整个启动链路；
- 版本升级后数据格式不兼容。

**启动保护核心机制：**

```
App 启动
   ↓
读取上次启动状态（mmap 文件，不是 UserDefaults）
   ├── 上次正常完成启动 → 清零计数，正常流程
   └── 上次未完成启动（crash/被杀）
          ↓
       连续崩溃计数 +1
          ├── 计数 < 3 → 正常启动，继续观察
          └── 计数 ≥ 3 → 进入保护模式
```

**保护模式分级自救：**

```
Level 1（轻度）：清除可疑缓存（图片缓存、列表缓存、SQLite WAL）
Level 2（中度）：重置用户配置 + Feature Flag 全部关闭
Level 3（重度）：清除 Documents/Library/Caches，保留登录态
Level 4（兜底）：强制更新提示 / 客服入口
```

**关键实现要点：**
- 用 **mmap 文件**记录启动状态（UserDefaults 在崩溃时可能未刷盘）；
- 标记"启动成功"的时机：**`applicationDidBecomeActive` 或首屏渲染完成后**；
- 进入保护模式时**必须上报事件**，方便线上监控发现问题。

### 追问 Q18：长效防劣化机制怎么建？

**答**

分三个层面：

**① 流水线卡口（事前预防）**

```

  └── SwiftLint：禁止 force unwrap、禁止主线程同步等待
```

### 追问 Q19：图片内存怎么控？imageNamed vs imageWithContentsOfFile？

**答**

- 图片解码后内存 ≈ **宽 × 高 × 4** 字节（RGBA）；一张 4000x3000 的图片 = **48MB**；
- 应按**显示尺寸** downsample（`ImageIO` 的 `CGImageSourceCreateThumbnailAtIndex`）。

**两种加载方式对比：**

| 方式 | 缓存 | 适用场景 |
|------|------|----------|
| `imageNamed:` | 系统级内存缓存，不会主动释放 | 小图、频繁使用的 icon |
| `imageWithContentsOfFile:` | 不缓存，用完即释放 | 大图、一次性使用的引导页/背景图 |

**远程大图注意：**
- SDWebImage 等默认会进内存缓存 → 大图列表页内存暴涨；
- 配合**降采样 + 解码在子线程 + 内存缓存设上限**。

### 追问 Q20：WKWebView 白屏/内存问题怎么处理？

**答**

- WKWebView 的网页内容跑在**独立的 WebContent 进程**中；
- 当系统内存紧张时，会优先杀掉 WebContent 进程 → WebView **白屏**；
- 处理方式：实现 `webViewWebContentProcessDidTerminate:` 回调，在里面 **reload**；
- WebContent 进程被杀后，主进程仍然存活，下次显示时 reload 即可恢复。

### 追问 Q22：内存泄漏的具体业务案例？

**答**

**案例 1：scroll 回调中反复 setImage**
- 现象：快速滑动列表时内存持续上涨；
- 原因：`scrollViewDidScroll:` 每次触发都重新 decode 图片，高频调用导致大量临时解码 buffer；
- 解决：加标志位，只在首次 / 可见时执行一次 `setImage`。

**案例 2：NSMutableAttributedString 巨大临时 rect**
- 现象：Memory Gauge 捕获到瞬间内存尖峰（几百 MB）；
- 原因：某个属性未设置宽度约束，计算 boundingRect 时生成了巨大的临时矩形；
- 定位方式：Instruments 跟不上瞬间尖峰，用 Memory Gauge + **注释二分法**缩小范围；
- 解决：补充宽度约束。

**案例 3：进出语音房内存只涨不降**
- 现象：多次进出语音房后，内存从 120MB 涨到 300MB+；
- 原因 1：RTC SDK 的音频 buffer 缓存未在退房时释放；
- 原因 2：房间内头像图片用 `imageNamed:` 加载，系统缓存不释放；
- 解决：退房时手动调用 RTC cleanup + 头像改用 `imageWithContentsOfFile:` + 退房后 `UIImage` 缓存清理。
