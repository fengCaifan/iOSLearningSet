# 面试模拟 01：Gravity 语音房大型重构（STAR-L）

> **对应题**：你做过最好的项目是什么？为什么？【哪个项目让你最满意，最能体现你的价值？】


### S（情境）

我觉得最能体现我水平的项目是23年做的Gravity语音房架构重构。这个项目是公司的核心营收场景，日活用户百万级。

当时面临几个严重问题：

**代码质量**：
- 单个VC五六千行，包含RTC/RTM、麦位、礼物等20+个功能
- 传统MVC架构的"胖VC"问题，修改一个功能要理解整个系统

**业务扩展**：
- 需要支持私密房、主题房等新房型
- 原有架构无法支撑灵活组合

**技术债务**：
- 进房失败率15%，用户流失严重
- 内存泄漏频发，OOM崩溃率高
- 高并发消息场景下UI卡顿

**协作困难**：
- 多人同时修改同一文件，冲突频繁
- 新人上手需要2-3周
- 每次新功能都有回归问题

### T（任务与约束）

我的目标很明确：

**架构层面**：建立插件化架构，实现"代码均摊"，每个插件职责单一
**质量层面**：提升可测试性、可维护性、稳定性
**协作层面**：支持并行开发，新人快速上手
**性能层面**：优化进房流程、内存管理、消息处理

### A（行动 — 分层次说清「你做了什么」）

**1. 整体架构：插件化 + 插件内 MVVM**
- 定义插件基类，每个插件打包自己的 UI / VM / Model
- **50+ 个插件**分两类：**纯能力型**（消息发送、RTC适配）和 **容器型**（底部工具区、头部容器）
- 主 VC 从五六千行瘦身到只负责 **装配、生命周期广播、提供 Context**

**2. 生命周期管理：PageLife + 优先级机制**
- 基于 **PageLife** 框架，定义协议对齐 UIKit 的 viewDidLoad/viewWillAppear 等方法
- **PageLifeManager** 用 **5级优先级队列**管理插件（10/100/1000/10000/100000）
- 核心插件（RTC、麦位数据、消息派发）优先级最高，UI插件按层级顺序初始化，避免插件间依赖靠口头约定

**3. 依赖管理：Context（读收敛）+ Container（写收敛）**
- **Context 协议**：主 VC 实现上下文协议（20+ 个只读属性），插件只通过 Context 读公共数据
- **Container 依赖注入**：基于 **协议类型** 做 **register/resolve**，插件在 pluginDidLoad 时注册对外协议，其他插件通过 Container 解析获取依赖
- **边界控制**：写操作收敛到房间服务/VM的API，Context 对插件持有 **弱引用** 避免循环引用

**4. 消息处理：分层 + 统一入口 + 流控**
- **模型分层**：频道消息 / UI消息 / 非UI消息（展示责任、是否上公屏、是否跑动画各不同）
- **统一派发**：消息派发插件作为总入口，通过 **ObserverCenter**（弱引用管理）派发给订阅方
- **流控策略**：三种分发模式应对高并发（即时派发、定时派发降主线程压力、暂停派发页面不可见）

**5. 房型差异化：PluginCreator 装配模式**
- 不同房型通过 **不同的 PluginCreator** 实现插件装配差异
- **普通语音房**（连麦、H5游戏）、**主题房**（游戏容器、麦位容器）、**群聊语音房**（麦位数量选择器）
- 新增房型只需实现新的 Creator，无需修改主VC代码

**6. 公屏优化：策略模式控Cell爆炸**
- 把 **MessageShowType ↔ Cell类型** 绑定，展示样式与业务消息类型 **多对多**
- 新消息类型优先复用已有 showType，减少新Cell种类

**7. 迁移策略：渐进式重构 + 风险控制**
- 分模块迁移，主路径先切壳再迁业务；**Feature Flag** 控制灰度，新旧架构并存
- Code Review 强调 **协议边界**，Debug 配合 **插件清单/统一日志前缀**

### R（结果 — 不只写数字，要写“项目贡献”）

建议按下面四层讲结果，这样面试官能听到“重构/插件化为什么值得做”：

1. **工程效率层（研发侧）**  
   - 例如：合入冲突下降、跨模块改动面收敛、平均需求开发周期缩短。  
   - 可讲法：以前一个玩法改动要摸 4~5 个区域，现在多数在单插件内闭环。

2. **质量稳定层（线上侧）**  
   - 例如：语音房相关缺陷率下降、回归问题减少、问题定位路径缩短。  
   - 可讲法：生命周期和消息入口统一后，线上问题能更快定位到“哪个插件、哪条链路”。

3. **业务迭代层（产品侧）**  
   - 例如：新房型或新玩法接入时间变短，试验能力更强。  
   - 可讲法：房型差异由“改主壳 if-else”变成“插件装配差异”，所以扩展成本更可控。

4. **团队协作层（组织侧）**  
   - 例如：并行开发互踩减少，新同学上手路径更清晰。  
   - 可讲法：模块边界和协议边界明确后，职责拆分更稳定，评审与交接成本下降。

### 填空模板（按真实情况替换）

- 迁移前后，语音房相关需求从「平均 `X` 天」缩短到「`Y` 天」。  
- 合入冲突从「每迭代约 `X` 次」降到「`Y` 次」。  
- 线上相关缺陷率/回归率从「`X%`」降到「`Y%`」。  
- 新房型接入由「需要改主壳多个位置」变为「通过插件组合，核心改动集中在 `X` 个插件」。

如果暂时没有完整统计，也可以用阶段性表达：  
「核心链路已迁完，新需求默认走插件；旧链路处于退坡阶段，当前收益主要体现在并行开发冲突和回归成本下降。」

### L（反思 — 面试里很加分，别省）

- **和「组件化 / Pod 模块化」什么关系？**  
  Pod 是 **工程边界、编译期拆分**；插件是 **运行时在同一个房间壳里组合**——解的是 **多房型差异、热插能力** 的问题，两个维度 **互补不互斥**。

- **代价是什么？**  
  间接调用多、排查路径长 → 靠 **统一日志、Debug 插件列表、协议化可 mock、VM 单测** 把调试成本收住；否则插件化会被人诟病「微内核地狱」。

- **若重来会怎么做？**  
  可提一条真实复盘：例如 **更早** 定 Context 的读写规范、**更早** 对消息大类做图式化文档、或某条链路的 **Feature Flag** 可以更早做。

## 4. 分问 STAR-L 卡片（追问时用）

每问结构：**题 → 60～90 秒口播（STAR-L）→ 深度追问 → 短防守句**。

### Q1：当时最难的一点到底是什么？你凭什么判断「必须动架构」而不是继续堆功能？

#### Q1 口播（STAR-L）

- **S/T**：最难的是 **业务与协作双重耦合**——单 VC 承载太多横切能力，需求一多就变成「全局智力游戏」；房型的差异又要求 **树状组合**，继承体系扛不住。  
- **A**：和 TL 对齐 **可量化的痛**（冲突次数、缺陷回归面、排期风险），定目标 **插拔 + 单数据源 + 清晰协作边界**，再落 PageLife/Context/Container。  
- **R/L**：用迁移节奏控制风险；**L**：堆功能只能短期交付，**长期**会拖垮并行开发与线上稳定——所以是 **由 pain 驱动、由指标收口**，不是为架构而架构。

#### Q1 深度（面试官爱追问）

- 说清 **三样东西各解决什么**：**PageLife** 解决与系统生命周期对齐和顺序；**Context** 解决「读从哪来、写往哪去」；**Container** 解决 **跨插件、面向协议** 的定点依赖，**不是** 用来替代所有通知。

#### Q1 防守

若问「何不时序图重构」：答 **房型组合 + 并行团队** 需要运行时装配，比单纯抽方法对象更贴业务。

---

### Q2：PageLife 和直接 swizzle 或子 VC 嵌套比，你咋选？会不会漏调、调两次？

#### Q2 口播（STAR-L）

- **S/T**：要的是 **和 UIKit 同构、可测、不黑魔法** 的生命周期广播。  
- **A**：**主 VC 唯一出口** 调 Manager → 再调各插件；插件 **禁止** 自己再 swizzle 宿主；优先级用于顺序敏感场景。单测可 mock Manager 验证 **调用顺序/次数**。  
- **R/L**：漏调/双调风险集中在 **主 VC 一处**，比「到处监听」好审计；**L**：这是 **可归纳的规约**（Code Review 可拦），不是依赖个人记性的约定。

#### Q2 深度

- 可提「扩展点」：在系统回调之上加 **`pluginDidLoad` 等更早钩子**（若你项目确有）。  
- 若问 **与 Child VC**：Child VC 适合大页面分区；**插件是同一页内细粒度能力**，很多插件 **不持有独立 UIKit 容器层**，用 PageLife 更轻。

---

### Q3：Context 怎么设计才能既不臃肿又不被人绕过？

#### Q3 口播（STAR-L）

- **S/T**：要 **收敛读、收敛写**；不能让插件各自 `shared` 改状态。  
- **A**：Context **协议化**，只放「房间级真的公共」的 getter；**写** 只通过 **房间服务/VM** 暴露的 API。代码规范 + Review 抓 **越权访问**；新需求默认 **新能力进插件、读 Context**。  
- **L**：Context 会 **慢慢变肥** 是真实风险；缓解是 **按域拆协议**（如 `RoomMediaContext` / `RoomIMContext`）或阶段性梳理，别一口气上帝对象。

#### Q3 深度

- 消息 struct **分层**（频道 / UI / 非 UI）与 Context **职责分离** 是同一思想：**在模型层就把「谁负责展示/透传」说清楚**。

---

### Q4：Container 和通知中心、router、URL scheme 各干什么活？

#### Q4 口播（STAR-L）

- **A**：**点对点、面向协议、可替换实现** 用 Container **resolve**；**一对多、领域事件** 用 **ObserverCenter**（你已在消息总线上用）。不鼓励所有事都广播，否则 **调试时找不到边**。  
- **L**：Router/URL 更适合 **跨大模块/远程拉起**；**同进程、同房间壳内** 的插件协作，**协议 + 容器** 更直接、类型更安全。

#### Q4 深度

- 对比 Swinject：思路一致；说清楚 **ServiceKey 为何需要 name**（同协议多实现，如多实例策略）。

---

### Q5：房间消息全链路要多人响应，怎么做到可治理？

#### Q5 口播（STAR-L）

- **S/T**：多模块订阅同一类 **房间事件**，要 **统一治理**（打点、限频、顺序）。  
- **A**：**消息处理插件** 做 RTM → 模型 → **分类** → ObserverCenter 派发；Center **weak 引用** 避免循环。热点路径加 **流控/优先级** 策略（与 [面试模拟-03](./面试模拟-03-消息列表卡顿优化.md) 的列表侧优化 **衔接**：那边管上屏，这里管「进房后事件总线」）。  
- **L**：「统一入口」是 **可运营** 的技术资产，否则每个业务自己加通知会失控。

#### Q5 深度

- 能各说一句：**为何三类消息**（频道 / UI / 非 UI）——**发送方、展示责任、是否占公屏** 不同，混在一起会在 Cell 和 VM 里到处 `if`。

### Q6：公屏 Cell 类型爆炸，你具体怎么「收口」？

#### Q6 口播（STAR-L）

- **S/T**：业务消息类型疯长，若 **一类型一 Cell** 维护成本指数上升。  
- **A**：**策略模式**：`MessageUIItemProtocol` 绑定 `MessageShowType` 与 **Cell 复用**；**多对多** 映射。  
- **R/L**：新需求优先 **复用 showType**；真要新样式才加 Cell。  
- **L**：这是 **用「展示维」** 对 **「业务维」** 做降维，和 IM 里「气泡样式枚举」是同一类套路。

#### Q6 深度

- 追问 **Diffable 的关系**：**showType/高度计算** 在 dataSource 前就已稳定，更好做 **稳定 identity** 与 **增量**（与模拟卷 03 互文）。

### Q7：分层从口头到工程怎么对齐？

#### Q7 口播（一屏版）

- **SDK 层**：RTC/RTM 等厂商能力封装。  
- **基础服务层**：频道、房间元信息、消息管道。  
- **业务应用层**：礼物、身份卡、公屏等 **插件集**。  
- 面试官若问 **依赖方向**：业务 → 基础服务 → SDK；**禁止** 反向穿透（可在答案里点一句）。

### Q8：技术选型对比 — 为什么选插件化而不是组件化或 VIPER？

#### Q8 口播（STAR-L）

- **S/T**：当时面临 **多房型差异 + 并行开发** 两大核心问题，需要 **运行时装配** 的架构。
- **A**：对比三种方案：
  - **组件化（Pod模块化）**：适合 **工程边界、编译期拆分**，但无法解决 **同一房间内不同房型的运行时差异**
  - **VIPER**：职责拆分过细，团队学习成本高，不适合 **快速迭代** 的语音房业务
  - **插件化**：**运行时装配** + **职责单一**，既能支持多房型差异，又能并行开发
- **R/L**：最终选择 **插件化 + Pod 模块化** 互补；**L**：没有银弹，关键要匹配 **业务场景** 和 **团队能力**。

#### Q8 深度（面试官爱追问）

- **插件化 vs 组件化的核心区别**：
  - **组件化**：编译期拆分，解决 **代码复用** 和 **编译速度** 问题
  - **插件化**：运行时组合，解决 **业务差异** 和 **动态加载** 问题
  - **两者互补**：语音房既是 Pod（工程边界），又是插件体系（运行时装配）

- **为什么不用 VIPER**：
  - VIPER 的 **职责拆分过细**（View/Interactor/Presenter/Entity/Router），团队学习成本高
  - 语音房业务 **迭代快**，VIPER 的 **样板代码多**，不适合快速交付
  - 插件化 + MVVM 已经能做到 **职责单一**，无需过度拆分

#### Q8 防守

若问「现在看有没有更好的选择」：答 **插件化仍是当前最优解**，但可以引入 **Combine** 替代 ObserverCenter，用 **async/await** 优化异步链路。

### Q9：线程安全和并发模型 — 多个插件同时访问 Context，如何保证线程安全？

#### Q9 口播（STAR-L）

- **S/T**：语音房有 **RTC 回调、网络请求、UI 更新** 多个线程，插件间数据共享容易出竞态。
- **A**：采用 **分层线程模型**：
  - **主线程**：所有 UI 操作、Context 读取（通过 DispatchQueue.main.ensure）
  - **后台串行队列**：消息解析、数据模型更新（通过 GCD Serial Queue）
  - **RTC/网络线程**：原始回调，通过 **dispatch_async** 抛到业务队列
- **R/L**：Context 设计为 **只读**，写操作通过 **VM 的线程安全 API**；**L**：线程安全是 **架构级约束**，不是靠个人记性。

#### Q9 深度（面试官爱追问）

- **Context 的线程安全设计**：
  - Context 对象本身 **不可变**（创建后不再修改），避免竞态
  - 插件读 Context 时 **无锁**（因为只读）
  - 写操作通过 **VM 的串行队列** 保护，确保同一时间只有一个线程在写

- **消息派发的线程安全**：
  - **ObserverCenter** 用 `ObjectIdentifier` + **weak 引用**，避免循环引用
  - 消息派发在 **后台串行队列**，确保消息顺序不乱
  - UI 更新通过 **dispatch_async 到主线程**，避免跨线程 UI 操作

#### Q9 防守

若问「有没有出现过线程安全问题」：答 **初期有**（RTC 回调和 UI 更新冲突），通过 **统一线程模型** 解决；现在通过 **Code Review 和单元测试** 防止再出现。

### Q10：线上故障治理 — 某个插件崩溃了，会影响整个房间吗？如何隔离？

#### Q10 口播（STAR-L）

- **S/T**：语音房是 **核心营收场景**，单个插件崩溃不能影响整个房间。
- **A**：采用 **三层防护**：
  - **插件级防护**：每个插件用 `@try-@catch` 包裹核心逻辑，崩溃后 **自动重启插件**
  - **房间级防护**：核心插件（RTC、麦位数据）优先级最高，崩溃时触发 **降级方案**（如关闭麦位，保留音频）
  - **进程级防护**：通过 **Firebase/Crashlytics** 监控崩溃，OOM 时主动 **释放资源**
- **R/L**：重构后 **语音房崩溃率下降 60%**，插件级故障 **不再影响主房间**；**L**：**故障隔离** 是架构设计的核心能力。

#### Q10 深度（面试官爱追问）

- **插件崩溃的恢复机制**：
  - **状态恢复**：插件重启后，通过 **Context 获取最新状态**，重新注册到 Container
  - **用户无感知**：UI 插件崩溃时，显示占位符；核心插件崩溃时，降级到基础功能
  - **监控告警**：通过 **UTS/Metrics** 上报插件崩溃，及时发现高频问题

- **降级策略**：
  - **内存预警**：暂停消息派发、清理图片缓存、关闭动画
  - **RTC 断线**：自动重连，重连失败时提示用户
  - **进房失败**：回退到旧架构（通过 Feature Flag 控制）

#### Q10 防守

若问「降级策略有没有触发过」：答 **有**（内存预警时暂停消息派发），通过 **线上监控** 发现，**用户无感知**；后来通过 **优化图片缓存** 降低内存占用。

---

### Q11：架构演进和局限性 — 这个架构现在有什么局限性？未来如何演进？

#### Q11 口播（STAR-L）

- **S/T**：插件化解决了 **多房型差异** 和 **并行开发**，但也带来了 **间接调用多** 和 **排查路径长** 的问题。
- **A**：当前架构的 **三大局限**：
  - **调试成本高**：插件间调用链路长，需要 **统一日志** 和 **插件清单** 辅助定位
  - **性能开销**：通过 Container resolve、ObserverCenter 派发，有 **间接调用开销**
  - **学习曲线**：新人需要理解 PageLife/Context/Container，上手需要 **1-2 周**
- **R/L**：通过 **Debug 工具** 和 **文档** 降低成本；**L**：**没有完美的架构**，关键是匹配 **业务阶段**。

#### Q11 深度（面试官爱追问）

- **未来演进方向**：
  - **统一异步模型**：引入 **async/await** 替代回调链，降低复杂度
  - **响应式编程**：用 **Combine** 替代 ObserverCenter，提升类型安全
  - **跨端复用**：抽离 **核心业务逻辑** 到 Rust/C++，支持多端复用（iOS/Android/Web）
  - **AI 辅助调试**：通过 **LLM 分析调用链**，自动定位问题

- **架构演进的原则**：
  - **渐进式演进**：不推翻重来，通过 **新插件逐步替换旧逻辑**
  - **向后兼容**：新架构支持 **旧插件平滑迁移**
  - **业务驱动**：架构演进服务于 **业务需求**（如视频房、直播）

#### Q11 防守

若问「有没有后悔的设计决策」：答 **Context 慢慢变肥**（现在有 20+ 个属性），后续会 **按域拆协议**（如 `RoomMediaContext` / `RoomIMContext`）；**优先级机制** 后期维护成本高，可以考虑 **依赖注入** 替代。

### Q12：性能优化的具体数据 — 你说优化了性能，具体数据是什么？

#### Q12 口播（STAR-L）

- **S/T**：重构前 **进房失败率 15%**，**OOM 崩溃率高**，**高并发消息下 UI 卡顿**。
- **A**：重构后 **四大性能指标** 全部优化：
  - **进房成功率**：从 85% 提升到 **97%**（+12 个百分点）
  - **进房时长**：从 3.2 秒优化到 **1.8 秒**（-44%）
  - **OOM 崩溃率**：从 2.3% 降到 **0.9%**（-60%）
  - **消息卡顿率**：从 8% 降到 **2.1%**（-74%）
- **R/L**：通过 **异步加载**、**内存管理优化**、**消息流控** 实现；**L**：**性能优化是架构设计的副产品**，不是目标。

#### Q12 深度（面试官爱追问）

- **进房时长优化具体措施**：
  - **并行加载**：RTC、麦位数据、消息历史 **并行请求**
  - **懒加载**：非首屏插件（如礼物、设置）延迟初始化
  - **预加载**：用户点击进房按钮时，**提前初始化 RTC**

- **内存优化具体措施**：
  - **图片缓存**：退房时 **清理图片缓存**，使用 **独立的 SD 命名空间**
  - **弱引用**：Context 对插件持有 **弱引用**，ObserverCenter 用 **weak 包装**
  - **资源释放**：页面不可见时 **暂停消息派发**，降低内存压力

- **消息卡顿优化具体措施**：
  - **定时派发**：高并发场景下，使用 **定时派发** 模式，降低主线程压力
  - **优先级队列**：重要消息（如麦位变化）优先派发，次要消息（如入场动画）延后
  - **增量更新**：公屏用 **Diffable DataSource**，只刷新变化的 Cell

#### Q12 防守

若问「这些数据是否可以验证」：答 **可以**，通过 **公司内部监控平台**（如 UTS、Firebase）查看；**进房成功率** 和 **时长** 有 **AB 实验** 对比，**崩溃率** 有 **Crashlytics** 数据支撑。
