# 面试模拟 05：AI 认知与使用实践

> 对应整理题：**「你在工作中怎么用 AI？」「AI 对你的开发效率有什么影响？」「你们项目中有 AI 相关功能吗？」**  
> 技术主线：**日常研发 AI 使用 → 工程化落地（Rules/Skills/MCP） → 产品侧 AI 功能 → 方法论与边界认知**

---

## 主线回答（STAR）

### S — Situation（背景）

> "我们项目 Gravity 从 23 年开始就在两个维度上引入了 AI：一是**研发侧**，用 AI 工具提升日常开发效率；二是**产品侧**，在 IM、虚拟人、内容创作等场景为用户提供 AI 能力。我作为 iOS 负责人，主导了研发侧 AI 工具链的搭建，同时也参与了产品侧 AI 功能的端侧实现。"

---

### T — Task（任务）

> "研发侧的目标是：让 AI 在不降低代码质量的前提下，减少重复性工作、加速需求交付。产品侧的目标是：在端侧做好场景编排、参数组装和交互展示，配合后端完成 AI 能力的闭环。"

---

### A — Action（行动）

> "具体分三个层面：

#### 1. 日常开发中的 AI 使用

我日常使用 AI 辅助开发主要覆盖以下场景：

| 场景 | 具体用法 | 注意事项 |
|------|----------|----------|
| **读代码 / 查接口** | 快速定位模块、理解调用链、对照服务端接口契约 | 结论以仓库代码和接口文档为准 |
| **方案设计与拆解** | 需求拆任务、边界条件列举、技术方案评审清单 | 方案需人工取舍，上线口径需业务确认 |
| **样板代码生成** | Model 层、网络请求层、UI 骨架、单测思路 | 必须通过 SwiftLint 和项目规范校验 |
| **文档与复盘** | 会议纪要整理、迭代总结草稿、面试准备文档 | 事实需与 Git/工单核对 |

#### 2. 工程化的 AI 工具链（Cursor + OpenSpec）

我们在项目中搭建了一套完整的 AI 辅助研发工具链：

**① Cursor Rules（`.cursor/rules/`）—— 约束 AI 输出质量**

通过规则文件约束 AI 的代码生成行为：
- 语言规范（Swift 风格、命名约定）
- SwiftLint 规则对齐
- 模块分层结构约束
- 网络层与 Model 规范
- 本地化、H5、CR 标准等

> 核心价值：**减少"AI 生成的代码不符合项目规范"的问题**，让 AI 的输出开箱即用。

**② Cursor Skills（`.cursor/skills/`）—— 面向任务的流程模板**

针对高频开发任务预置了 Skill：
- `@model` — Model 层代码生成
- `@api` — 网络接口对接
- `@ui` — UI 组件骨架
- `@figma` — 设计稿还原
- `@l10n` — 国际化文案
- `@track` — 埋点方案
- `@cr` — Code Review 检查清单
- `@cache` — 缓存方案
- `@h5` — H5 容器对接
- `xcode-build-check` — 修改代码后的编译校验流程

> 核心价值：**一次定义，反复使用**。新人 onboard 后按 Skill 操作即可输出符合规范的代码。

**③ OpenSpec 工作流 —— 全链路文档驱动**

配合 OpenSpec 做「提案 → 设计 → 任务 → 规格 → 实现 → 归档」：
- 每一步都有明确上下文，AI 辅助时不会丢失背景信息；
- Commands 快捷指令：`opsx-propose`（提案）、`opsx-apply`（实现）等。

**④ MCP 外部工具集成**
- **iAPI MCP**：直接在 IDE 中检索后端接口定义（免切换浏览器查文档）；
- **Figma MCP**：设计稿读取，辅助 UI 还原。

**⑤ IterationCoach（可选）**
- 收集 Git diff/log，结合 LLM 生成迭代复盘报告；
- 支持 OpenAI API 或 Cursor 原生能力两种模式。

#### 3. 产品侧 AI 功能的端侧实现

我们 App 内面向用户的 AI 功能，**架构统一原则**是：端侧负责场景入口、参数组装、展示与埋点；**核心生成能力在后端**。

| 功能模块 | 端侧职责 | 后端能力 |
|----------|----------|----------|
| **IM 助聊（破冰/话术优化）** | 面板交互、话题选择、消息展示 | GPT 生成 + 预制文案 |
| **Plato/AiGuru 虚拟人** | 激活流程、资料展示、脚本菜单 | 人设管理、对话生成、等级系统 |
| **星球 AI 帮写** | 写作配置获取、标签选择、结果展示 | 文案生成 |
| **IM 内 AI 插件** | 消息卡片、推荐面板、玩法入口 | 推荐算法、脚本引擎 |

---

### R — Result（结果）

> "研发侧：通过 Rules + Skills，新需求的样板代码编写时间减少约 40%~50%，Code Review 中的规范问题显著减少。文档和复盘效率提升明显。  
> 产品侧：AI 助聊上线后用户消息发送率提升，破冰场景的首条消息发送时间缩短。虚拟人模块的用户留存有正向影响。"

## 深挖问题

---

### 深挖 Q1：你用 AI 生成代码时，怎么保证质量？

**答**

> "我们有三层保障：

**① 规则前置（Rules）**
- AI 生成代码时自动遵循项目的 SwiftLint 规则、命名约定、分层规范；
- 避免了"生成后还要大量调整格式和结构"的问题。

**② 流程约束（Skills）**
- 每个 Skill 预置了输入/输出模板，比如 `@api` 会按照项目的网络层规范生成 TargetType + Model + ViewModel；
- 不是"随意问随意答"，而是有结构化的协作流程。

**③ 人工兜底**
- 生成的代码必须通过 `xcode-build-check`（编译校验）；
- 合并前必须自测 + Code Review；
- 对于复杂逻辑（并发、内存管理、加密等），AI 只做辅助参考，实现以人工为主。

**底线原则：**
- 敏感数据（用户信息、密钥、业务逻辑细节）不外传给第三方 AI；
- AI 的输出是**草稿**，不是**最终产出** — 人的判断始终是最后一道关。"

---

### 深挖 Q2：Cursor Rules 和 Skills 具体怎么设计的？

**答**

**Rules 设计思路 —— 约束 AI 的"默认行为"：**

```
举例：rule-swift.mdc
├── 命名：驼峰、前缀约定（TP 开头）
├── 文件组织：按 MVVM 分层
├── 禁止事项：禁止 force unwrap、禁止中文注释混入代码
├── 网络层：必须用 TargetType 协议、Response 必须 Codable
└── 本地化：字符串必须走 L10n 枚举
```

**Skills 设计思路 —— 模板化高频任务：**

```
举例：skill-api（对接一个新接口）
输入：接口文档 URL 或 JSON 描述
输出模板：
  1. Path 枚举定义（TPUrlPaths+XXX.swift）
  2. Request Model（参数结构体）
  3. Response Model（Codable）
  4. TargetType 实现
  5. ViewModel 调用示例
  6. 埋点 key 建议

触发方式：在 Cursor 中输入 @api + 接口描述
```

> "本质上是把**团队的编码经验和项目规范**编码成了 AI 可理解的规则，让 AI 成为一个'懂项目规范的初级开发者'。"

### 深挖 Q3：产品侧 AI 功能，端侧架构是怎么设计的？

**答**

> "我们遵循一个统一原则：**端侧做编排，后端做智能**。

**端侧职责清单：**
1. **场景入口管理**：什么时机、什么位置展示 AI 功能入口（如聊天输入框上方、长按气泡）；
2. **参数组装**：将当前上下文（对话对象、关键词、用户类型等）打包成请求参数；
3. **结果展示与交互**：加载态、结果渲染、重新生成、一键发送；
4. **埋点**：AI 功能的曝光、点击、使用、效果追踪。

**不在端侧做的事：**
- 不做本地模型推理（成本和效果都不如后端）；
- 不做 Prompt 管理（全部后端控制，方便 A/B 和迭代）；
- 不缓存 AI 生成结果（时效性和个性化由后端保证）。

**架构示意（以 IM 助聊为例）：**

```
用户点击"AI 帮写" → 端侧组装参数（会话 ID、对象信息、关键词）
       ↓
POST gravity/im/assistChatting → 后端 LLM 生成
       ↓
端侧收到结果 → 展示在面板 → 用户选择发送/重新生成
       ↓
埋点上报（功能使用率、发送转化率）
```

### 深挖 Q4：AI 的使用边界和风险你怎么看？

**答**

> "我对 AI 的认知是：**它是一个能力极强但不可全信的协作者**。具体来说：

**能力边界：**
- ✅ **擅长**：模式化代码生成、信息检索与整合、文档草稿、方案枚举；
- ⚠️ **有限**：复杂架构决策、边界条件遗漏、性能敏感代码、安全相关逻辑；
- ❌ **不能**：替代人的判断力、承担代码质量责任、处理未公开的业务知识。

**风险管控：**
1. **数据安全**：敏感代码和用户数据不外传；内部代码用自托管或企业版；
2. **质量风险**：AI 输出必须经过编译、自测、CR 三重验证；
3. **依赖风险**：不能形成"离了 AI 就不会写代码"的依赖；核心能力（架构设计、系统思考、调试定位）仍需人自己具备；
4. **合规风险**：产品侧 AI 功能的文案、生成内容需过合规审核。

**我的使用原则：**
> AI 帮我**提速**，但不帮我**思考**。它是我的**副驾驶**，不是**驾驶员**。"

---

## 一页纸总结（面试快速复述版）

1. **日常研发**：用 AI 做检索、拆解、样板代码与文档草稿；输出必须经过规范校验（SwiftLint/自测）与人工把关，敏感数据不外泄。

2. **工程化落地**：通过 **Cursor Rules & Skills** 将团队规范编码给 AI、**OpenSpec** 做全链路文档驱动、**MCP** 集成后端接口和设计稿，形成闭环提效。

3. **产品 AI 功能**：面向用户的 AI 能力集中在 **IM 助聊**、**Plato/AiGuru 虚拟人**、**发帖 AI 帮写** 及会话插件；**端侧以编排与展示为主，核心生成能力在后端**。

4. **方法论**：AI 是副驾驶不是驾驶员；**规则前置 → 流程约束 → 人工兜底**三层保障质量；核心能力（架构、调试、系统思考）不可外包给 AI。
