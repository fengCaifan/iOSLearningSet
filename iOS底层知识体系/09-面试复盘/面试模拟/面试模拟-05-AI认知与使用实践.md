## 📐 AI Agent 底层原理框架

### 1. Agent 基本架构

```
┌─────────────────────────────────────────────┐
│              AI Agent 架构                   │
├─────────────────────────────────────────────┤
│  ┌─────────────┐    ┌───────────────────┐  │
│  │   LLM 核心   │◄──►│   工具调用层      │  │
│  │  (推理引擎)  │    │ (Tools/Functions) │  │
│  └─────────────┘    └───────────────────┘  │
│           ▲                    ▲            │
│           │                    │            │
│  ┌────────┴─────────┐  ┌───────┴──────────┐ │
│  │   上下文管理      │  │   执行结果反馈   │ │
│  │ (Context Window) │  │  (Result Loop)   │ │
│  └──────────────────┘  └──────────────────┘ │
└─────────────────────────────────────────────┘
```

### 2. 核心组件解析

#### 🧠 LLM 推理引擎
- **作用**：理解指令、规划任务、生成代码
- **关键参数**：temperature、top_p、max_tokens
- **模型选择**：不同复杂度任务路由到不同模型

#### 🛠️ 工具调用层 (Function Calling)
```python
# 伪代码：Function Calling 原理
class Agent:
    def __init__(self):
        self.tools = {
            "read_file": read_file_function,
            "search_code": search_code_function,
            "execute_command": execute_command_function
        }

    def process(self, user_query):
        # 1. LLM 分析需要调用哪些工具
        tool_calls = self.llm.decide_tools(user_query)

        # 2. 执行工具调用
        results = []
        for call in tool_calls:
            result = self.tools[call.name](call.parameters)
            results.append(result)

        # 3. 将结果反馈给 LLM
        final_response = self.llm.synthesize(user_query, results)
        return final_response
```

#### 📚 上下文管理 (Context Management)
- **上下文窗口**：管理 token 限制
- **信息检索**：RAG (Retrieval-Augmented Generation)
- **上下文压缩**：提取关键信息，减少 token 消耗

### 3. Agent 执行流程

```

   ↑                                                                    ↓
   └──────────────────────────── 迭代优化 ───────────────────────────────┘
```

## 🔌 MCP 协议深度解析

### 1. MCP 基本概念

**MCP (Model Context Protocol)** 是 Anthropic 推出的开放协议，用于连接 AI 应用和外部数据源。

```
传统 AI 架构 vs MCP 架构：

传统架构：
AI 应用 ──► 直接访问 ──► 文件系统/数据库/API (散乱、不安全)

MCP 架构：
AI 应用 ──► MCP Client ──► MCP Server ──► 标准化接口 ──► 外部资源
```

### 2. MCP 协议架构


### 3. MCP Server 实现原理

#### 基础 MCP Server 结构
```typescript
// MCP Server 基础架构
interface MCPServer {
    // 服务器信息
    name: string;
    version: string;

    // 资源管理
    resources: Resource[];

    // 工具定义
    tools: Tool[];

    // 处理请求
    handleRequest(request: MCPRequest): MCPResponse;
}

// 资源定义
interface Resource {
    uri: string;           // 资源标识
    name: string;          // 资源名称
    description: string;   // 资源描述
    mimeType: string;      // MIME 类型
}

// 工具定义
interface Tool {
    name: string;              // 工具名称
    description: string;       // 工具描述 (给 LLM 看)
    inputSchema: JSONSchema;   // 输入参数结构
    handler: Function;         // 执行函数
}
```

#### 自定义 MCP Server 实现
```typescript
// 示例：构建一个 API 文档 MCP Server
class APIDocMCPServer implements MCPServer {
    name = "api-doc-server";
    version = "1.0.0";

    // 定义可访问的 API 资源
    resources = [
        {
            uri: "api:///users",
            name: "用户接口文档",
            description: "用户相关的所有 API 接口",
            mimeType: "application/json"
        },
        {
            uri: "api:///orders",
            name: "订单接口文档",
            description: "订单相关的所有 API 接口",
            mimeType: "application/json"
        }
    ];

    // 定义工具
    tools = [
        {
            name: "search_api",
            description: "搜索 API 接口定义，支持按关键词搜索",
            inputSchema: {
                type: "object",
                properties: {
                    keyword: { type: "string", description: "搜索关键词" },
                    module: { type: "string", description: "模块名称" }
                },
                required: ["keyword"]
            },
            handler: async (params) => {
                return await this.searchAPI(params.keyword, params.module);
            }
        },
        {
            name: "get_api_detail",
            description: "获取指定 API 的详细定义",
            inputSchema: {
                type: "object",
                properties: {
                    apiPath: { type: "string", description: "API 路径" }
                },
                required: ["apiPath"]
            },
            handler: async (params) => {
                return await this.getAPIDetail(params.apiPath);
            }
        }
    ];

    // 处理 MCP 请求
    async handleRequest(request: MCPRequest) {
        switch(request.method) {
            case 'resources/list':
                return { resources: this.resources };
            case 'tools/list':
                return { tools: this.tools };
            case 'tools/call':
                return await this.callTool(request.params);
            default:
                throw new Error('Unknown method');
        }
    }

    // 私有方法：搜索 API
    private async searchAPI(keyword: string, module?: string) {
        // 实际实现：从文档数据库或文件系统中搜索
        const results = await this.apiDatabase.search(keyword, module);
        return {
            apis: results.map(api => ({
                path: api.path,
                method: api.method,
                description: api.description,
                parameters: api.parameters
            }))
        };
    }

    // 私有方法：获取 API 详情
    private async getAPIDetail(apiPath: string) {
        const api = await this.apiDatabase.findByPath(apiPath);
        return {
            path: api.path,
            method: api.method,
            description: api.description,
            request: api.requestSchema,
            response: api.responseSchema,
            examples: api.examples
        };
    }
}
```

## 📋 OpenSpec 工作流深度解析

### 1. OpenSpec 核心理念

**OpenSpec** 是一种文档驱动的开发方法论，将软件开发流程标准化。

```
传统开发流程 vs OpenSpec 流程：

传统：需求 → 代码 → 测试 → 文档(经常缺失)
OpenSpec：提案 → 设计 → 规格 → 实现 → 归档(全程文档化)
```

### 4. OpenSpec 与 AI 协作

#### AI 辅助的 OpenSpec 流程
```python
# OpenSpec AI 协作框架
class OpenSpecAI:
    def __init__(self):
        self.llm = LLMClient()
        self.context = OpenSpecContext()

    async def create_proposal(self, user_input):
        """AI 辅助创建提案"""
        # 1. AI 分析用户输入
        analysis = await self.llm.analyze(user_input)

        # 2. 生成提案结构
        proposal = await self.llm.generate_proposal({
            'problem': analysis.problem,
            'context': self.context.get_project_context(),
            'similar_cases': self.context.find_similar_proposals()
        })

        # 3. 人工审核和修改
        return proposal

    async def create_specification(self, proposal):
        """从提案生成规格说明"""
        spec = await self.llm.generate_spec({
            'proposal': proposal,
            'project_rules': self.context.get_coding_rules(),
            'api_patterns': self.context.get_api_patterns()
        })
        return spec

    async def implement_from_spec(self, spec):
        """根据规格生成实现代码"""
        implementation = await self.llm.implement({
            'spec': spec,
            'codebase_context': self.context.get_relevant_code(),
            'templates': self.context.get_code_templates()
        })
        return implementation
```

## 🎯 Vibe Coding 应对策略

### 1. Vibe Coding 定义与区分

**Vibe Coding（Andrej Karpathy, 2025年2月提出）**：不审查、不理解、直接Accept AI生成的代码。

| 维度 | Vibe Coding | AI 辅助编程 |
|---|---|---|
| 代码生成 | AI 生成 | AI 生成 |
| 代码审查 | 不看，直接 Accept | 逐行审查 |
| 报错处理 | 粘贴给 AI | 分析根因再决定 |
| 对代码负责 | 不负责 | 完全负责 |

**核心问题**：面试官问你是不是 Vibe Coding，其实是在问：**你对你 Accept 的代码负不负责？**

### 2. 为什么说"AI 做不了"已经过时了？

**2026年的现实**：
- ✅ **复杂业务逻辑** → Claude Code 能写出带完整异常处理的微服务调用
- ✅ **安全代码** → 告诉它要注意什么，能写出带输入校验和权限检查的代码
- ✅ **跨模块调用** → 把接口文档喂给它，能生成正确的调用链路
- ✅ **性能优化** → 让它关注性能，能帮你找出 N+1 查询和内存泄漏

**结论**：继续说"AI 做不了 XX"，面试官只会觉得你脱离实际。

### 3. 面试官的真正担忧

```
表面问题：现在都是 Vibe Coding，你的优势是什么？
真正担忧：
1. 你是否失去了代码能力？
2. 你能否判断 AI 代码的正确性？
3. 你能否在 AI 失效时兜底？
4. 你是否理解 AI 工具的底层原理？
```

### 4. 核心优势框架（五个层次）

**核心观点转变**：
- ❌ "AI 做不了什么"（防守型，越守越窄）
- ✅ "AI 需要我做什么"（驱动型，越用越强）

#### 优势一：问题定义能力

**核心观点**：AI 能解决你定义好的问题，但**定义问题本身就是最难的部分**。

**具体场景**：
产品经理说"加个退款功能"——这不是需求，这是一句话。真正的需求定义要回答：
- 部分退款怎么处理？
- 退款和优惠券的互斥规则是什么？
- 多次退款的幂等性怎么保证？
- 退款超时了怎么自动关闭？

这些问题的答案，AI 不知道，产品经理也没说清楚。**是你把一句话变成了可执行的规格，AI 才能写出正确的代码。**

**面试回答**：
> "AI 很强，但它需要精确的问题定义。我的优势在于能把模糊的需求拆解成清晰的技术规格——边界条件、异常处理、业务规则，这些 AI 不会主动问你，但不说清楚代码一定写不对。"

**实践支撑**：
- OpenSpec 提案阶段的问题拆解
- 需求评审时的边界条件列举
- 技术方案评审的风险识别

**关键要点**：
- 如果你自己都没想清楚，AI 写出来的代码一定也是模糊的
- 你给它一句话，它给你一个"看起来像那么回事"的接口
- 跑是能跑，但业务逻辑经不起推敲

#### 优势二：上下文构建能力

**核心观点**：**AI 的输出质量，直接取决于你给的上下文质量。**

**实际对比**：
同样的需求，两种人用 AI：
- **A 直接说**"写一个退款接口" → AI 凭想象写，大概率不符合你的业务
- **B 给了完整的业务规则、数据库表结构、上下游接口文档** → AI 写出来的代码基本能直接用

**差距在哪**？不是 AI 的能力差距，是**喂给 AI 的上下文质量**的差距。

**上下文构建能力包括**：
- **知道给什么**：哪些信息是 AI 必须知道的，哪些是噪音
- **知道不给什么**：塞 10 万行无关代码进上下文，既浪费 Token 又干扰模型
- **知道怎么组织**：先给背景再给需求，和反过来，AI 的生成质量完全不同

**为什么同一个 AI 工具，高手用和新人用效果差 10 倍？**
不是工具不同，是输入不同。

**面试回答**：
> "同样用 Claude Code，不同人产出质量差很多。差别在于上下文构建——我给 AI 的 Prompt 包含完整的业务规则、相关代码片段和边界条件，而不是一句话就让它写。AI 的上限是由你的输入质量决定的。"

**实践支撑**：
- MCP Server 的资源选择策略（只读取相关文件）
- Cursor Skills 的上下文文件管理（精准定义所需文件）
- Prompt 的结构化组织能力（背景→需求→约束→示例）

**性能数据**：
- 只给相关代码 vs 给整个项目，Token 消耗可能差 3-5 倍
- 无关信息会干扰模型的注意力，降低生成质量
- 高质量上下文能让一次生成的代码直接可用率从 30% 提升到 80%

#### 优势三：结果验证能力

**核心观点**：**代码跑起来了 ≠ 代码对了。**

**AI 的陷阱**：AI 生成的代码经常"看着对、跑得通、但语义是错的"。

**实际案例**：
- 退款接口返回成功，但实际是退到了错误的账户
- 权限校验通过了，但用的是错误的角色
- 数据处理完成了，但精度丢失了两位小数

**为什么测试发现不了？**
测试是按你的预期写的，而你的预期可能和业务需求有偏差。

**验证能力的三个层次**：
- ❌ **基础验证**："跑一下看有没有报错"
- ✅ **业务语义验证**：这段代码的行为是否符合业务意图
- ✅ **边界验证**：极端情况下的行为是否符合预期
- ✅ **回归验证**：这次改动有没有影响其他功能

**特别注意 AI 的"合理但错误"代码**：
- 逻辑通顺、能跑通、但语义和业务需求不一致
- 这种代码最容易通过 Code Review，因为看起来真的很合理

**面试回答**：
> "AI 生成的代码我会重点验证业务语义，不是看能不能跑通，而是看行为是否符合业务意图。比如退款接口我会验证退款金额、退款对象、幂等性，这些是测试覆盖不到的，必须人工理解。"

**实践支撑**：
- Code Review 中的业务语义检查清单
- AI 代码的"合理但错误"识别经验
- 边界条件的验证方法论
- 建立了 AI 代码审查重点检查项

#### 优势四：技术决策能力

**核心观点**：AI 能列出方案 A 和方案 B 的 pros/cons，但**拍板选哪个是你决定的**。

**技术决策包括**：
- **选型决策**：用 Redis 还是 Memcached？用 gRPC 还是 REST？
- **架构决策**：拆微服务还是单体优先？同步还是异步？
- **成本决策**：花 3 天重构还是花 3 个月重构？用贵的模型还是便宜的模型？

**AI 的建议是通用的，你的决策是具体的**。
通用建议和具体场景之间，永远需要人来做判断。

**实际案例**：
AI 会告诉你"高并发场景用缓存"，但不会告诉你**你们团队的缓存之前出过两次线上事故，这次要用就得多加一层降级**。
这个判断只能你做。

**面试回答**：
> "AI 能帮我分析方案，但最终的选型决策是我做的。因为决策要考虑的不仅是技术因素，还有团队现状、业务阶段、历史教训——这些 AI 不知道，也不应该由 AI 决定。"

**实践支撑**：
- 技术方案评审中的决策框架
- 架构演进路径的选择经验
- 成本与质量的平衡考虑
- 团队能力和业务阶段的权衡

#### 优势五：成本控制能力

**核心观点**：这一条在面试里越来越重要，因为**AI 编程不是免费的**。

**成本现实**：
- 一次 Claude Code 的交互，可能消耗 5 万到 20 万 Token
- 一个项目跑下来，Token 费用可能比工程师工资还高
- 不控制成本，一个月 Token 账单可能比工程师工资还高

**成本控制能力包括**：
- 知道什么时候用大模型，什么时候用小模型
- 知道怎么组织上下文才能省 Token
- 知道怎么写 Prompt 才能减少来回次数
- 知道哪些任务让 AI 做更贵，自己做更便宜

**面试回答**：
> "一次 Claude Code 交互可能消耗 5-20 万 Token。我们团队做了成本控制——简单任务用小模型、只给相关代码、优化 Prompt 减少往返次数。这样既保证质量又控制成本，整体 Token 费用能降 60% 以上。"

**实践支撑**：
- 建立了团队模型路由策略
- MCP Server 的精准数据获取（减少无关上下文）
- Cursor Skills 的模板化复用
- 定期的成本效果评估

### 4. Token 成本控制五策略（详细版）

#### 策略一：模型路由——什么活用什么模型

**不是所有代码都需要最强的模型来写**。根据任务复杂度路由到不同模型：

| 任务类型 | 推荐模型级别 | 原因 |
|---|---|---|
| 代码补全、简单修改 | 小模型 | 速度快、成本低、够用 |
| 函数实现、Bug 修复 | 中模型 | 平衡成本和质量 |
| 架构设计、复杂重构、代码审查 | 大模型 | 需要深度推理 |
| 代码解释、文档生成 | 小模型 | 不需要强推理 |

**成本差距有多大？**
大模型的输出价格是小模型的近 20 倍。如果一个 70% 的任务能用小模型解决，整体成本能降 60% 以上。

**模型路由不是让你手动选**：
- Claude Code 内部已经在做这件事——简单补全走轻量模型，复杂推理走主力模型
- 但面试官想听的不是"工具自动做了"，而是**你理解为什么这么做**

**面试怎么说**：
> "我们团队做了模型路由策略——简单补全用小模型，复杂任务才用大模型。70% 的日常编码任务其实不需要最强模型，这样整体 Token 成本能降 60% 以上。"

#### 策略二：上下文管理——别把整个代码库塞进去

**上下文窗口是 Token 消耗的大头**。

**错误做法**：
很多人用 Claude Code 时，习惯把整个项目目录打开，让它自己找文件。结果每次交互，模型都要读取大量无关代码，Token 消耗直接翻几倍。

**正确的做法**：
- **只给相关的代码**：修改用户模块，就不要把支付模块的代码也塞进去
- **用摘要代替全文**：不需要把 500 行的配置文件全给 AI，给关键部分就行
- **按需加载**：先让 AI 看接口定义，需要实现细节时再给具体代码
- **定期清理上下文**：长时间对话会积累大量历史 Token，该开新会话就开新会话

**实际效果**：
只给相关代码 vs 给整个项目，Token 消耗可能差 3-5 倍。

**还有一个容易被忽略的点**：
**AI 读到的无关代码越多，生成质量反而越差**。
因为无关信息会干扰模型的注意力，让它关注到不该关注的地方。

所以上下文管理不只是省钱，也是在提升质量。

**面试怎么说**：
> "我会主动管理上下文，只给 AI 相关的代码片段而不是整个项目。修改用户模块就只给用户模块的代码和它依赖的接口定义。这样做 Token 消耗能降 3-5 倍，而且 AI 生成质量反而更好——因为无关信息少了，模型不容易被干扰。"

#### 策略三：Prompt 优化——一次说清楚，别来回改

**来回改是最浪费 Token 的**。

模糊的 Prompt → AI 生成不符合预期 → 再改 Prompt → 再生成 → 还是不对 → 再改……

一次说清楚，直接省掉 3-4 轮交互。

**怎么写好 Prompt**：
- **说清楚目标**：不是"写个接口"，是"写一个 REST 接口，接收退款请求，参数包括订单号和退款金额，需要幂等校验"
- **说清楚约束**：性能要求、安全要求、代码规范
- **说清楚上下文**：相关的数据库表结构、上下游接口
- **给示例**：一个具体的输入输出示例，比 100 字描述更有效

**成本对比**：
- 一次精确 Prompt 可能 500 Token
- 四轮模糊 Prompt 可能 12000 Token
- **差了 24 倍**！这还没算时间的浪费

**面试怎么说**：
> "我非常注重 Prompt 质量，会一次性说清楚目标、约束、上下文和示例。虽然准备 Prompt 需要多花点时间，但能避免 3-4 轮来回修改，总体 Token 消耗反而更低，生成的代码质量也更好。"

#### 策略四：缓存和复用

**相似的问题，不要让 AI 从零生成**。

**三个层面的缓存**：
1. **Prompt 缓存**：相同的 Prompt 前缀，API 层面可以缓存，省掉重复计算的 Token
   - Anthropic 的 API 已经原生支持了 Prompt Caching
   - 相同前缀的输入可以打到 90% 的缓存命中率

2. **代码模板**：常见的 CRUD 接口、表单验证，维护一套模板
   - AI 只需要填差异部分，而不是每次从零生成

3. **会话复用**：同一类任务的 Claude Code 会话，可以复用之前的上下文
   - 不要每次从零开始

**实际效果**：
配合 Prompt Caching，相似任务的 Token 消耗能降低 50% 以上。

**面试怎么说**：
> "我们团队维护了一套代码模板，AI 只需要根据具体需求填充差异部分，而不是每次从零生成。配合 Prompt Caching，相似任务的 Token 消耗能降低 50% 以上。"

#### 策略五：任务评估——哪些任务让 AI 做更贵

**不是所有任务都适合让 AI 做**。

**适合让 AI 做的**：
- 重复性高、模式固定的代码（CRUD、样板代码）
- 你知道要什么但手写太慢的代码
- 需要快速探索多种方案的场景
- 不熟悉的语言或框架的入门代码

**不适合让 AI 做的**：
- 改一行配置就能解决的小修改
- 你已经非常熟悉的代码区域，手写比解释更快
- 需要深度理解业务上下文的决策型代码
- 已经有精确模板、复制粘贴比生成更快的情况

**实际案例对比**：

**场景：线上报了一个 NullPointerException**
- 你翻日志定位到是 `OrderService.java` 第 127 行，`user.getAddress()` 没做空判断
- 你加一行 `if (user.getAddress() != null)` **10 秒搞定**

**如果交给 AI**：
- 很多录友直接粘贴报错信息给 AI，让 AI 去修复
- AI 读报错信息，再去读文件，又要分析上下文，再生成修复代码
- 前后 3 分钟，Token 消耗可能几万

**结果**：**10 秒的手工活，变成了 3 分钟的 AI 交互，还更贵**。

这就是"让 AI 做更贵"的典型场景：**你已经知道问题在哪、怎么改，这时候直接改就是最优解**。

**面试怎么说**：
> "我会评估每个任务是否适合用 AI。对于已经知道怎么改的问题，比如加个空判断，直接改 10 秒就完了，没必要让 AI 花 3 分钟和几万 Token。AI 用在真正需要它推理和生成的场景上，成本效益比最好。"

## 🎯 面试高频问题应对（完整版）

### Q1：AI 越来越强，你的优势是什么？

**❌ 差的回答**：
> "AI 做不了复杂业务逻辑和安全代码。"

**✅ 好的回答**：
> "AI 确实越来越强，很多之前说 AI 做不了的场景现在都做得不错。但 AI 的输出质量直接取决于人的输入质量——定义问题、构建上下文、验证结果、做决策、控成本，这五件事 AI 替代不了我。我的优势不是比 AI 写得好，是让 AI 写得更好。"

### Q2：你负责的项目里，哪些让 AI 写，哪些自己写？

**✅ 结构化回答**：
> "判断标准不是'AI 做得了还是做不了'，而是**'这段代码出 bug 的代价有多大'**和**'让 AI 写和手写哪个综合成本更低'**。
>
> **代价大、AI 写更贵的**：自己写或 AI 写但严格审查
> **代价小、AI 写更便宜的**：让 AI 加速
>
> 具体来说，核心业务逻辑、安全相关代码、性能敏感代码我会自己写或严格审查。样板代码、CRUD 接口、数据模型这些会让 AI 生成，但会通过 Rules & Skills 约束质量。"

### Q3：你怎么审查 AI 生成的代码？

**✅ 三步检查法**：
> "重点查三样：**业务语义**（代码行为是否符合业务意图）、**安全风险**（输入校验、权限控制、敏感数据）、**工程性**（性能、可维护性、规范一致性）。
>
> **特别注意 AI 的'合理但错误'代码**——逻辑通顺、能跑通、但语义和业务需求不一致。这种代码最容易漏过 Review，我会重点检查这类问题。"

### Q4：AI 生成的代码出了线上 bug，你怎么处理？

**✅ 三步走策略**：
> "**先止血，再定因，最后补流程**。
>
> **止血**：回滚或降级，先让线上恢复，不管是不是 AI 写的代码，处理方式一样。
>
> **定因**：看监控确认影响范围，看日志追踪调用链路，定位到具体的问题代码。如果是 AI 生成的代码，还要想清楚**审查的时候为什么没拦住**——是安全没审到，还是边界条件没覆盖，还是业务语义理解有偏差。
>
> **补流程**：补充测试用例、加强审查重点、甚至调整哪些场景允许 AI 生成。**一个 bug 不可怕，同类 bug 再出一次才可怕**。"

### Q5：AI 写的代码上线出问题了，让 AI 修，结果 AI 也修不好，你怎么兜底？

**这个问题很刁钻，但确实会发生**。AI 自己写的代码，自己修不好——可能是因为它对线上环境没有感知，也可能是因为问题根因涉及多个模块的交互，AI 的上下文窗口里装不下全局信息。

**✅ 兜底四步法**：
> "**你不能等 AI 来救你，你得能自己接手**：
>
> **1. 先止血**：不管 AI 能不能修，先回滚到上一个稳定版本，线上用户等不了
>
> **2. 自己排查**：看日志、看监控、看链路追踪，定位根因。这时候你之前审查 AI 代码积累的理解就派上用场了——如果你审查的时候理解了逻辑，排查速度会快很多；如果你审查的时候是'看着没问题就过了'，那排查起来跟看别人的代码没区别
>
> **3. 修复上线**：自己改代码，走正常的测试和发布流程
>
> **4. 复盘**：为什么 AI 修不好？是上下文不够，还是问题超出它的能力范围？这次复盘的结论，决定下次类似问题还要不要交给 AI
>
> **说到底，AI 修不了的时候，你得能修。这是底线。**"

### Q6：AI 编程工具的 Token 成本怎么控制？

**✅ 五策略回答**：
> "**模型路由**（70% 任务用小模型）、**上下文管理**（只给相关代码，消耗降 3-5 倍）、**Prompt 优化**（一次说清楚，往返次数降 3-4 倍）、**缓存复用**（维护模板 + Prompt Caching，相似任务降 50%）、**任务评估**（不该用 AI 的就别用）。
>
> 核心是在成本和质量之间找平衡，不是越便宜越好，也不是越贵越好。我们的实践是整体 Token 成本降了 60% 以上，同时保持了代码质量。"

### Q7：你们团队怎么管理 AI 生成的代码？

**✅ 四件事管理法**：
> "**代码归属**：谁 Accept 谁负责，AI 生成的不例外
>
> **审查流程**：AI 代码走和人工代码一样的 Review，不因为有 AI 生成标签就放松标准
>
> **监控指标**：追踪 AI 代码的 Bug 率、漏洞率、规范遵循率，用数据说话
>
> **持续优化**：根据数据调整 AI 使用策略，哪些场景鼓励用，哪些场景限制用"

### Q8：用 AI 写代码，怎么保证不泄露公司代码？

**✅ 四层防护策略**：
> "**敏感代码隔离**：核心算法、密钥管理、交易策略这些代码，不在 AI 工具里打开，更不让 AI 生成和审查
>
> **工具选择**：用企业版而非个人版，企业版有数据隔离协议，代码不会被用于训练
>
> **配置防护**：配置 .gitignore 和 .claudeignore，把敏感目录和文件排除在 AI 的访问范围之外
>
> **团队规范**：哪些项目可以用 AI、哪些不能，写进开发规范，新人入职就知道边界"
>
> 我们团队区分了敏感项目和非敏感项目，敏感项目不用 AI 工具，非敏感项目用企业版。同时配置了 .claudeignore 排除敏感文件，确保 AI 不会读到不该读的代码。"

### Q9：现在都是 Vibe Coding，你不对 AI 代码负责吗？

**✅ 态度明确**：
> "**我对所有 Accept 的代码都负责，不管是不是 AI 生成的**。审查流程一样、质量标准一样、出了问题我一样修。Vibe Coding 是不负责任的做法，我不会这么干。
>
> 实际上我建立的审查流程比以前更严格，因为我知道 AI 容易生成'合理但错误'的代码，所以我会重点检查业务语义和边界条件。"

### Q10：你觉得未来 3-5 年，AI 会完全替代程序员吗？

**✅ 理性分析**：
> "AI 会替代不会用 AI 的程序员，但不会替代所有程序员。
>
> **会被替代的**：只写样板代码、不懂业务逻辑、无法判断代码质量的'代码搬运工'
>
> **不会被替代的**：能定义问题、构建上下文、验证结果、做决策、控成本的'问题解决者'
>
> **我的策略**：持续强化 AI 替代不了的那五项能力，同时提升使用 AI 工具的工程化能力。**让 AI 成为我的放大器，而不是我的替代品**。"

## 🚀 面试策略建议

### 回答问题的黄金法则

**1. 具体化原则**
- ❌ "我用 AI 提高效率"
- ✅ "通过构建自定义 MCP Server，API 对接时间从 2 小时降到 30 分钟"

**2. 原理化原则**
- ❌ "我熟练使用 Cursor"
- ✅ "我理解 Cursor 的 Skills 机制，并根据团队规范设计了自定义 Skills"

**3. 数据化原则**
- ❌ "成本控制做得不错"
- ✅ "通过模型路由和上下文管理，Token 成本降了 60% 以上"

**4. 责任化原则**
- ❌ "AI 是辅助，最终还是人负责"
- ✅ "我对所有 Accept 的代码都负责，建立了和人工代码一样的审查流程"

### 避免的面试陷阱

**陷阱 1：过度夸大 AI 能力**
- ❌ "AI 什么都能做，只要给够上下文"
- ✅ "AI 在特定场景很强，但需要人来定义问题、验证结果"

**陷阱 2：完全否定 AI 价值**
- ❌ "AI 做不了复杂业务，还是得人来写"
- ✅ "AI 能做很多事，但需要在人的指导下才能做得好"

**陷阱 3：逃避责任归属**
- ❌ "AI 写的代码出了问题，我也没办法"
- ✅ "AI 代码我同样负责，所以审查得更严格"

**陷阱 4：缺乏深度思考**
- ❌ "我就是按 Skill 的流程操作"
- ✅ "我设计这个 Skill 是因为发现了团队的重复性工作"
